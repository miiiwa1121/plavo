# 非機能要件

plavo の性能・信頼性・プライバシー・対応環境に関する要件。

最終更新: 2026-08-28

> **注記**: 本ファイルの数値目標は現時点での**提案**であり、確定していない。実装して計測してから調整する。

## 1. 前提

D1（ポートフォリオ作品）により、非機能要件の重み付けは通常のプロダクトと異なる。

| 通常のプロダクト | plavo（ポートフォリオ） |
|---|---|
| 幅広い端末で動く | **1台の実機で確実に動く**ほうが重要 |
| 長期運用の安定性 | **デモの数分間が破綻しない**ほうが重要 |
| エッジケースの網羅 | **主要シナリオの完成度**が重要 |

したがって「対応端末を広げる」「異常系を網羅する」よりも、**デモが絶対に失敗しないこと**を最優先する。

## 2. 性能

### 2.1 応答時間

| 対象 | 目標 | 根拠 |
|---|---|---|
| 起動からカメラプレビュー表示 | 2秒以内 | トップがカメラであり、ここが遅いと第一印象が壊れる |
| 植物の検出 | 1秒以内 | 「向けたら反応する」体感の下限 |
| 検出直後の一言（事前定義） | 即時（通信なし） | D27。間を繋ぐ役割のため遅延が許されない |
| AI診断の完了 | 15秒以内 | D27で沈黙を許容する設計にしたため、上限は緩い |
| 日記・マイプラント画面の表示 | 1秒以内 | 通常のアプリ水準 |

**AI診断が遅いこと自体は失敗ではない**（D27）。ただし15秒を超えると「壊れた」と受け取られる可能性があるため、上限として設定する。

### 2.2 フレームレート

| 対象 | 目標 |
|---|---|
| カメラプレビュー | 30fps を下回らない |
| AR吹き出しの追従 | 30fps を下回らない |
| 物体検出の実行間隔 | 描画を阻害しない範囲（数フレームおきで可） |
| 写真の一覧（日記・ギャラリー）の送り | 引っかからない |

**吹き出しの追従が落ちると、体験が一気に安っぽくなる。**検出の頻度を落としてでも描画のフレームレートを守る。

**一覧では、写真を毎回開き直さない。**`LazyVGrid` は画面から出たマスを捨てるため、戻ってくるたびに同じ写真を開き直すことになる。小さい絵を一度だけ作って覚えておく（`ThumbnailCache`）。

| 開き方 | 900×1200（仕込みの仮の写真） | 4032×3024（本体カメラ） |
|---|---|---|
| 元の大きさで開く | 約 3.7 ms/枚 | 約 32 ms/枚 |
| 400px に縮めて開く | 約 4.0 ms/枚（効かない） | **約 8.7 ms/枚** |
| 覚えたものを使う | **0** | **0** |

60fps の1コマは 16.7ms。**本体カメラで撮った1枚は、開くだけで1コマを食い潰す。**縮めて開くことと、覚えておくことの両方が要る。

### 2.3 リソース

| 対象 | 目標 | 根拠 |
|---|---|---|
| デモ中の連続動作 | 10分間、発熱によるスロットリングなし | カメラ＋AR＋検出は端末負荷が高い |
| バッテリー | デモ1回（10分）でバッテリー10%以内 | 審査の場で充電できるとは限らない |

**測り方:** 説明員用のパネルの「AR の診断」に、電池の減り・熱の状態・検出の回数と処理時間を出している（`EnergyMonitor`）。手順は [device-setup.md §3](../development/device-setup.md) の「電池と熱の測り方」。

**見えていない映像では重い処理を回さない。**今日の写真（全面）を開いている間は、植物の検出と札の検索を止める（`SceneController.isCovered`）。セッションと相手は残すので、閉じれば続きから見える。

## 3. 信頼性

### 3.1 絶対に避けるべき事象

D1により、以下は**バグではなく事故**として扱う。

| # | 事象 | 対策 |
|---|---|---|
| 1 | 審査員の前で通信エラーが表示される | F-12（オフラインフォールバック） |
| 2 | 植物にカメラを向けても何も起きない | F-02の検出感度調整、D24の未検出時表示 |
| 3 | 吹き出しが空中で震える・明後日の方向へ飛ぶ | D3-a（レイキャスト＋固定距離フォールバック） |
| 4 | アプリがクラッシュする | 権限拒否・トラッキング喪失・API失敗の全経路にフォールバックを用意 |
| 5 | 記録が消える | F-11（iCloud同期） |

### 3.2 異常系の方針

**原則3（失敗をユーザーのせいにしない）**に従い、すべての異常系を植物の様子として表現する。

| 状況 | 見せ方 |
|---|---|
| 植物が見つからない | 「見当たらないなぁ」（D24） |
| 通信できない | 植物が少し眠そうにしている（D28） |
| ARトラッキングを失った | 吹き出しを消さず、その場に留める。復帰したら追従を再開 |
| 診断が失敗した | 事前定義のセリフでその場を成立させる（D6） |
| カメラ権限が拒否された | 他タブへの導線を残し、理由と再許可の導線を出す |

**「エラー」「失敗」「できません」という語を、ユーザーに見せる文言に使わない。**

## 4. プライバシー

| 項目 | 方針 |
|---|---|
| 撮影画像 | 診断のため Claude API へ送信される。**送信先で保存はしない** |
| 診断履歴・日記 | 端末内 ＋ ユーザーのiCloud。自前サーバーには置かない（D10 / D19） |
| APIキー | アプリバイナリに含めない。プロキシサーバーが保持する |
| 位置情報 | 取得しない |
| 個人情報 | 収集しない。アカウントを作らない |
| 外部送信 | Claude API 以外への送信は行わない |

**線引きの明示**: 「画像が外部に出ない」とは言えない。診断のために送信される。言えるのは「**送信先で保存されず、履歴として残るのは自分の端末とiCloudだけ**」ということ。この区別を曖昧にしない。

将来 G-03（クローズドSNS）を実装する時点で、この方針は全面的に見直しが必要になる。

## 5. 対応環境

| 項目 | 内容 |
|---|---|
| プラットフォーム | iOS（D15） |
| 対応端末 | ARKit のワールドトラッキングに対応した iPhone |
| 最低OSバージョン | 実装開始時の最新から2世代前を目安（要確定） |
| Android | 対応しない（D15） |
| iPad | 動作を妨げないが、最適化はしない |
| LiDAR | **必須としない**（D3-a）。あれば精度が上がるが、なくても固定距離フォールバックで動く |
| ネットワーク | 診断にはインターネット接続が必要。ただしオフラインでもアプリは成立する（F-12） |

**LiDARを必須にしない判断は重要**である。ポートフォリオでは「自分の手持ち端末で確実に動く」ことが、精度より優先される。

## 6. 保守性

| 項目 | 方針 |
|---|---|
| センサー入力 | モックデータと実センサーを差し替えられるインターフェースにする（F-10） |
| 診断エンジン | プロンプトとスキーマをコードから分離し、調整をアプリのビルドなしで試せるようにする |
| 導出指標 | 元データから計算する純粋関数として実装する。保存しないため、式の変更が過去データに波及しない（D23） |
| 対象植物の拡張 | ミニひまわり特化のプロンプトを、種別ごとに差し替えられる構造にする（D17の段階的解放） |
