# 機能要件

plavo（植物の気持ち翻訳アプリ）の機能要件。[decisions.md](./decisions.md) の決定37件を反映した第2版。

最終更新: 2026-08-28

## 1. このプロダクトは何か

カメラを植物に向けると、**実物の植物から吹き出しが出て、その植物が自分の言葉で状態を伝える**アプリ。

キャラクターは作らない。主役は目の前の実物の植物であり、アプリが重ねるのは「植物の声」だけ。これにより「**自分の**植物の気持ちが分かる」という一人称性が保たれる。

最終的な目標は、**ユーザーがその植物の死に、人の死と同等に感情移入して泣くこと**（D18-a）。したがってこれは植物管理ツールではなく、愛着と喪失を扱う作品である。

### 貫く3つの原則

設計判断はすべて以下のいずれかに帰着する。迷ったらここに戻る。

**原則1 — 実物を主役から降ろさない**
キャラクターを作らない（D2）。声を当てない（D5）。日記にAI生成の絵を使わない（D26）。実物より魅力的なものを置いた瞬間、主役が入れ替わる。

**原則2 — 情報を情報として出さない**
数値を画面に表示せず、必ず植物の言葉に翻訳する（D23）。「開花予測日: 10月12日」と表示した瞬間に農業管理アプリになる。植物が「あと12日で咲くよ」と言うからこのアプリである。

**原則3 — 失敗をユーザーのせいにしない**
植物が見つからないときも（D24）、通信できないときも（D28）、エラーとして表示せず、植物の様子として描く。

## 2. 用語

| 用語 | 定義 |
|---|---|
| 観察 | カメラを植物に向け、検出・診断が走り、植物が言葉を返すまでの一連 |
| 診断 | 画像とセンサー値をAIが解析し、観測結果とセリフを返すこと |
| 観測 | 診断のうち、画像からしか取れない情報（見た目の様子、生育ステージ、草丈） |
| 導出指標 | 元データから計算できる値（DLI・GDD・VPD・開花予測日など）。保存も表示もしない |
| セリフの吹き出し | 診断結果を翻訳した植物の言葉。尖った形 |
| 夢の吹き出し | 生成AIが作った、植物が動く映像。雲形（今回は実装しない） |
| 親密度 | 継続によって蓄積され、セリフの層の深さと夢の出現率を駆動する唯一の指標 |
| ガジェット | 自作の専用センサー。日照・水量・気温・湿度・栄養素を計測する |

## 4. 機能詳細

### F-01 カメラ画面

アプリのトップ。起動したらいきなりカメラが立ち上がる。説明画面もログインもない。

- タブ構成の既定タブがカメラ（D13）
- ライブプレビューを全画面で表示
- カメラ権限が未許可なら許可を促す
- 権限が拒否されてもクラッシュせず、他タブへの導線が残る
- タブは カメラ / マイプラント / 日記 / マイページ / ルーム の5つ。今回はカメラ・マイプラント・日記の3つを実装し、残り2つは枠のみ

**受け入れ基準**
- 起動から2秒以内にカメラプレビューが表示される
- タブを切り替えて戻ってもカメラが復帰する

---

### F-02 植物の検出

オンデバイスで植物を検出する。Claudeには毎フレーム投げない（D4）。

- Vision framework による物体検出を毎フレーム実行
- 検出したら、その位置と範囲を F-03 のアンカー決定に渡す
- 検出は「植物が画面に入った」の判定と、吹き出しの配置の両方を兼ねる
- 未検出のあいだは診断を走らせない（通信もAPIコストも発生しない）

**受け入れ基準**
- ミニひまわりにカメラを向けると1秒以内に検出される
- 植物以外を向けても誤って診断が走らない

**未検出時の挙動（D24）**
- エラー表示を出さない。「見当たらないなぁ」程度の軽いポップアップにとどめる
- カメラがトップ画面である以上、これが**最も長く画面に映る状態**である。ユーザーを失敗者として扱わない

---

### F-03 AR吹き出しの配置と追従

吹き出しを現実空間に固定する（D3）。

- ARKit のワールドトラッキング（6DoF）を使う
- 平面検出は使わない。植物は平面検出が最も苦手な被写体のため、特徴点ベースのトラッキングのみを使う
- 奥行きは、検出した植物の方向へレイキャストし、特徴点や平面に当たればその距離を採用。外れたら固定距離（1.2m前後）にフォールバックする（D3-a）
- カメラを回しても歩いて移動しても、吹き出しは空間のその位置に留まる。画面端から消え、戻せば同じ場所に見える

**受け入れ基準**
- 端末を左右に振ると吹き出しが画面外へ流れ、戻すと同じ位置に現れる
- 植物に近づく・離れると、吹き出しの見かけの大きさが自然に変わる
- 追跡を失っても吹き出しが明後日の方向へ飛ばない

---

### F-04 AI診断

**実行契機**: 植物を検出したら自動で1回だけ。シャッターは持たない。同じ個体には再診断せずキャッシュを使う（D4）。

**入力**
- 撮影画像
- センサーの1日分の時系列（日照・水量・気温・湿度・栄養素）
- 前回の診断結果
- 個体情報（名前・生育ステージ・育成開始日）

**出力** — 画像からしか取れない観測と、セリフのみ（D23）

| 項目 | 内容 |
|---|---|
| 植物の有無 | true / false |
| 生育ステージ | 発芽 / 本葉 / つぼみ / 開花 / 結実 / 枯死 |
| 見た目の観察 | 自由記述の配列（「下から3枚目の葉が黄色い」「茎がやや徒長」） |
| 草丈の推定 | cm |
| 確信度 | 低 / 中 / 高 |
| セリフ | 文字列 |

**出力に含めないもの** — DLI・GDD・VPD・開花予測日・次の水やり予測日・前回水やりからの経過・成長速度・総合の元気さ・緊急度・推定原因。これらは元データから計算できるため保存しない。セリフを生成する瞬間に計算し、Claudeに渡す文脈として使う。

**セリフ生成時に計算して渡す導出指標**

| 指標 | 導出元 | 意味 |
|---|---|---|
| DLI（積算光量） | 日照の積分 | 1日に浴びた光の総量。園芸で光を語る標準指標 |
| GDD（積算温度） | 気温の積算。基準温度6.7℃ | 生育の進行度 |
| 開花予測日 | GDD 958 到達予測 | ひまわりは発芽に約206、開花に約958、成熟に約1725 GDD |
| VPD（飽差） | 気温＋湿度 | 蒸散の効率。適正域は概ね 0.8〜1.2 kPa |
| 次の水やり予測日 | 土壌水分の減衰カーブ | 既存の水やりアプリ最大の不満への回答 |

**画像とセンサーの突き合わせ**: 両者が食い違ったときが最も情報量が多い。「土壌水分は十分なのに葉がしおれている → 根腐れの疑い」は、画像だけでも数値だけでも出せない診断であり、ガジェットの価値の証明になる。ただしこの判断結果も保存せず、セリフ生成時に導出する。

**時系列の価値**: 点のデータなら「今、水が足りない」しか言えないが、1日分の線があれば「昼過ぎから急に乾いてきた」「今朝は日が当たってたのに午後はずっと日陰だったね」と言える。

**対象植物**: 室内の鉢植えに限定。MVPはミニひまわり1種（D17）。1種に絞ることで診断プロンプトをひまわり特化にでき、汎用の植物診断より精度が上がる。範囲外の植物を向けても診断は試み、確信度を下げて控えめに喋る。

**受け入れ基準**
- ミニひまわりを撮影すると上記の構造化データが返る
- 水切れの株と水やり後の株で、異なる観測とセリフが返る
- 日陰の株と日向の株で、異なる観測とセリフが返る
- 植物が写っていない画像では「植物の有無 = false」が返る

---

### F-05 セリフの提示

**表示形式**: テキストのみ。声は当てない。人格を持たない効果音（葉ずれ、吹き出しの出現音）は添える（D5）。

**生成方式**: Claudeが診断と同時に生成する。ただし一般的な言葉は事前定義する（D6）。

| 事前定義 | AI生成 |
|---|---|
| 検出直後の短い一言（「はにゃ？？？」など） | 診断結果の翻訳 |
| 挨拶（おはよう / おやすみ） | 状態に固有の言い回し |
| 植物が見つからないとき、通信失敗時 | 経過を踏まえた言葉 |

事前定義側が通信失敗時のフォールバック（F-12）を兼ねる。

**待ち時間の扱い（D27）**: 診断には5〜15秒かかる。**沈黙を許容する。**カメラを向けたときに必ず何か話しているとは限らない。

```
検出 → 即座に「はにゃ？」（事前定義・0秒・通信不要）
     → 裏で診断が走る
     → 何か言うことがあれば本編のセリフへ / なければそのまま静か
```

常に喋るキャラクターは疲れる。生き物らしさは反応しないことにも宿る。

**危険域での切迫感（D30・第1層）**: 危険域が一定期間続いたら、セリフの切迫感を上げる。

| 段階 | セリフの調子 |
|---|---|
| 通常 | 「のどが渇いたよ」 |
| 心配 | 「ちょっと苦しくなってきた」 |
| 切迫 | 「もう、だめかもしれない」 |
| 消耗 | 言葉が減っていく（F-13のセリフ減衰へ接続） |

**「あなたのせいだ」とは言わない。**植物は自分の状態を言うだけ。ここで救えれば、追悼の語り口という問題自体が発生しない。**死んでから語り方を工夫するより、死なせないほうがいい。**

**確信度のトーンへの反映（D7から導出）**: 画像認識は水やりを見逃すことがある。確信が低いときは断定せず「なんだか土が乾いてる気がするんだけど…気のせいかな」のように植物の主観として揺らがせ、外れたときのダメージを抑える。

**受け入れ基準**
- 同じ状態で複数回観察しても、まったく同じ文言が連続しない
- セリフを読めば、次に何をすればよいかが分かる
- 確信度が低いとき、断定口調にならない

### F-06 植物の登録と個体同定

**登録（D9）**: 起動 → カメラ → 未登録の植物を検出 →「はじめまして」の吹き出し → 名前を入力して登録完了。専用の登録画面は作らない。種類はAIが推定し、後から修正できる。

登録という作業を出会いという体験に溶かす。ユーザーが入力するのは名前ひとつだけ。

**個体同定（D8）**

| | 同定方法 |
|---|---|
| ガジェットあり | ガジェットIDが個体IDになる。誤認が原理的に起きない |
| ガジェットなし | 画像特徴による自動同定 ＋ 名前による手動修正 |

**保持数**: 現状は「少数精鋭」。候補が少ないほど自動同定は「既知のどれに最も近いか」を選ぶだけで済み精度が上がる。数十株になると誤認が急増するため、拡大は同定精度とのトレードオフとして扱う（L-5）。

**削除（D29）**: 削除できる。ただし強い確認を挟む。確認の文面は、何が失われるかを明示する形で設計する。

**受け入れ基準**
- 未登録の植物を検出すると登録の導線が出る
- 名前をつけると登録され、再起動後も残っている
- 誤同定時に名前で選び直せる

---

### F-07 記録の蓄積

観察するたびに記録が積み上がる。これが F-09（日記）と F-13（追悼ムービー）の素材になる。

**保存するもの**
- 撮影画像
- センサーの生データ（時系列）
- AIの観測（見た目の観察・生育ステージ・草丈・確信度）
- セリフ
- 観察日時

**保存しないもの** — 導出指標すべて。計算式を後から直したときに過去データと矛盾するため、元データだけを持つ。

**AIの観測を保存する理由（D23-a）**: センサーの生データや計算値は何度計算しても同じ答えになるが、**AIが見たことはその瞬間にしか存在せず、計算で再現できない**。観測記録として扱う。

保存しない場合、3ヶ月後に追悼ムービーを作る際に90枚を再診断する必要があり、コストと待ち時間が発生するうえ、**再診断で違う答えが出て当時のセリフと食い違う**。8月10日に植物が「下の葉が黄色くなってきた」と言ったのに、3ヶ月後のAIが「特に問題なし」と答えたら、その日の記憶が書き換わる。

**受け入れ基準**
- 観察するたびに記録が増え、時系列で確認できる
- 再起動後も記録が残っている

---

### F-08 マイプラント画面

育てている植物を管理する。

- 登録した植物の一覧
- 個体ごとの詳細（名前・種類・育成開始日・現在の生育ステージ）
- 記録の推移（原則2により、数値のダッシュボードにはしない。写真と観測の時系列を見せる）
- 植物の削除（F-06）

**未確定**: 画面の具体的な構成はUI設計時に決める。

### F-09 日記

**書き手（D14）**: 基本はユーザー本人が書く。加えて自動生成モードも用意する。自動生成は、観察のたびの診断結果とセリフをもとに Claude が植物の一人称で綴る。

**絵（D26）**: 観察時に撮影した写真をそのまま使い、ユーザーがスタンプやテープ風の飾りを貼れる。AI生成イラストは使わない——生成された絵は「自分の植物」ではなく、3ヶ月後に振り返ったとき感情が乗らない。泣くために必要なのは、あの日撮った不格好な写真のほうである。

「絵日記らしさ」は、手書き風フォント・紙のテクスチャ・マスキングテープ風の飾り枠といった様式で作る。

**日記の重み**: 書いたものが最後に追悼ムービーへ流れ込むため、書く動機が「後で効くから」になる。日記タブが空のまま放置されるという一般的な懸念への回答になっている。

**受け入れ基準**
- 写真を選び、文章を書いて保存できる
- 自動生成モードに切り替えると、観察内容から日記が生成される
- 保存した日記が時系列で読み返せる

---

### F-10 センサーデータの取り込み

**今回の実装**: 事前に作成した**1日分のデータセット**を読み込む（D23）。BLE連携（G-04）は実装しない。

**データ項目**: 日照・水量・気温・湿度・栄養素の時系列。

**将来の実装**: ガジェットが常時計測して内部に記録し、アプリが近づいたときにBLEでまとめて同期する（D11）。日照時間は積算値なので、アプリを開いている瞬間だけでは測れない。「スマホと繋がっている間だけ計測する」方式は原理的に成立しない。

**受け入れ基準**
- データセットを読み込み、F-04の入力として渡せる
- 実センサーに差し替えられるインターフェースになっている

---

### F-11 データの保全

**保存先**: 端末内（D10）＋ CloudKit / iCloud による自動同期（D19）。

**理由**: 数ヶ月分の写真・セリフ・日記が追悼ムービーの素材になる。端末の故障や機種変更で消えたら体験が根本から壊れる。**その植物が生きた証が消えるということ**である。

D15でiOSネイティブを選んだことで、Apple ID に紐づく自動同期が使え、自前のアカウント基盤もバックエンドも作らずに済む。

**自前サーバーの役割**: Claude API のキーを隠す薄い中継のみ。データは持たない。

**プライバシーの線引き**: 診断のために画像はAPIへ送信される（避けられない）。送信先で保存はせず、履歴として残るのは端末内とiCloudだけ。

**受け入れ基準**
- 端末を初期化して再ログインしても記録が復元される
- APIキーがアプリバイナリに含まれていない

---

### F-12 オフライン時のフォールバック

**挙動（D28）**: 通信エラーをユーザーに見せない。事前定義のセリフと前回の診断結果だけで振る舞い、植物が少し眠そうにしている表現にする。

「今日はなんだかぼんやりする」「昨日は元気だったんだけどな」程度のことは通信なしで言える。

**背景**: デモをする場所のWi-Fiはたいてい不安定（展示会場、面接の会議室、カフェ）。審査員の前で通信エラーが出るのは、ポートフォリオで起きうる最悪の事故である。

**受け入れ基準**
- 機内モードでも植物が何かを喋る
- 「ネットワークに接続できません」という文言が一切出ない

---

### F-13 追悼ムービーの再生枠（余力があれば）

**位置づけ（D22）**: アプリ内での生成は必須としない。外部で制作した動画を再生する枠がアプリにあれば足りる。

**理由**: ポートフォリオで問われるのは「その場で生成されたか」ではなく「見た人が泣いたか」。手で編集した3分のほうが、プログラムが組んだ3分より確実に質が高い。

**内容**: これまでの植物の写真、セリフ、夢やイベントでの出来事、ユーザーのコメント、お世話の記録。その植物の人生を振り返る、約3分の動画。

**Claudeの活用（実装せず、外部制作の補助として）**: 全記録をClaudeに渡し「この植物の一生を3分で振り返る構成を作れ」と指示する。返るのは、選ぶべき写真・並べる順序・章立て・重ねるテキスト・尺の配分・間を置く箇所。それを人が手で編集する。工数ゼロで手作業の質を上げられる。

**語り口（D30）**: **死因には触れない。語るのは一緒にいた時間だけ。**ただし天寿（開花・結実まで到達）の場合のみ「役目を果たした」「種を残したよ」と明示する。天寿でない場合はその言葉が出てこない。ユーザーは、**あるはずの言葉がないことで自分で察する**。

アプリは一度も責めていないのに、ユーザーは理解する。糾弾されて流す涙は悲しみではなく罪悪感であり、D18-aの目標とは別物になるため、この線引きが要る。

トーン（写真の選び方・言葉の温度・音楽の色）は死因判定に応じて変えるが、明示はしない。

**制約**: この手法は1株目では成立しない（「天寿ならこう言う」を知らなければ不在に気づけない）。ただし主目的である「責めない」は1株目から満たされる。

### F-14 振り返り画面（D30・第3層）

**追悼と反省を同じ画面に置かない。**葬式と反省会は別の場所でやる。

追悼ムービー（F-13）を見終わった後、**別の導線として**「この子に何が起きていたか」を置く。ユーザーが見たいときだけ開き、押しつけない。

**内容**: 枯死前2週間の土壌水分・DLI・気温の逸脱から、何が不足していたかを事実として記述する。

**書き方の制約**
- **断定を避ける。**現実には過失かどうか判定できない（病気、購入時点で弱っていた、家が暗いのは過失か）
- 「水が不足していました」という事実の記述にとどめ、「あなたが水をやらなかったから」とは書かない
- **観察頻度に言及しない。**「あなたは20日間会いに来ませんでした」は、このプロダクトが最も言ってはいけない言葉である

**死因判定のロジック**

| 判定材料 | 使い方 |
|---|---|
| 到達した生育ステージ | 開花に届いたか。天寿判定の主軸 |
| 枯死前2週間の土壌水分 | 平均・最小値から水不足／過多を判定 |
| 同期間のDLI | 日照不足の判定 |
| 同期間の気温の逸脱 | 高温・低温障害の判定 |
| 観察頻度 | 判定には使うが、**文言には出さない** |

**優先度**: F-13（追悼ムービー）と同じく余力があれば。ただしF-13を実装するなら、これも同時に必要になる。

## 5. デモの受け入れ基準

D1がポートフォリオである以上、**デモで見せられることが実質的な完成の定義**になる（D25）。

```
1. アプリを開く              → いきなりカメラ。説明画面もログインもない
2. ミニひまわりに向ける      → 検出 → 診断 → 吹き出しが出る
   「のどが渇いたよ…」        ← 実際に水を切らせておいた株
3. その場で水をやる
4. もう一度向ける            → 「ありがとう、生き返った」
5. 日記タブを開く            → その日の記録が積まれている
```

| # | 見せるもの | 対応する機能 |
|---|---|---|
| 1 | 水切れ→水やり→回復（必須） | F-02 / F-03 / F-04 / F-05 |
| 2 | 光量の変化への反応 | F-04 / F-10 |
| 3 | 日記に記録が積まれていく | F-07 / F-09 |
| 4 | 追悼ムービー | F-13 |

**事前に準備が必要なもの**
- 意図的に水を切らせたデモ用のミニひまわり
- 日陰／日向を切り替えられる環境
- 1日分のセンサーデータセット
- 追悼ムービー用の仕込みデータと、外部制作の動画
