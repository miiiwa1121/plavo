## 詳細

### D1 — プロダクトのゴール

**決定**: ポートフォリオ作品・デモ。人に見せることが目的。

**帰結**:
- 最優先: 表現の完成度、初見のインパクト、動画・スクショでの映え
- 優先度を下げる: エッジケース堅牢性、長期運用のデータ設計、複数端末同期
- スコープ外: アカウント、課金、プッシュ通知、ストア審査対応
- AI診断は「本当に見ている」ことがデモの説得力になる。ただし**デモ中に失敗しないこと**が精度より重要 → フォールバック必須

### D2 — 中核体験の形

**決定**: カメラがトップ画面。植物にカメラを向けると、実物の植物から吹き出しが出る。**キャラクターは生成しない**。

**理由**: キャラクターを重ねると、主役が「アプリのマスコット」に移ってしまう。実物の植物を主役に保つことで、「**自分の**植物の気持ちが分かる」という一人称性が守られる。

**吹き出しは2種類ある**:

| 種類 | 中身 | 出るタイミング | 形 |
|---|---|---|---|
| セリフの吹き出し | 診断結果を翻訳した植物の言葉 | 即時 | 尖った吹き出し |
| 夢の吹き出し | 生成AIが作った、植物が動く映像 | 生成完了後 | 雲形 |

漫画の記法をそのまま使うため、説明なしに「喋っている／夢を見ている」が伝わる。

### D2-a — 「仕草・踊る」の担い手

**決定**: 実物の植物は動かさない。手を振る・お辞儀・踊るといった動きは、**夢の中でのみ**生成AIが表現する。

**理由**: リアルタイムのメッシュ変形は技術的難度が高く、失敗すると植物が溶けた見た目になる。夢という枠を設けることで、動きを安全な場所に隔離できる。

**副次的な利点**: 生成AIの処理時間（30秒〜数分）が「植物が眠って夢を見ている時間」として演出に転化される。技術的制約が体験の必然になる。

### D2-b — 夢の生成タイミング

**決定**: 生成が完了してから吹き出しを出す。タップすると即座に再生される。

**実装上の帰結**: 「押したらすぐ再生」を成立させるには、**生成完了 → 端末へのダウンロード → キャッシュ → 吹き出し出現** の順序が必要。生成完了＝URL取得の時点で吹き出しを出してはいけない。

### D2-c / D2-d — 夢の位置づけと出現ロジック

**決定**: 夜限定。出たり出なかったりする、やり込み・イベント要素。出現率とレア度はお世話の積み重ねで上がり、最後は運が決める（D2-d は暫定）。

**理由**: 生成AIの映像は毎回出すと急速に飽きる。「出ない」を設計に入れることで、出たときの価値が生まれる。生成頻度が1日最大1回に制限されるため、コストも読める。

**位置づけ**: サービス全体から見ればおまけ。詳細設計は後回し。

### D3 / D3-a — ARの方式と奥行き

**決定**: ワールドトラッキング（6DoF）。ARKit / ARCore を使い、現実空間に吹き出しの座標を打つ。奥行きはレイキャストで特徴点・平面に当て、外れたら固定距離にフォールバックする。

**理由**: ユーザーは前後左右上下への移動と回転を行う。向きしか見ないジャイロ固定（3DoF）では移動時に破綻する。

**技術選定への制約**: 6DoF ARを使う以上、実装手段は実質的に以下に限られる。

| 手段 | 評価 |
|---|---|
| Unity + AR Foundation | ARKit / ARCore を1コードで両対応。AR用途で最も実績がある |
| ネイティブ（Swift + ARKit / Kotlin + ARCore） | 各OSで最高品質。実装が2本になる |
| React Native / Expo | 現実的でない。メンテされた6DoF ARモジュールが存在しない |
| Flutter | プラグインの成熟度が低い |

平面検出は使わない（植物は平面検出が最も苦手な被写体）。特徴点ベースのワールドトラッキングのみを使う。

### D4 — 診断の実行契機

**決定**: 植物を検出したら自動で1回だけ診断する。シャッター操作は持たない。同じ植物には再診断せずキャッシュを使う。

**理由**: シャッターがあると撮影アプリになり、「向けたら喋りだした」という体験が失われる。一方で継続診断はコスト・発熱・結果のブレが表に出る。

**帰結**: 「植物が画面に入った」の判定を毎フレームAIに投げられないため、**オンデバイスの植物検出が必須**になる。この検出結果は、そのまま吹き出しのアンカーに使う。

### D4-a — 再診断の契機（D4とD25の矛盾の解消）

**発見された矛盾**: D4は「検出したら自動で1回。以降はキャッシュ」と定めていたが、D25のデモシナリオは「水やり前に観察 → 水をやる → もう一度向ける → 『ありがとう、生き返った』」を要求する。キャッシュして再診断しないなら4手目が動かない。これはデモだけの問題ではなく、D7で決めたコアループ（前回との差分に気づいて喜ぶ）そのものが成立しなくなる。

**決定**: **画像診断とセンサー読み取りで頻度を分ける。**

| 対象 | 頻度 |
|---|---|
| **画像診断** | 数分に1回を上限とするスロットル。加えてセンサーの急変で即時起動 |
| **センサー読み取り** | リアルタイム（常時） |

画像診断の起動条件:

| トリガー | 検知内容 |
|---|---|
| 土壌水分の急上昇 | 水やりが行われた → 即時に再診断 |
| 照度の大幅な変化が継続 | 置き場所が変わった → 即時に再診断 |
| スロットル時間の経過 | 数分以上 → 次の検出時に再診断 |
| 上記以外での再検出 | **診断しない。**キャッシュを使う |

**理由**: 植物の姿は数分どころか数時間、場合によっては数日変わらない。カメラを向け直すたびに診断すると、コストだけ増えて得るものがない。一方でセンサー値は刻々と変わるため、常時読み続ける。

水やりの検知はセンサー側で起きるので、リアルタイムに拾える。D7で決めた「申告制を採らず、機械が検知したものだけ信じる」原則がそのまま使え、D4の「シャッターを持たない」も維持される。

**派生仕様 — 同じセリフを繰り返さない**: スロットル内に再検出した場合、本編のセリフを繰り返さない。短い一言だけ出すか、黙る。10秒おきに同じことを言う植物は不自然であり、D27で決めた「沈黙の許容」がそのまま適用できる。

**ガジェットなしの場合（将来）**: センサーがないため、時間経過と画像の差分で判定するしかない。精度は落ちる。


### D5 — セリフの提示

**決定**: テキストのみ。声は当てない。人格を持たない効果音（葉ずれ、吹き出しの出現音）は添える。

**理由**: D2でキャラクターを作らないと決めたのと同じ論理。声を当てた瞬間に「アプリのキャラクター」になる。声は見た目より強く人格を規定する。テキストなら読む人の頭の中で各自の声になる。

### D6 — セリフの生成

**決定**: Claudeが1回の呼び出しで、診断の構造化データとセリフを同時に生成する。ただし一般的な言葉は事前定義する。

**境界**:

| 事前定義 | AI生成 |
|---|---|
| 挨拶（おはよう / おやすみ） | 診断結果の翻訳（症状・原因・お世話の要求） |
| お世話への基本リアクション | 状態に固有の言い回し、経過を踏まえた言葉 |
| 植物が見つからないとき、通信失敗時 | |
| アンロック演出のセリフ | |

事前定義側が通信失敗時のフォールバックを兼ねる。

**理由**: 「翻訳」をテンプレートに落とすとプロダクトの本質が失われる。一方で診断とセリフを2回に分けると、同じ画像を見た結果を分ける必然性がないままレイテンシとコストが2倍になる。

### D7 — お世話の検知

**決定**: ガジェットなしの場合、**画像認識による判断のみ**。お世話の申告ボタンは持たない。ガジェットありの場合、センサーが自動検知する。

**理由**: 申告制は証明ができない。植物は自分で見て分かることしか知らない、という制約をそのまま設計原理にする。

**帰結**: コアループは以下になる。

```
観察する → 診断 → 植物が語る → （現実世界でお世話する） → また観察する → 前回との差分に気づいて喜ぶ
```

前回診断の保存が必須要件になる。差分がなければ「良くなったね」が言えない。

**設計原理（この決定から導出）**: 診断の確信度をセリフのトーンに反映させる。確信が低いときは「なんだか土が乾いてる気がするんだけど…気のせいかな」のように植物の主観として揺らがせ、外れたときのダメージを抑える。

### D8 — 個体の同定

**決定**:

| | 同定方法 |
|---|---|
| ガジェットあり | ガジェットIDが個体IDになる。誤認が原理的に起きない |
| ガジェットなし | 画像特徴による自動同定 ＋ 名前による手動修正 |

植物ひとつひとつに名前をつけるよう促し、同定が誤っていたら名前で選び直せるようにする。

**保持数**: 現状は「少数精鋭」。技術的・UX的に問題がなければ増やす。候補が少ないほど自動同定は「既知のどれに最も近いか」を選ぶだけで済むため精度が上がる。数十株になると誤認が急増するので、保持数の拡大は同定精度とのトレードオフとして扱う。

### D9 — 植物の初回登録

**決定**: 起動 → カメラ → 未登録の植物を検出 →「はじめまして」の吹き出し → 名前を入力して登録完了。専用の登録画面は作らない（出来次第で再検討 = L-6）。種類はAIが推定し、後から修正できるようにする。

**理由**: 専用の登録画面を作ると、アプリの第一印象がフォーム入力になり、植物管理アプリに見える。登録という作業を出会いという体験に溶かす。ユーザーが入力するのは名前ひとつだけ。

### D10 — データとサーバー

**決定**: サーバーは Claude API と動画生成 API のキーを隠すための薄い中継のみ。診断履歴・撮影画像・夢の動画はすべて端末内に保存する。

**理由**: クラウドDBが効くのは機種変更時の引き継ぎと複数端末での閲覧だが、どちらもデモでは発生しない。サーバーにデータを持つと認証・DB設計・ストレージ・削除導線が芋づるで必要になり、ARと診断という本題から工数が逃げる。

**プライバシーの線引き**: 診断のために画像はAPIへ送信される（避けられない）。送信先で保存はせず、履歴として残るのは端末内だけ。

**既知の制約**: アプリを配布して不特定多数に触らせる場合、APIコストが青天井になる。レート制限のためにはサーバー側に状態が必要。配布方法が決まった時点で再検討する。

### D11 — ガジェット連携

**決定**: BLE + ガジェット内にログ蓄積。常時計測して内部に記録し、アプリが近づいたときにまとめて同期する。加えて、Wi-Fi によるクラウド接続を上位階層として用意する。

**理由**: 日照時間は積算値なので、アプリを開いている瞬間だけでは測れない。水量の変化も気温の推移も同じで、点ではなく線のデータが要る。「スマホと繋がっている間だけ計測する」方式は原理的に成立しない。

BLE同期を選ぶ理由は、ユーザーがやることが電池を入れて土に挿すだけで済むこと（Wi-Fiパスワード入力という最大の離脱ポイントが消える）、消費電力が桁違いに小さいこと、そして D10（端末内保存）と整合することにある。

**3階層構造**:

| 階層 | 手段 | 得られるもの |
|---|---|---|
| 1 | アプリのみ | 画像認識による診断とセリフ |
| 2 | ＋ ガジェット（BLE） | 実測値、留守中のログ、自動お世話検知、確実な個体同定 |
| 3 | ＋ Wi-Fi接続 | 外出先からの状態把握、遠隔水やり、家族とのシェア |

**階層3の扱い**: 階層3は D10（端末内保存）と D1（アカウントはスコープ外）の両方と衝突する。外出先から見るにはクラウドにデータが要り、家族とシェアするにはアカウントと権限管理が要る。**設計としては3階層で定義し、今回の実装スコープからは階層3を外す。**

**階層3で見つかった良い性質**: 遠隔水やりは D7 の原理と矛盾しない。「申告制は証明できない」から画像認識のみにしたが、遠隔水やりは装置が実際に水を出すので証明できる。したがって階層3ではお世話ボタンが正当な形で復活する。押した結果として本当に水が出るなら、それは申告ではなく実行である。

**ハードの段階差**: 階層3ではセンサーからアクチュエータへの格上げが起きる（専用タンク、ポンプ、バルブ）。電源・防水・故障時の安全設計を含む別次元の開発になるため、階層2とは明確に切り離す。

### D12 — 継続の手応え

**決定**: 親密度という指標を一本だけ持ち、それが「セリフの層の深さ」と「夢の出現率」の両方を駆動する。

親密度が上がると、セリフの層が深くなる。最初は状態を伝えるだけ。やがて挨拶をし、名前を呼び、思い出を語るようになる。同時に夢を見る確率も上がる。

**理由**: 複数のゲージを持つと植物が管理対象に見える。親密度・健康度・経験値が並ぶと育成シミュレーションのステータス画面になる。関係が深まるという一次元の変化だけにしておけば、ゲージを表に出さずに「最近よく喋るようになった」という体感で伝えられる。

### D13 — 画面構成

**決定**: タブナビゲーション（Instagram風）。起動時のデフォルトタブはカメラ。

| タブ | 役割 | 状態 |
|---|---|---|
| カメラ | メイン。AR・診断・セリフ・夢 | 確定 |
| マイプラント | 育てている植物の管理 | 中身は未定 |
| 日記 | 植物との思い出を残す絵日記 | D14で方針決定 |
| プロフィール | ユーザー自身の情報 | 中身は未定 |
| ルーム | 自分だけの部屋。ゲーム要素 | D16で形態決定、実装は後回し |

まず4タブで設計し、ルームは枠だけ残す。

**D57 でルームを廃止し、同じ位置（4つ目）をトーク（D57-a で命名）に置き換えた。**

### D13-a — 5つ目のタブの名前を「プロフィール」にする（D13 の改訂）

**決定**: 5つ目のタブの名前を「マイページ」から**「プロフィール」**に改める。

**理由**: **タブバーの項目の幅は、名前の文字数で決まる。**左右の重さが釣り合っていないと、真ん中の「日記」が画面の中心からずれる。その上に並ぶ中身（ギャラリーの列、写真の枠）は画面の中心にそろえているため、**並べて見ると中心が食い違って見えた。**

実測（iPhone 17・pt。画面の中心は 201）:

| | 左（カメラ＋マイプラント） | 右（ルーム＋5つ目） | 「日記」の中心 |
|---|---|---|---|
| 「マイページ」（5文字） | 74 ＋ 88.3 ＝ **162.3** | 74 ＋ 79 ＝ **153** | 205.7（**4.7 右へずれる**） |
| 「プロフィール」（6文字） | 74 ＋ 88.3 ＝ **162.3** | 74 ＋ 88.3 ＝ **162.3** | **201.0（ちょうど中心）** |

**左右を「3文字＋6文字」でそろえる。**同じ文字数なら幅も同じなので、文字の大きさが変わっても釣り合いは崩れない。「日記」自体は2文字で最小幅（74）に張り付くため、中央の名前の長さは効かない。**タブの名前を変えるときは、反対側の文字数と合わせること。**

**意味の面でも合う。**D20 で「他人に公開する自己紹介」と定めており、「プロフィール」はその中身をそのまま指す。「マイページ」は中身を何も言っていない。

**選んでいるタブでは位置が変わらない。**5つのタブを順に選んで測り、項目の位置が同じであることを確かめた。

### D14 — 日記

**決定**: 基本はユーザー本人が書く。加えて自動生成モードも用意する。

**帰結**: 日記の編集UI（写真選択・テキスト入力）が必要要件になる。自動生成モードは、観察のたびの診断結果とセリフをもとに Claude が植物の一人称で綴る。

### D15 — 技術スタック

**決定（暫定）**: iOSネイティブ。Swift + SwiftUI + ARKit + Vision。バックエンドはAPIキーを隠す薄い中継のみで、言語は未定。

**理由**: D3（6DoF AR）と D13（Instagram風のタブUI）は相性が悪い制約の組み合わせである。Unity は AR に強いがUIが極端に弱く、タブバー・リスト・テキスト入力といった当たり前の部品を全部自作することになる。ネイティブは ARもUIも第一級で、代償はプラットフォームごとの実装。

D1（ポートフォリオ）なら1プラットフォームで十分であり、両対応のために Unity を選んでUIの質を落とすのは目的に対して逆行する。

iOSを選ぶ具体的な利点: ARKit が最も安定している / **Vision framework でオンデバイス物体検出が標準機能として使える**（追加のモデル調達が不要）/ SwiftUI でタブUIが自然に書ける / Core ML で診断補助モデルを後から載せられる。

**前提**: 手持ちの端末がiPhoneであること。

**状態が暫定である理由**: 要件が確定しきっていないため、今後の決定によって変更の可能性がある。

### D16 / D16-a — ルーム画面

> **廃止（D57）。**ルームはやめ、4つ目のタブはトークになった。以下は当時の記録として残す。

**決定**: 正方形の3D空間ルーム。**RealityKit** で実装し、D15 を維持する。

**「3DならUnity」は誤り**: iOSネイティブには3Dフレームワークが標準で載っている。正方形の固定ルームに家具やアイテムを配置する規模なら RealityKit で十分であり、しかも ARKit と同じフレームワークなのでアセットとレンダリングを共通化できる。植物のモデルも集めたアイテムも、同じ形式でARとルームの両方に使える。

Unity との実際の差は3D**制作**の生産性（エディタ、アセットストア、物理・アニメーション）だが、視点の決まった部屋にオブジェクトを並べる用途ではその差が効く場面が限られる。一方で Unity を選ぶと日記もプロフィールもマイプラントもUnityのUIになるという代償は変わらず、**未定のルーム1画面のために確定した4画面を犠牲にする**構図になる。

**工数上の警告**: 3Dルームの本当のボトルネックは実装ではなく**3Dアセットの調達**。部屋・家具・装飾アイテムのモデルを揃える作業は、コードを書く時間より長くかかる可能性がある（L-7）。


### D17 — 対象とする植物

**決定**: 大前提として室内の植物。まずは室内の鉢植え（観葉植物）に限定し、**段階的に対象を解放していく**。種類に制限を持たせたくないが技術的に難しいため、この順序を取る。

**MVPはミニひまわり1種に絞る。**

**ミニひまわりを選ぶ理由**:

| 観点 | 内容 |
|---|---|
| 変化が速い | 発芽から開花まで約60日。日単位で見た目が変わる。D7のコアループ（前回との差分に気づいて喜ぶ）は変化がなければ成立しないが、観葉植物は数ヶ月見ても変わらない |
| 状態が劇的 | 水切れで数時間のうちにうなだれ、水をやれば同じ日のうちに立ち上がる。この落差がデモとして圧倒的に分かりやすい |
| 個性が備わっている | 太陽を追う、背を伸ばしたがる、花を咲かせる。セリフに書くべき個性が植物側に元からある。「日なたが恋しい」が比喩ではなく事実になる |

1種に絞ることで**診断プロンプトをひまわり特化にでき**、汎用の植物診断より精度が跳ね上がる。

**範囲外の扱い**: 「観葉植物しか受け付けない」という排他的な作りにはしない。範囲外の植物を向けても診断は試み、確信度を下げて控えめに喋る（D7の設計原理を流用）。

### D18 — ライフサイクル

**決定**: 設計としては**種から枯れて無くなるまで全部**を扱う。ただしモックで見せられるのは成長過程ではなく、水分量や光量の変化に対する植物の反応が主になる。

| | 範囲 |
|---|---|
| プロダクトとしての設計 | 発芽 → 本葉 → つぼみ → 開花 → 結実 → 枯死 |
| デモで見せるもの | 水切れ→水やり→回復、日照不足→日向へ移動、といった数時間単位で観測できる反応 |

デモに60日を要しない。ミニひまわりは水切れで数時間のうちにうなだれ、水をやれば同じ日のうちに立ち上がる。デモ用の株を意図的に水切れさせておけばよい。

### D18-a — 枯死の扱い

**決定**: 枯れゆく過程でセリフが徐々に減っていく。そして最後に**約3分の追悼ムービー**が生成される。

**追悼ムービーの内容**: これまでの植物の写真、セリフ、夢やイベントでの出来事、ユーザーのコメント、お世話の記録。その植物の人生を振り返るもの。既存素材の編集（スライドショー＋テキスト＋BGM）であり、生成AIによる動画生成とは別系統。端末内で完結できる。

**設計目標**: ユーザーが**人の死と同等に植物へ感情移入し「泣く」こと**。したがって死という概念は曖昧にせず適切に表現する。人間の葬式と同じ扱い。リアリティを追求し、**植物を人と同等に扱う**ことを軸とする。

**セリフの減衰**: 饒舌だった植物が、だんだん言葉少なになる。説明せず、量で伝える。

**この決定がもたらす波及**:

1. **概要にあった「成長ムービー」の正体が判明**。「お世話を続けた期間の成長記録をムービーで振り返る」は、この追悼ムービーと同じ機能系統。いつでも見られる振り返りと、最期の総括。実装は共通化できる
2. **日記の価値が跳ね上がる**。書いたものが最後にムービーへ流れ込むため、書く動機が「後で効くから」になる。日記タブが空のまま放置されるという懸念への最も強い回答
3. **データ喪失が致命傷になる**。数ヶ月分の記録が消えることは、その植物が生きた証が消えること。D10（端末内保存のみ）では不十分 → D19 へ

### D19 — 記録の保全

**決定**: CloudKit / iCloud で自動保全する。自前のアカウント基盤もバックエンドも作らない。

**理由**: D18-a により、数ヶ月分の写真・セリフ・日記が追悼ムービーの素材になる。端末の故障や機種変更で消えたら体験が根本から壊れる。D15でiOSネイティブを選んだことで、Apple ID に紐づく自動同期が使え、**D10の「自前サーバーはAPIプロキシのみ」を維持したままデータだけ守れる**。


### D20 / D20-a — プロフィールとクローズドSNS

### D22 — 追悼ムービーの作り方

**決定**: 余力ができた場合は追悼ムービーに向ける。ただし**アプリ内での生成は必須としない**。外部で制作したモック動画を再生する枠がアプリにあれば足りる。優先度は「できたらいいな」。

**理由**: ポートフォリオで問われるのは「その場で生成されたか」ではなく「見た人が泣いたか」。手で編集した3分のほうが、プログラムが組んだ3分より確実に質が高い。実装としての生成機能は、デモで見せる価値に対して工数が見合わない。

**技術的な整理（将来アプリ内生成する場合の参考）**:

追悼ムービーは生成AIではなく**既存素材の編集**である。写真・セリフ・日記という手元にある素材を並べる作業。

| 方法 | 評価 |
|---|---|
| AVFoundation で端末内合成 | 素材が全部端末内なのでアップロード不要、コストゼロ、共有可能なファイルが作れる。第一候補 |
| サーバーで ffmpeg | 端末負荷はゼロだが、数ヶ月分の写真のアップロード時間・コスト・プライバシーの問題 |
| 動画生成SDK（Shotstack等） | 実装は最速。外部依存とランニングコストを負う |
| アプリ内でアニメーション再生のみ | 実装は最軽量だが、保存も共有もできない |

**本質は編集の設計にある**。数ヶ月分の写真からどの15枚を選ぶか、どの順序で並べるか、どのセリフをどこに重ねるか、どこで間を作るか。技術ではなくここが作品性を決める。

**Claudeの活用（実装せず、外部制作の補助として使う）**: 全記録（診断履歴・セリフ・日記・写真のメタデータ・お世話の記録）をClaudeに渡し、「この植物の一生を3分で振り返る構成を作れ」と指示する。返るのは、選ぶべき写真、並べる順序、章立て、重ねるテキスト、尺の配分、間を置く箇所。それを人が手で編集する。工数ゼロで手作業の質を上げられる。

### 参考 — 夢ムービーの技術（今回は実装しない）

image-to-video。Claudeは動画を生成できないため別ベンダーが必要（Google Veo / Runway Gen-4 / Luma Dream Machine / Kling など）。いずれも**静止画1枚＋テキストプロンプト → 5〜10秒のクリップ**、生成30秒〜数分、1本あたり数十〜数百円が相場。

工夫の余地:

1. **短いループにする** — 3分は不要。5秒のクリップを吹き出しの中でループ再生する。「夢」らしく、コストも1/10以下
2. **入力画像を作り込む** — 撮影写真をそのまま渡すとただ揺れる植物になる。背景を抜いて夢らしい空間に合成してから渡すと生成結果が一気に「夢」になる
3. **プロンプトをClaudeに書かせる** — 診断結果 → 夢の内容の変換はClaudeが得意。元気なら太陽に向かって伸びる夢、水不足なら雨を待つ夢。**Claudeが「何を夢見るか」を決め、動画生成APIが「それを映像にする」**
4. **一貫性を保つ** — 必ず同じ株の写真を入力に使い、同一個体であることを担保する


### D23 / D23-a — 診断の入出力

**前提の変更**: 今回は**1日分のデータセットを事前に作成する**ため、**ガジェットがある前提で実装する**。D7で決めた「ガジェットなしは画像認識のみ」は今回のスコープから外れ、将来対応となる。

**入力**: 撮影画像 / センサーの1日分の時系列（日照・水量・気温・湿度・栄養素）/ 前回の診断結果 / 個体情報（名前・生育ステージ・育成開始日）

**出力（診断が返すもの）**:

| 項目 | 内容 |
|---|---|
| 植物の有無 | true / false |
| 生育ステージ | 発芽 / 本葉 / つぼみ / 開花 / 結実 / 枯死 |
| 見た目の観察 | 自由記述の配列（「下から3枚目の葉が黄色い」「茎がやや徒長」） |
| 草丈の推定 | cm |
| 確信度 | 低 / 中 / 高（この観測がどれだけ信頼できるか） |
| セリフ | 文字列（D6により同時生成） |

#### 貫く原則1 — 再計算できるものは保存しない

診断が返すのは、**画像からしか取れない観測**と**セリフ**だけ。DLI・GDD・VPD・開花予測日・次の水やり予測日・前回水やりからの経過・成長速度・総合の元気さ・緊急度・推定される原因は、**すべて元データから計算できるため保存しない**。セリフを生成する瞬間に計算し、Claudeに渡す文脈として使う。

導出値を保存すると、後で計算式を直したときに過去データと矛盾する。元データだけ持てば、式を変えても全期間が即座に新しい値になる。

#### 貫く原則2 — 情報を情報として出さず、必ず翻訳を通す

導出指標は**画面にも出さない**。「開花予測日: 10月12日」と表示した瞬間に、これは農業管理アプリになる。植物が「あと12日で咲くよ」と言うからこのアプリである。

これは D2（キャラクターを作らない = 実物の植物を主役に保つ）、D5（声を当てない = 人格を固定しない）と同じ論理の延長にある。

**例外はマイプラントの「育成」だけ（D43）。**植物が話す場面ではなく、人が土の状態を確かめに来る場所のため、実測値をそのまま出す。

#### 例外 — AIが見たことは保存する（D23-a）

センサーの生データや計算値は何度計算しても同じ答えになるので保存不要だが、**AIが見たことはその瞬間にしか存在せず、計算で再現できない**。観測記録に近いものとして元データ扱いする。

保存しない場合の具体的な損失:

| | 観察も保存 | 画像だけ保存 |
|---|---|---|
| 3ヶ月後の追悼ムービーの素材 | 90日分が即座に使える | 90枚を再診断する必要がある |
| コスト | ゼロ | 90回分のAPI費用と待ち時間 |
| 一貫性 | あの日植物が見たことがそのまま残る | 再診断で違う答えが出て、**当時のセリフと食い違う** |

8月10日に植物が「下の葉が黄色くなってきた」と言ったのに、3ヶ月後に同じ写真を見せたAIが「特に問題なし」と答えたら、その日の記憶が書き換わる。

#### 参考 — セリフ生成時に計算する導出指標

リサーチの結果、園芸で「育成者が本当に欲しがるデータ」として繰り返し挙がるのは以下。いずれも**ガジェットの5項目から計算で導出でき、追加センサーは不要**。

| 指標 | 導出元 | 意味 |
|---|---|---|
| **DLI**（積算光量, mol/m²/day） | 日照センサーの積分 | 園芸で光を語る唯一の標準指標。照度ではなく「1日に浴びた光の総量」で、植物が実際に反応するのはこちら |
| **GDD**（積算温度） | 気温の積算 | 生育の進行度。ひまわりの基準温度は 6.7℃ |
| **開花予測日** | GDD 958 到達予測 | ひまわりは発芽に約206 GDD、**開花に約958 GDD**、成熟に約1725 GDD。気温を積算すれば「あと何日で咲くか」を算出できる |
| **VPD**（飽差, kPa） | 気温＋湿度の計算 | 湿度は蒸散量と直接関係しないが、VPDは直接関係する。適正域は概ね 0.8〜1.2 kPa |
| **次の水やり予測日** | 土壌水分の減衰カーブ | 既存の水やりアプリ最大の不満（「一定間隔で水やりすると土が乾ききっておらず根腐れする」）への構造的な回答 |

開花予測がひまわりで成立するのは、D17でミニひまわりを選んだ判断の思わぬ副産物。植物自身が「あと12日で咲くよ」と言えて、それが当たれば、このアプリが本当に植物の内部を見ていることの証明になる。

出典: [Apogee Instruments — DLI](https://www.apogeeinstruments.com/daily-light-integral-measuring-light-for-plants/) / [Virginia Tech — Calculating and Using DLI](https://www.pubs.ext.vt.edu/SPES/spes-720/spes-720.html) / [NDSU — Sunflower Development and Growing Degree Days](https://www.ndsu.edu/agriculture/ag-hub/ag-topics/crop-production/crop-pest-report/plant-science/sunflower-development-and-growing) / [Pulse Grow — VPD Guide](https://pulsegrow.com/blogs/learn/vpd) / [植物の水やりを記録・管理・通知するアプリ3選](https://cotomono.life/plant-manager-select3/)

#### 画像とセンサーの突き合わせ

センサーが入ると、診断は「見た目からの推定」ではなく**画像と数値の突き合わせ**になる。最も情報量が多いのは両者が食い違ったとき。

> 土壌水分は十分なのに葉がしおれている → **根腐れの疑い**

これは画像だけでも数値だけでも出せない診断であり、ガジェットの価値の証明になる。ただし D23 の原則により、この判断結果は保存せず、セリフ生成時に導出する。

**時系列の価値**: 点のデータなら「今、水が足りない」しか言えないが、1日分の線があれば「昼過ぎから急に乾いてきた」「今朝は日が当たってたのに午後はずっと日陰だったね」と言える。時間を語れるかどうかでセリフの質が大きく変わる。


### D24 — 植物が見つからないときの挙動

**決定**: エラーとして扱わず、「まだ会えていない」状態として描く。実装は「見当たらないなぁ」程度の軽いポップアップにとどめ、詳細はUI設計時に決める。

**理由**: カメラがトップ画面である以上、これが**最も長く画面に映る状態**になる。アプリを開いた瞬間は必ずここから始まり、外出先で開けば最後までこの状態が続く。

多くのアプリはここで「植物が見つかりません」と赤字を出したりスキャン枠を点滅させたりするが、どちらも**ユーザーを失敗者として扱う**設計である。植物が写っていないのは、まだカメラを向けていないだけであってエラーではない。

D18-a の「植物を人と同等に扱う」という軸の、日常側での現れ。人に会いに行くとき、会えるまでの時間は失敗ではない。

**技術上の利点**: この状態では診断を走らせない。オンデバイス検出だけが動き、Claudeは呼ばれない。コストがかからない状態を最も長く画面に出すことになる。

### D25 — デモのシナリオ

**決定**: 以下の4つを見せる。これがそのまま実装の優先順位になる。

| # | 見せるもの | 位置づけ |
|---|---|---|
| 1 | **水切れ→水やり→回復** | 必須。デモの核 |
| 2 | 光量の変化への反応 | センサー値が診断に効いていることの証明 |
| 3 | 日記に記録が積まれていく | 「その場の診断」ではなく「時間の積み重ね」を扱うことの証明 |
| 4 | 追悼ムービー | 企画の感情的な到達点 |

**基本の流れ**:

```
1. アプリを開く              → いきなりカメラ。説明画面もログインもない
2. ミニひまわりに向ける      → 検出 → 診断 → 吹き出しが出る
   「のどが渇いたよ…」        ← 実際に水を切らせておいた株
3. その場で水をやる
4. もう一度向ける            → 「ありがとう、生き返った」
5. 日記タブを開く            → その日の記録が積まれている
```

**2〜4が核心**。同じ植物が、水をやる前と後で違うことを言う。これが目の前で起きれば、AIが本当に見ていることは説明不要で伝わる。ミニひまわりは水切れからの回復が数時間で目に見えるため、デモの時間内に完結できる（D17）。

**準備が必要なもの**:
- 意図的に水を切らせたデモ用の株
- 日陰／日向を切り替えられる環境
- 1日分のセンサーデータセット（D23）
- 追悼ムービー用の仕込みデータと、外部制作の動画（D22）


### D26 — 日記の「絵」

**決定**: 観察時に撮影した写真をそのまま使い、ユーザーがスタンプやテープ風の飾りを貼れるようにする。

**AI生成イラストを採らない理由**: 生成された絵は「自分の植物」ではない。D18-a の目標はその植物の死に泣くことであり、3ヶ月後に振り返ったとき並んでいるのがAIの描いた汎用的なひまわりの絵では感情が乗らない。**泣くために必要なのは、あの日撮った不格好な写真のほう**である。

これは D2（キャラクターを作らない）と同じ判断。実物より魅力的な絵を置いた瞬間、主役が入れ替わる。

**「絵日記らしさ」の作り方**: 手書き風フォント、紙のテクスチャ、マスキングテープ風の飾り枠。写真を絵日記の様式に載せることで、生成AIを使わずに情緒は作れる。デコレーション要素はルーム画面の飾り付けとも系統が揃う。

### D27 — 診断の待ち時間

**決定**: **沈黙を許容する。**カメラを向けたときに必ず何か話しているとは限らない。何もない時間があること自体は問題ではない。間を繋ぐために、検出直後に事前定義の短い一言（「はにゃ？？？」など）を出す。

```
検出 → 即座に「はにゃ？」（事前定義・0秒・通信不要）
     → 裏で診断が走る
     → 何か言うことがあれば本編のセリフへ / なければそのまま静か
```

**理由**: 常に喋るキャラクターは疲れる。**生き物らしさは反応しないことにも宿る。**犬に話しかけても、こちらを見て終わることがある。沈黙を許容すると、喋ったときの重みが増す。

短い一言は D6 で決めた事前定義の枠にそのまま収まる。通信不要で即座に出せる。

**背景**: Claudeに画像とセンサー時系列を投げて構造化結果とセリフを生成させると、現実的には5〜15秒かかる。ここに素のローディング表示を出すと「向けたら喋りだす」体験が「待たされる作業」に変わる。速いモデルに落とす選択肢は採らない——D6で「翻訳をテンプレートに落とすと本質が失われる」と判断したのと同じ失敗を、別の形でやることになるため。


### D28 — オフライン時の挙動

**決定**: 通信エラーをユーザーに見せない。事前定義のセリフ（D6）と前回の診断結果だけで振る舞い、植物が少し眠そうにしている表現にする。

**理由**: 診断は Claude API を叩くため通信が要る。そして**デモをする場所のWi-Fiはたいてい不安定**（展示会場、面接の会議室、カフェ）。審査員の前で通信エラーが出るのは、ポートフォリオで起きうる最悪の事故である。

D27で「必ず喋るわけではない」と決めたことがここで効く。「今日はなんだかぼんやりする」「昨日は元気だったんだけどな」程度のことは通信なしで言える。

裏で何が起きているかを植物の様子として表現する点で、D24（見つからないときをエラー扱いしない）と同じ原理。

**副次効果**: D23の「1日分のデータセットを事前に用意する」方針が、そのままオフライン対策を兼ねる。

### D29 — 植物の削除

**決定**: 削除できる。ただし強い確認を挟む。

**論点だったこと**: D18-aで「植物を人と同等に扱う」と決めた軸から見ると、一覧からスワイプで消せる削除ボタンは矛盾する。枯死は終わりであって消滅ではなく、追悼ムービーと日記が残る設計になっているため。一方で誤登録やテスト登録を消せないと実害が出る。

確認ダイアログの文面は、この矛盾を引き受ける形で設計する必要がある（何が失われるかを明示する）。


### D30 — 追悼の語り口と死因の扱い（旧L-8）

**当初の問いの立て方が誤っていた。**これを「死因に応じて追悼ムービーの語り口を分ける」問題として記録していたが、正しい問いは「**追悼の場で死因を語る必要があるのか**」だった。

D18-a の目標は「泣くこと」だが、**糾弾されて流す涙は悲しみではなく罪悪感**であり、まったく別の感情である。「水をやらなかったから死にました」と言われて泣いた人は、二度とアプリを開かない。一方で「寿命でした」と嘘をつけば、「死という概念は曖昧にせず適切に表現する」「リアリティを追求する」という方針に反する。

人間の葬式では、弔辞で死因を糾弾しない。しかし嘘もつかない。**触れない、という第三の選択肢がある。**

#### 決定

**追悼ムービーでは死因に触れない。語るのは一緒にいた時間だけ。**

ただし**天寿の場合のみ明示する**。そして天寿でない場合はその言葉が出てこない。ユーザーは、**あるはずの言葉がないことで自分で察する**。

| 状況 | 語ること |
|---|---|
| 開花・結実まで到達（天寿） | 「役目を果たした」「種を残したよ」と**明示する** |
| 開花前に終わった | その言葉が出てこない。死因にも触れない |

アプリは一度も責めていないのに、ユーザーは理解する。自分で気づいた理解なので、外から言われるより深く刺さり、しかも角が立たない。

**この手法の制約**: 1株目では成立しない。「天寿ならこう言う」を知らなければ、その不在に気づけないため。察せるのは2株目以降、あるいは他人の追悼を見る機会がある場合（G-03のSNS層）。ただし主目的である「責めない」は1株目から満たされるため、察する効果は上乗せと位置づける。

これは原則2（情報を情報として出さない）の直接の帰結でもある。死因は情報であり、追悼ムービーは情報を提供する場ではない。植物の視点としても自然で、**植物は自分がなぜ死ぬかを分析しない**。知っているのはユーザーと過ごした時間だけである。

#### 3層に分ける

死因の判定自体は必要だが、用途が異なる。

**第1層 — 予防（枯れる前）**

**ここが本当の解決策。**死んでから語り方を工夫するより、死なせないほうがいい。危険域が一定期間続いたら、植物のセリフの切迫感を上げる。

| 段階 | セリフの調子 |
|---|---|
| 通常 | 「のどが渇いたよ」 |
| 心配 | 「ちょっと苦しくなってきた」 |
| 切迫 | 「もう、だめかもしれない」 |
| 消耗 | 言葉が減っていく（D18-a のセリフ減衰へ接続） |

**「あなたのせいだ」とは言わない。**植物は自分の状態を言うだけ。ここで救えれば L-8 の問題そのものが発生しない。実装は D5・D6 の範囲で収まる。

**第2層 — 追悼ムービー（死後）**

死因に触れない。ただしトーンは判定に応じて変える。明示せず、写真の選び方・言葉の温度・音楽の色で。

**第3層 — 振り返り（追悼とは分離）**

**追悼と反省を同じ画面に置かない。**葬式と反省会は別の場所でやる。

ムービーを見終わった後、**別の導線として**「この子に何が起きていたか」を置く。ユーザーが見たいときだけ開く。押しつけない。ここでは事実を正直に書く。

ただし**断定を避ける**。現実には過失かどうか判定できないケースが多い——病気だったかもしれない、買った時点で弱っていたかもしれない、家が暗いのは過失なのか。「水が不足していました」という**事実の記述**にとどめ、「あなたが水をやらなかったから」とは書かない。D7 で確立した「確信度をトーンに反映する」のと同じ原則。

#### 死因判定のロジック

センサーの時系列と診断履歴から機械的に判定する。

| 判定材料 | 使い方 |
|---|---|
| 到達した生育ステージ | 開花に届いたか。**天寿判定の主軸** |
| 枯死前2週間の土壌水分 | 平均・最小値から水不足／過多を判定 |
| 同期間のDLI | 日照不足の判定 |
| 同期間の気温の逸脱 | 高温・低温障害の判定 |
| 観察頻度 | 判定材料には使うが、**ユーザーに見せる文言には絶対に出さない** |

「あなたは20日間会いに来ませんでした」は、このプロダクトが最も言ってはいけない言葉である。


### D31 — 一人称代名詞を使わない

**決定**: 植物のセリフで一人称代名詞（ぼく・わたし・おれ など）を使わない。日本語の主語省略を使う。

**理由**: これは D5 から導かれる。D5で声を当てないと決めたのは、声が人格を固定するからだった。**一人称代名詞もまったく同じ働きをする。**「ぼく」と言った瞬間、その植物は少年になる。「わたし」なら別の何かになる。ユーザーが自分の植物に対して抱いていたイメージが、アプリの選んだ代名詞に上書きされる。

日本語は主語を省略できるため、これは制約にならない。

| 代名詞あり | 代名詞なし |
|---|---|
| ぼく、のどが渇いたよ | のどが渇いたよ |
| わたしは日なたが好き | 日なたが恋しいなあ |
| おれ、もうだめかも | もう、だめかもしれない |

**むしろ省略したほうが自然で、余韻が出る。**キャラクターを作らないという判断（D2）が、文体のレベルまで一貫する。

実装上はシステムプロンプトで禁止する（[../design/diagnosis-prompt.md](../design/diagnosis-prompt.md) §5）。規則が破られやすい箇所なので、検証項目に含める。


### D32 — ゴールの具体化

**決定**: 2026年10月中旬の技術イベントでの展示。

| 項目 | 内容 |
|---|---|
| 目的 | 「将来的にこんなサービスを作りたい」と知ってもらうこと |
| **目的ではないこと** | **買ってもらうこと** |
| 求められる完成度 | **モックでよい。**サービスの価値が伝わればそれで足りる |
| 期限 | 2026年10月中旬（決定時点から約6週間） |

D1で「ポートフォリオ作品・デモ」としていたものが、具体的な日付と場と目的を持った。

#### この決定が変えること

**診断精度は主題ではなくなる。**来場者は数分しか立ち止まらず、その場で診断の正しさを検証する人は一人もいない。彼らが受け取るのは「植物が自分の言葉で話しかけてきた」という体験そのもの。

| 項目 | 重要度の変化 |
|---|---|
| セリフの質・規則遵守 | **上がる。**展示の成否はここに懸かる |
| レイテンシ | **上がる。**来場者は待ってくれない |
| 通信障害への耐性（D28） | **上がる。**会場のネットワークは不安定 |
| 診断の精度 | 下がる。正確さより「それらしさ」で足りる |
| コスト試算 | ほぼ無関係。展示中の数十回だけ |
| 実物を状態別に撮影して精度を検証する必要 | **なくなる** |

**実物がないほど、サンプルセンサーデータの価値は上がる。**実センサーがないなら、モックデータがそのまま展示の本番データになる。

#### 展示という場から来る新しい制約

| 制約 | 影響 |
|---|---|
| 来場者が入れ替わる | 記録が積み上がる体験（日記・追悼）は、その場では育たない。**事前に仕込んだ状態を用意する必要がある** |
| 滞在時間が数分 | 体験を短く区切る。長い導入を置けない |
| 会場のネットワークが不安定 | D28（オフライン時のフォールバック）が必須要件になる |
| 会場の照明が特殊 | 植物検出の精度に影響する。現地で調整が要る |
| 騒がしい | 音に依存しない設計が有利。D5（テキストのみ）が効く |

### D17-a — 対象植物の改訂

**決定**: 実物の植物を使うことは確定。**種類は未定。**

D17では「MVPはミニひまわり1種」としていたが、実物の入手が不確実になった。またD32により、ひまわりを選んだ理由（変化が速い・状態の落差が劇的）の重みも下がった——**センサーがモックである以上、変化は演出で作ることになる**ため。

**対応**: 植物種に依存する知識を**プロファイルとして切り出し、差し替え式にした**。種が決まったらプロファイルを1つ書くだけで済む。決定を10月直前まで遅らせられる。

実装は `server/src/domain/profile.ts`。現時点でミニひまわりとポトスの2種を定義してある。

```
PlantProfile
  ├─ 一年草か（枯死をライフサイクルの正常な完結として扱えるか）
  ├─ GDDの基準温度・開花までの積算温度（null なら開花予測をしない）
  ├─ 適正環境（光・土の湿り・気温・湿度・養分）
  ├─ 生育段階の一覧と説明
  ├─ よくある症状と原因
  ├─ 性格の記述
  └─ 天寿の判定段階（D30）
```

#### 未解決の波及 — 多年草だと D30 が成立しない

D30では**天寿の判定を「開花に到達したか」**に置いた。ひまわりは咲けば役目を果たしているから。

しかし**ポトスのような多年草は室内でまず開花しない**。開花を天寿の基準にできず、`naturalCompletionStage` が null になる。この場合、追悼ムービーで「役目を果たした」と言える条件が存在しなくなり、D30の「天寿のときだけ明示し、不在で察させる」という仕組みが機能しない。

多年草を選ぶ場合、天寿の判定基準を別に定める必要がある（L-10）。

#### デモシナリオへの波及

D25のデモは「水切れ→水やり→回復」をその場で実演する前提だった。実物の植物を使うこと自体は確定しているので**この骨格は維持できる**が、植物種が変われば以下が変わる。

- 水切れから回復までの時間（ひまわりは数時間、多年草はもっと遅い）
- 見た目の変化の大きさ
- プロンプトの植物特化部分

種が決まった時点でD25を見直す。


### D33 — 展示の構成

**決定**: 伝えたい価値を3つに分け、展示物とセクションを対応させる。

| # | 価値 | 展示物 |
|---|---|---|
| 1 | ARで植物から吹き出しが出る | 本物の植物 |
| 2 | 時系列でコミュニケーションが変わる | 時系列の植物パネル数枚 |
| 3 | センサー値を気持ちに翻訳する | 造花＋スポンジ＋水分センサー |

**きっかけ**: 「展示会中では植物の時系列を表現できない。植物は数分・数時間で変化しないから」という指摘。展示物が1つでは、3つの価値を同時に見せられない。

**来場者の体験フロー**: 説明 → 本物の植物にカメラを向ける → 時系列パネルに順に向ける → 造花に水をやる → データをリセットして次の人へ。

**重要な設計判断**:

- **パネルではAI診断を走らせず、その日の記録を再生する。**Claude vision は印刷物を高い確率で見抜き、「印刷された写真のように見える」と観察に書く恐れがある。また記録の汚染と、生育段階の後戻り防止との衝突も起きる。再生ならすべて回避できる
- **造花のセクションでは画像を一切使わない。**入力はセンサー値だけ。造花であることがむしろ「見た目に依存せず数値だけで反応している」証明として働く
- **セクション2は事前定義の一言に留め、中身はセクション4で見せる。**役割を分けないと来場者が「さっき見たのと何が違うのか」と感じる

**リセット**: 毎回データを消して最初から。展示は再現性がすべて。ただしリセットの操作設計が未着手（L-13）。

詳細は [../design/exhibition.md](../design/exhibition.md)。

### D34 — 完全オフライン化

**決定**: 展示当日は Claude API を一切呼ばない。セリフはすべて事前に生成してアプリに埋め込む。

**理由**: AI生成の最大の利点は**多様性**——同じ状態で何度観察しても違う言い回しが出ること。これは数ヶ月使うユーザーには決定的だが、**数分しか触らない来場者には一切効かない。**利点が発揮されない一方で、通信断・レイテンシ・失敗という代償だけは満額で払うことになる。技術イベントの会場はモバイル回線が混雑し、API呼び出しが通らない可能性が現実的にある。

**ただし「AIを使わない」のではない。実行時ではなく制作時に使う。**

セリフを人が全部手で書くと量も質もばらつく。AIに大量に生成させ、人が厳選して埋め込む。これにより、当日は絶対に失敗せず、質は人が管理でき、「AIが生成したセリフです」と正直に言える。技術者に聞かれたら「製品版ではリアルタイム生成、今日は会場の回線を考えて事前生成に切り替えました」と説明でき、**その判断自体が展示の設計として評価される。**

**構成が単純になる**:

| | オンライン前提 | 完全オフライン |
|---|---|---|
| Claude API | 必要 | 不要 |
| プロキシ（`server/`） | 当日も稼働 | 当日は不要（セリフ制作の道具になる） |
| PC | プロキシ＋センサー中継 | センサー中継のみ |
| APIキーの管理 | 必要 | 不要 |
| 通信断のリスク | 残る | **ゼロ** |

**既存資産の位置づけの変化**: `server/` は当日の実行環境ではなく**セリフ制作の道具**になる。診断クライアントはセリフの大量生成に、`rules.ts` は生成したセリフを人が選ぶときの機械的なふるいに使う。センサーのサンプルデータと導出指標はそのまま必要。**無駄になるものはない。**

**D28（オフライン時のフォールバック）は、展示では常時発動している状態になる。**製品版の設計としては維持する。

### D35 — ガジェット連携

**決定**: 水分検知ガジェットはハードに詳しいメンバーが担当する。アプリ側は受け取ったデータの扱いに専念する。

**経路**:

```
ガジェット ──USB(シリアル)──▶ 担当PC ──ローカルHTTP──▶ スマホ
  ネットワークは「スマホのインターネット共有」で作る
```

会場のWi-Fiは使わない（信用できない、かつ準備できない）。スマホのテザリングでローカルネットワークを作り、PCをそこに繋ぐ。必要なのはUSBケーブル1本のみ。

BLEで直接スマホに送れる場合は**PCが不要**になる。その場合もペイロードの形式は同じにする。

**PC→スマホを有線にはできない。**iOSアプリがUSB経由でPCと通信するには MFi 認証などが必要で、6週間には乗らない。

**役割分担が生まれたため、インターフェースの定義が最重要になった。**仕様は [../design/gadget-interface.md](../design/gadget-interface.md) に切り出し、ハード担当に渡せる形にした。要点は以下。

- 最小要件は**土壌水分だけ**。他は任意
- `raw`（生値）と `percent`（正規化値）の**両方**を送る。キャリブレーションはハード側が持ち、生値はアプリ側の逃げ道として残す
- 送信頻度は展示では1秒に1回
- モックのスライダーと実センサーが同じインターフェースを満たすため、**どちらが間に合っても展示は成立する**


### D36 — 展示での永続化（D19との衝突の解消）

**発見された矛盾**: D19は「数ヶ月分の記録が消えたら体験が壊れる」として CloudKit / iCloud での自動保全を決めた。しかし D33 により**展示では毎回データをリセットする**。両立しない。

**決定**: 用途を分けて解く。**展示に CloudKit は使わない。**

| 用途 | 展示での実装 | 製品版の設計 |
|---|---|---|
| 時系列パネルの記録 | アプリバンドル同梱の JSON（読み取り専用） | 端末内 + CloudKit |
| セリフのプール | アプリバンドル同梱の JSON | 同上 |
| セッション中の状態 | **メモリのみ**（来場者ごとにリセット） | SwiftData + CloudKit |
| 撮影画像 | 保存しない | ファイル + CloudKit |

**理由**: 展示で CloudKit を使うと、Apple ID が必要になり、リセットが同期先まで波及し、端末を変えたときに挙動が変わる。展示の要件（毎回同じ状態から始まる再現性）と正面から衝突する。

**D19 は製品版の決定として維持する。**数ヶ月使うユーザーにとって記録の喪失が致命的であることは変わらない。今回の実装スコープから外すだけ。

これは D34（完全オフライン化）と同じ構図で、**製品としての設計と、展示として作るものを分ける**という整理にあたる。


### D39 — 個体の指定は人が選ぶ（D8の改訂）

**決定**: 画像特徴による個体同定（D8）をやめる。カメラ画面の左端に弧状のUIを置き、**観察中の株を人が選ぶ。**

**理由**: 同じ品種の株を画像で区別するのは精度が出にくい。そして**間違えたときの代償が大きい。**記録が別の株に混ざると、日記もギャラリーも成長の履歴も汚染され、しかもユーザーは気づきにくい。

**人が選ぶほうが確実で、実装も軽い。**D8は「登録の摩擦を減らす」ために画像同定を選んだが、弧状UIなら摩擦はほぼ同じで、確実性が上がる。

**ガジェットが判定できる場合は自動で選ぶ。**センサーの `gadgetId` と株が紐づいていれば、値が届いた時点でその株に切り替わる。

**自動選択でもUIを一度開く。**黙って切り替わるとユーザーが気づけない。開いて、選択されたことを見せてから、触られなければ自動で閉じる。

**UIの形**: iPhone のカメラでズームを長押ししたときの円弧に倣う。

| 状態 | 見た目 |
|---|---|
| 通常 | 左端に小さな半円。選択中の株の名前を示す |
| 展開 | 弧に沿って株の名前が並ぶ。ドラッグで選ぶ |
| 数秒後 | 自動で小さくなる |

**株が1つでも常に出す。**選ぶ必要がなくても、**今どの子を見ているのかが常に見えること自体に意味がある**——自分がつけた名前が画面にあることが、関係を実感させる（D9）。

**F-06（植物の登録と個体同定）はこれで満たす。**


### D38 — 画面の向きは縦持ち固定

**決定**: 縦持ちを基本とし、**上下反転のみ許可する。横向きには対応しない。**

**経緯**: D3 の議論で「カメラを反転させる」という要件が挙がり、その意味が長く未確定だった（C-1）。**①端末を上下逆さまにする**ことだと判明した。

**この確認によって実装のバグが1つ露見した。**Vision へ渡す画像の向きを `.right`（縦持ち）で決め打ちしており、端末を上下逆さまにすると検出が働かない状態だった。ARKit が渡す画像はカメラの物理的な向きのままなので、画面の向きに合わせて回転の指定を変える必要がある。画面の向きから導出するよう修正した。

**横向きを対応しない理由**: 吹き出しのレイアウトが縦持ち前提であり、横向きにすると文字の折り返しと位置が崩れる。展示では縦持ちで使うため、対応する必要がない。


### D37 — 署名アカウントは無料版

**決定**: Apple Developer Program（年99ドル）には加入せず、無料の Apple ID で署名する。

**帰結**: **アプリは7日で失効する。**インストールから7日経つと起動しなくなる。回避する方法はない（無料アカウントのプロビジョニングプロファイルの有効期間が7日のため）。

| 対応 | 内容 |
|---|---|
| **展示の前日または当日朝に必ず入れ直す** | 忘れると会場でアプリが起動しない |
| 予備端末も同様 | iPhone 11 を予備に使うなら、そちらも同じ日に入れ直す |
| 手順を書き残す | 当日慌てないよう、誰でも実行できる形にしておく |

**これは展示当日の最大の事故要因になりうる。**通信断（D28で対策済み）やセンサー故障（モックで代替可能）と違い、**アプリが起動しないと何も見せられない。**

その他の制約:

| 項目 | 無料版での制約 |
|---|---|
| 配布 | TestFlight が使えない。ケーブル接続での直接インストールのみ |
| App ID | 同時に登録できる数に上限がある |
| 有効期間 | **7日** |

展示は自分の端末で見せるため、配布ができないことは問題にならない。

### D40 — 2株目以降を迎える（D9の拡張）

**決定**: シャッターに種類を持たせ、**左右のスライドで「撮る」と「迎える」を切り替える。**「迎える」で撮った1枚をその場で止め、見つけた植物を枠で囲んで示す。「話しかける」を押すと通常のカメラ画面に戻り、その子が「はじめまして。名前をつけてくれる？」と話し始める。

**理由**: D9 の登録は「**まだ誰もいないとき**」にしか走らなかった。株を選ぶ弧（D39）、株ごとのギャラリー、株の削除と、**複数株を前提にしたUIを作っておきながら、2株目を作る手段が無かった。**

**専用の登録画面は作らない**という D9 の方針は維持する。増やしたのは入口だけで、名前をつける体験そのものは変えていない。

| 入口 | 契機 | 対象 |
|---|---|---|
| D9（自動） | 未登録の状態でカメラを向ける | 1株目 |
| **D40（迎える）** | シャッターを「迎える」にして撮る | **2株目以降** |

**なぜ一段挟むのか**: 1株目は「まだ誰もいない」ので、カメラが見つけた相手＝迎える相手で迷いがない。2株目以降は**すでに知っている子が周りにいる。**向けただけで勝手に話しかけてくる作りのままだと、どの子を迎えたのかが本人にも分からない。**迎える相手を自分で確かめてから決める**ための一段として、静止画と枠を挟む。

**確かめた相手をそのまま引き継ぐ。**「話しかける」のあとに映像から検出し直すと、同じ植物でも見つかるまで間が空き、押した手応えが消える。確認で決まった枠の位置にその場でアンカーを打つ。

**確認中は検出を止める。**止めないと、確かめている裏で映像の側が別の相手を決めてしまう。止めるのは検出だけで、ARのセッションは回したままにする（止めると復帰に時間がかかり、戻ったときに画面が固まって見える）。

**枠が出なくても断らない。**見つけられなかったときは「うまく見つけられなかったみたい」と出し、それでも「話しかける」は押せる。見つからないことをエラーとして扱わない（D24・原則3）。

**種類は今後も増える前提。**シャッターの並びは数に依らず組めるようにしてあり、選択中が中央に大きく、残りは横に小さく並ぶ。

### D40-a — 登録の入口はシャッターだけにする（D9の改訂）

**決定**: D9 の「未登録ならカメラを向けただけで登録が始まる」をやめる。**新しい株はシャッターの「迎える」からしか増えない。**

**株が未登録、またはどれも選ばれていないあいだは、植物を探さない。**見当たらない扱いにして「見当たらないなぁ」を出す。

**理由**: D40 で「迎える」を足した結果、**登録の入口が2つになった。**しかも自動のほうは、迎えるつもりのない場面でも走る。近くの別の鉢、隣の人の植物、写真に写った葉——向けただけで「はじめまして」と言い出し、名前の入力欄が出る。**迎える相手を自分で確かめてから決める**という D40 の趣旨を、自動の入口が裏から崩していた。

| | 変更前 | 変更後 |
|---|---|---|
| 1株目 | 向けると自動で「はじめまして」 | **「迎える」で撮る** |
| 2株目以降 | 「迎える」で撮る | 同じ |
| 未選択のとき | 見つけたら勝手に話し始める | **見当たらない** |

**「誰を見ているか」が決まっていないなら話しかけない。**選ばれている株がいないのに吹き出しが出ると、そのセリフが誰のものなのか決まらない。観察の記録も積む先が無い（`selectedPlantId` が nil のため捨てられていた）。**話しかけてくる以上、相手は決まっているべき。**

**D9 の中身は変えていない。**専用の登録画面を作らず、名前ひとつだけを入力し、種類はAIが推定する——この形はそのまま。変えたのは**いつ始まるか**だけで、始まったあとの体験は同じ。

**パネルは選択の有無に関わらず動く。**時系列パネル（D33）は画像アンカーで検出しており、この判定を通らない。株を1つも持たない来場者でも、展示の記録は見られる。

**展示への影響**: 来場者は「見当たらないなぁ」から始まる。ここから先へ進む道は2つ——弧（D39）で仕込みの株を選んで観察するか、「迎える」で自分の株を迎えるか。**どちらも自分で選ぶ操作になった。**説明員の案内が要る点は変わらない。

### D40-b — 迎える最中は、ほかを動かさない

**決定**: 「迎える」に切り替えているあいだ、株を選ぶ弧（D39）は**小さくなり、誰も指さない状態になる。**名前を入れているあいだは、**動くのは入力欄だけ**にする。

**弧が退く理由**: これから新しい株を迎えようとしているのに、**いま選ばれている株の名前が画面に出ていると相手を取り違える。**「ひまり」と出たまま別の鉢を撮ることになる。半径を落として名前を消し、触れる先も閉じる——開いて選べてしまうと、選んだのに名前が出ない状態になるため。

**持ち上げない理由**: キーボードは画面ごと押し上げる。名前を入れているだけなのに、シャッターもタブバーも**画面の中ほどまで上がってくる。**特に吹き出しは位置をARの投影で決めているため、座標系がずれると**植物から離れたところに出る。**

| 要素 | 扱い | 理由 |
|---|---|---|
| 吹き出し | 動かさない | ずれると植物から離れる |
| シャッター | 出さない | 撮る場面ではない |
| 弧・下部の案内 | 動かさない | — |
| タブバー | **退ける** | 留めてもキーボードの下。見え方は変わらない |
| 名前の入力欄 | 上げる | 隠れては入力できない |

**タブバーだけ扱いが違う。**`TabView` のものなので、カメラ画面側で `.ignoresSafeArea(.keyboard)` を掛けても止められない。留められない以上、隠す。**留めた場合と見え方は変わらない**——どのみちキーボードの下に隠れる位置にある。

### D41 — 株の選び方をダイヤルにする（D39の改訂）

**決定**: 弧の選び方を**ダイヤル**に変える。**指定の場所（弧の頂点）は動かず、名前のほうが回ってくる。**指を離した時点で頂点にあるものが決まる。あわせて、名前を**円の中心に向けて寝かせ**、一覧に**「未設定」**を加え、**選択中の株のアイコンを画面の上中央に常時出す。**

| | 変更前（D39） | **D41** |
|---|---|---|
| 動くもの | 指。名前は止まっている | **名前。指定の場所が止まっている** |
| 選ばれ方 | 指にいちばん近い名前 | **指定の場所にある名前** |
| 決まる契機 | 通過した瞬間 | **指を離したとき** |
| 文字の向き | 全部水平 | **円の中心に向けて寝かせる** |
| 選択肢 | 株のみ | **先頭に「未設定」** |
| 選択中の表示 | 弧を閉じたときだけ | **上中央のアイコンと名前で常時** |

**離すまで決めない理由**: 通過した瞬間に確定する作りだと、**目的の名前まで回す途中で、通り過ぎたものが次々に選ばれる。**選ぶ行為が「決める」ではなく「通る」になっていた。通過は色と触覚で仮に知らせ、**離すという明確な動作で決める。**見比べてから決められる。

**文字を寝かせる理由**: 弧に沿って並んでいるのに文字だけ水平だと、**目盛りではなく、ただ散らばった文字に見える。**中心に向けて寝かせると弧の一部になる。副産物として、**決まっているもの（＝頂点にあるもの）は常に水平**になり、いちばん読みやすい位置に来る。

**「未設定」を置く理由**: 観察をやめる手段が無かった。D40-a で「株が選ばれていないと見当たらない扱い」になったので、**未設定に戻すこと自体が操作として意味を持つ。**弧から選べるのが筋。

**アイコンを常時出す理由**: **弧は触らないと何も語らない。**上中央にアイコンと名前を置けば、いま誰を見ているかが常に分かる。小さな半円の中に押し込まれた名前より読みやすく、置き場所も1つに定まる。

**寸法**: 名前1つあたり 16°、指の移動 44pt で1つ進む。頂点から 24° まではっきり見せ、48° で消える。**止まっているとき、ちょうど5つ見える。**端で止まり、ぐるりとは回らない。

弧の中心は画面の外（x = −73）にあり、名前は半径 147 の上に乗る。**角度が開くほど左へ寄る**ため、間隔は「2つ外側（32°）でも画面に残る」ところから決めた。消える角度は「6つ目がちょうど消える位置」（16° × 3）に置く——中途半端に残ると、画面の縁で切れた文字が見える。

**閉じているあいだ、弧は名前を出さない。**名前の置き場所は上中央のアイコンの下ひとつにする。両方に出すと二重になり、弧のほうは小さな半円に押し込まれて読みにくい。**回している最中、上は決まっているものを、弧は考えている途中のものを示す。**

### D41-a — 選択の印を、下のタブバーの動きに揃える

**決定**: 頂点の印を、**iOS のタブバーが選択を切り替えるときと同じ見え方**にする。

**タブバーで起きていること**（同じタブ構成の確認用アプリを録画し、コマ送りで確認した）:

| # | 起きること |
|---|---|
| 1 | 印は**分裂しない。1つの塊のまま伸びて移る** |
| 2 | 伸びている間は**両端を包む長円**になり、一時的に2項目にまたがる |
| 3 | **色はフェードではない。塊の縁を境に切り替わる**——通過した側から変わる |
| 4 | 所要はおよそ 0.4秒 |

**3 が要点。**アイコンが左半分だけ色を変えているコマがある。膜が通り過ぎた場所だけ色が変わる、という見え方をしている。

**弧では動くものが逆になる。**

| | タブバー | 弧（D41） |
|---|---|---|
| 動くもの | **印** | **名前** |
| 止まっているもの | 項目 | 印（頂点） |

そのまま写せないので、こう置き換える。

**印は頂点に留まり、回している間だけ縦に伸びる。**頂点にある名前が頂点から離れているぶんだけ伸び、**半分まで来たところで最も長くなって、出ていく名前と入ってくる名前の両方をまたぐ。**止まると元に戻る。塊の幅は包んでいる名前の実寸に合わせる——短い名前に長い塊が付くと、何を指しているのか分からなくなる。

**色は塊の形で切り抜いて出し分ける。**名前を2枚重ね、下地（白）は塊の形で抜き、アクセント色は塊の形だけ出す。**塊が半分かかった名前は、半分だけ色が変わる。**下地を抜かずに色を重ねると、白が透けて色が濁る。

**塊を着色しない。**タブバーの選択中の塊も無彩色で、色が付いているのは中身だけ。塊を青くすると、同じ色の名前が読めなくなる。

**材料の割り当ては D41-b で改めた。**当初はこの塊（囲い枠）に `glassEffect` を付けたが、**手本と逆だった。**

**未完了（2026-08-31 時点で保留、D41-b で一部が解消）**

| # | 残件 | 分かっていること |
|---|---|---|
| 1 | 実機でガラスに見えない | **D41-b で材料を全体枠へ移した。**囲い枠はすでにガラスの上に乗っており、重ねてもぼかす先が無かった |
| 2 | 融合・変形が使えていない | `GlassEffectContainer` に入れると名前がガラスの下に隠れる。器に入れずに融合させる方法が未調査 |
| 3 | AR の映像を取り込むか未確認 | `UIVisualEffectView` と Material は取り込めなかった（`7cbf8dd`）。Liquid Glass は別実装なので同じとは限らない。**取り込めなくても明暗が付くよう、D41-b で色を掛けてある** |

伸び・色のマスク・名前の省略・アイコンの出入りは入っており、動作としては成立している。

**名前は弧の内側に収める。**収まらなければ「…」で切る。名前は半径に沿って寝ているので、使える範囲は「外側＝弧の縁、内側＝画面の左端」で決まり、**角度が開くほど狭くなる。**端の名前ほど短くなるのは、弧の形からの帰結。**印も、止まっているあいだは縁を越えない**（回している最中は伸びるので越えてよい）。

**頂点に来ている株のアイコンを、円の外側の決まった場所に出す。**名前だけだと、回している最中に頂点がどこなのかを色でしか追えない。**位置を固定するのが要点**——名前に添えるとその長さで位置が動き、印としての意味が薄れる。場所が動かないからこそ、名前のほうが回っていることが分かる。弧の縁から 32pt 外に置き、塗りから出して映像の上に独立させる。「未設定」にはアイコンが無いので、そのときは何も出ない。

**閉じるまでを 0.2 → 0.4秒に伸ばした。**離してから決まる方式では、即座に畳むと何が選ばれたのかを見る間がない。

### D41-b — サイドバーの部品名と材料を、タブバーに揃える

**決定**: サイドバー（左端の弧）の部品に**タブバーと対応する名前**を与え、**材料の割り当ても手本と同じにする。**

**まず名前を決めた。**UI の改善が難航していた原因の一つが**名前だった。**「印」「塊」「弧」「バー」が混ざり、どこを直しているのかが会話とコードで食い違っていた。

| 呼び方 | タブバー（手本） | サイドバー | コード |
|---|---|---|---|
| **全体枠** | バーそのもの | **通常円** / **拡大円** | `ArcSegment` / `arcVisual` |
| **囲い枠** | 選択中を囲う塊 | 名前を囲う塊 | `nameFrame*` |
| **文字** | 項目名＋アイコン | 名前 | `names` / `nameLabel` |

- **通常円** … 触っていないときの小さな半円（`restingRadius`）
- **拡大円** … 触っているときの大きな弧（`expandedRadius`）

**名前を決めたら、間違いが目で見えた。**

| | 変更前 | **変更後** |
|---|---|---|
| 全体枠（通常円・拡大円） | 明るさから作ったべた塗り | **Liquid Glass**（タブバー本体と同じ） |
| 囲い枠 | **Liquid Glass** | **べた塗り**（タブバーの選択中と同じ） |

**材料が逆に付いていた。**タブバーでガラスなのは全体枠のほうで、選択中を示しているのは無彩色の塗りひとつ。**囲い枠はすでに全体枠の上に乗っているので、そこにガラスを重ねてもぼかす先が無い。**「実機でガラスらしく見えない」（D41-a の残件1）はこれが理由と見ている。

**地は白か黒の2状態にする。途中の灰色は作らない。**タブバーは周りの明るさで白い地と黒い地を切り替えるだけで、あいだを取らない。**サイドバーだけが連続で変わると、並んだときに別の作りに見える。**

| 状態 | 地 | 名前（選択外） | 囲い枠 |
|---|---|---|---|
| 暗い | 白 0.06 | 白 0.72 | 白 0.20 |
| 明るい | 白 0.92 | **黒 0.66** | 白 0.92 |

**名前の色も一緒に返す。**地が白へ回れば文字は黒へ回る。連続だったころは白い文字のまま地だけが明るくなり、明るい場所で読めなくなっていた。**2状態にして初めて見えた不具合。**

**切り替わる明るさは、入るときと出るときでずらす**（0.58 で明るいへ、0.42 で暗いへ）。境目がひとつだと、そこで明るさが揺れるたびに白黒が往復する。

**ガラスには色を掛けて使う。**Liquid Glass が AR の映像を取り込めるかは未確認（D41-a の残件3）。取り込めていないと無着色では明るくても暗くても同じ見え方になるので、**実測した明るさから作った色を掛けておけば、どちらに転んでもタブバーと同じ明暗に付いてくる。**

**縁の光沢は弱める。消しはしない。**タブバーの全体枠にも同じ光沢があり、無くすと材料が違って見える。ただし**弧は輪郭の片側しか見えないぶん、同じ光沢でも一本の白線として強く出る**——タブバーでは枠を一周するので、線ではなく丸みとして馴染む。

強さを直す設定は材料側に無いので、**削る幅だけ大きく描いて元の大きさで切る**（暗い地 1.5pt / 明るい地 0.5pt）。いちばん明るいところが外側に落ち、淡いところだけ残る。**暗い地を多く削る**のは、白い光沢が黒地でいちばん際立つため。縁取りで隠す手は、地が半透明なのでそこだけ濃くなり、白線が濃い線に変わるだけ。

**iOS 26 より前ではべた塗りに落とす。**ガラスが無い環境では、色だけを塗る。

### D43 — マイプラント詳細を3つに分け、「育成」だけ数値を解禁する

**決定**: マイプラントの詳細を**記録・育成・ギャラリー**の3つに分ける。**育成に限り、土壌水分などの実測値を数値とグラフでそのまま出す。**カメラ画面を含むほかの場所は、これまでどおり原則2に従う。

| セクション | 役割 | 数値 |
|---|---|---|
| **記録**（旧「情報」） | 節目の記録。出会った日、これまでの歩み、観察の履歴 | 出さない |
| **育成**（新設） | 水分量のグラフなど、リアルタイムの育成サポート | **出す** |
| ギャラリー | 思い出の写真 | 出さない |

**理由**: 原則2は、**植物が話しかけてくる場面**を農業管理アプリにしないための原則である。カメラ画面の体験は「植物の言葉による育成」であり、そこは変えない。

一方で育成は、**育てている人が土の状態を自分から確かめに来る場所**で、植物が話す場面ではない。この場で「のどが渇いたよ」だけを返されても、次にいつ水をやればよいかは判断できない。**実測値そのものが育成のサポートになる。**

**境界は「植物が話す場所」と「人が確かめに来る場所」で引く。**入口を分けておけば、数値がカメラ画面や記録に漏れ出すことはない。

**「情報」を「記録」に改めた。**「情報」は中身を何も言っていない。育成が加わり、こちらは節目を振り返る場所になったので、それを名前にした。中にあった節「記録」は、タブ名と重なるため「観察の履歴」に改めた。

**実装上の制約**:

- 土壌水分の推移は**観察中の株にだけ積む。**センサーは1株1ガジェットで、値がどの株のものかは選択中の株で決まる（D39）
- 推移は**セッション内だけ持つ**（D36）。リセットで消える
- 実測されているのはいまのところ土壌水分だけ。**光・気温などを0で埋めて `SensorReading` に詰めない。**DLIやVPDに誤って使われると、もっともらしい誤った値が出る

**→ 項目と持ち方は D44 で改めた。**

### D44 — 育成のグラフ（項目・持ち方・時間幅）

**決定**: 育成に10項目のグラフを出す。**項目は「定義」と「値の列」に分け、項目を足すときに画面を書き換えずに済む構造にする。**画面の下端に時間幅のバーを置き、全部のグラフを一斉に切り替える。左右に送って過去も見られる。仕込みの株ひまりには、一生分（0〜78日目）の仮データを持たせる。

#### 項目

| 項目 | 単位 | 刻み | 出どころ | 保存 | 適正範囲（ミニひまわり） |
|---|---|---|---|---|---|
| 土壌水分 | % | 10分 | センサー | する | 25〜60 |
| 気温 | ℃ | 10分 | センサー | する | 20〜30 |
| 湿度 | % | 10分 | センサー | する | 40〜70 |
| 光量 | lux | 10分 | センサー | する | 持たない（光の良し悪しはDLIで判断するため） |
| CO2 | ppm | 10分 | センサー | する | 持たない |
| EC | mS/cm | 10分 | センサー | する | 1.0〜2.0 |
| 土の温度 | ℃ | 10分 | センサー | する | 持たない |
| pH | — | 10分 | センサー | する | 6.0〜7.5 |
| 草丈 | cm | 1日 | 画像 | する | 持たない |
| 日長 | 時間 | 1日 | 計算（光量から） | **しない**（原則1） | 持たない |

**ハードウェアの仕様上の制約は考えない。**いまのガジェットに無い項目（CO2・土の温度・pH）も持つ。

**葉の数は入れない。**画像から数えると±1〜2枚の推定になる。研究でも、真上から撮った葉の放射状に広がる植物を照明固定で撮って、ぴったり一致は4割程度。ひまわりは茎に葉が互い違いに付くので重なりやすく、つぼみ以降はさらに崩れる。**あとから足せる構造にしておく。**

**草丈は観察ではなく、グラフ用の値の列に入れる。**観察に入れると毎日1件ずつ増え、記録の「観察の履歴」にセリフの無い日付が70行ほど並ぶ。グラフの項目を同じ形にそろえておくほうが、項目を足すときにも迷わない。製品版でAIが草丈を読んだときは、観察と値の列の両方に書く。

#### 持ち方 — 定義と値の列

| 定義に持つもの | 例（土壌水分） |
|---|---|
| ID | `soilMoisture` |
| 表示名・単位 | 土壌水分・% |
| 刻み | 600秒 |
| 出どころ | センサー／画像／計算 |
| 描き方・小数の桁・適正範囲を外れたときの言い方 | 折れ線・0桁・乾き気味／湿り気味 |

適正範囲は定義ではなく**植物のプロファイル**から引く（種によって違うため）。無い項目もある。長い幅でまとめるときは、**どの項目も平均を取る**ので定義には持たせない。

```json
{
  "series": {
    "soilMoisture": { "interval": 600,   "values": [52.0, 51.9, null, 51.8] },
    "heightCm":     { "interval": 86400, "values": [null, null, 0.8, 1.3] }
  }
}
```

| 規則 | 理由 |
|---|---|
| **項目を足すときは、定義に1行・データに1列を足すだけ** | 画面は定義を読んで並べる。画面のコードを触らない |
| **測れなかった点は `null`。0で埋めない** | D43 と同じ。0は「測った結果が0」と区別できない |
| **定義に無い列は読み飛ばす** | データを先に足してもアプリが壊れない |
| 計算で出す項目は、元の列から作る | 日長は保存しない（原則1） |
| 日長＝光量が 1,000 lux 以上だった時間の合計 | 室内の照明（300〜500 lux）を日中に数えないため。**閾値は仮** |

#### 時間の刻み

| 株 | 刻み |
|---|---|
| ひまり（仕込み） | **出会った日の0時から10分ごと。**出会った日は起動日から逆算で決まる（L-12）ため、データには日付を書かず、何番目の点かだけを持つ |
| 登録した株 | **届いた値を10分ごとに平均して1点にする。**時計の区切り（:00・:10…）にそろえる。選ばれていないあいだは `null` で、線が途切れる |

**10分より細かい変化は、グラフではなくカメラ画面の会話で伝える。**登録したての株は、展示の数分では点が1〜2個しか出ない。それでよい。

#### 時間幅

| 規則 | 内容 |
|---|---|
| 選べる幅 | 全体・1年・1ヶ月・1週間・1日・1時間。既定は全体 |
| 切り替え | **1つのバーで全グラフが一斉に変わる** |
| 送り | **左右に送って過去を見られる。全グラフが一緒に動く。**開いたときの右端は最新の点 |
| データより長い幅 | **全体と同じ表示にする。**軸を1年に広げて線を右に寄せることはしない |
| まとめ方 | **実際に表示する長さで決める。**1日以下は10分そのまま、1週間以下は1時間の平均、それより長ければ1日の平均と最小〜最大の幅 |
| 1日1点の項目 | 表示する幅で点が2つ未満なら、グラフを描かず値だけを出す |

**まとめ方をボタンの名前ではなく表示する長さで決める**のは、データより長い幅を全体と同じ表示にするため。登録して30分の株で「1ヶ月」を押したとき、1日平均にすると点が1つになる。

#### 実装で決めたこと

| 規則 | 理由 |
|---|---|
| **グラフには、見えている幅の前後1つ分の点と目盛りだけを渡す。**送るたびに作り直す | 全期間を渡すと、1時間の幅では78日分（約1,900画面ぶん）を描くことになり、開くのに20秒以上かかった。切り出すと約1.5秒 |
| **縦軸は全期間の値から決め、送っても変えない** | 見えている点だけで決めると、送るたびに縦軸が伸び縮みして線の高さを比べられない |
| 横軸は 1日以内なら「14:00」、それより長ければ「8/31」 | 日記と同じ日付の書き方 |
| **幅を変えるときは、位置も同じ更新で変え、グラフを作り直す** | 幅を変えたあとで位置を送ると、スクロールできない「全体」から切り替えたときに、グラフが渡した位置を受け取らずデータの先頭に居座り、空に見えた |
| 送る操作は Swift Charts のスクロールを使う | 横になぞるとグラフが送られてページは切り替わらず、縦になぞると画面がスクロールする。自前のドラッグだと、ページ送りや縦スクロールと取り合いになる |

#### ひまりの仮データの筋書き

時系列パネル（timeline.json）と仕込みの日記の本文に合わせる。**生成スクリプト（`npm run gen:growth`）で作り、乱数の種を固定して、何度作り直しても同じ値にする。**

| 日 | 出来事 | データ |
|---|---|---|
| 0〜17 | 部屋の奥 | 光量は昼でも 3,000〜5,000 lux |
| 18 | 窓際に移す | **光量が 20,000〜40,000 lux に跳ね上がる** |
| 21〜23 | 暑い日が続き水切れ | 気温が高め。土壌水分が15%を下回る |
| 23夜 | あわてて水やり | 土壌水分が急に上がる。土の温度が下がる |
| 28〜 | 3日に1回の水やり | 土壌水分がのこぎり状に上下する |
| 45 | 開花 | 草丈の伸びが止まる（約50cm）。**積算温度が開花の目安（958）に届くよう気温を合わせる** |
| 70〜 | 水をやっても戻らない | **吸い上げが落ち、水やり後の土が乾きにくくなる** |
| 78 | 茎が倒れる | 草丈が下がる。データはこの日の終わりまで |

**水やりは1刻み（10分）で染みたことにする。**2刻みに分けると、既存の水やり検出（`Metrics.detectWateringEvents`）が1回の水やりを2回と数える。検出は TypeScript 版と共通のロジックなので、データの側を合わせた。

**筋書きとの一致はテストで守る。**`MetricSeriesTests` が、水切れの日に15%を下回って水やりが1回検出されること、開花のパネルの日に積算温度が958に届くことを確かめる。パネルの日付を動かしたら、データを作り直さないとテストが落ちる。

全期間を通じて、気温・湿度・CO2・土の温度は1日の周期で上下する。EC は7〜10日おきの肥料で上がり、pH はほぼ横ばいで肥料の後にわずかに下がる。

#### D43 からの変更

| D43 | D44 |
|---|---|
| 土壌水分だけを扱う | 10項目 |
| `MoistureSample`（水分だけの型） | 値の列に置き換える |
| 1秒ごとに積む・1株500点まで | 10分ごとにまとめる。上限は設けない |
| セッション内だけ持つ（D36） | 登録した株はそのまま。ひまりの仮データはアプリに同梱する |


### D45 — マイプラント詳細の操作部品を浮かせる

**決定**: マイプラント詳細（記録・育成・ギャラリー）では、**操作部品の後ろに帯を敷かない。**日記と同じく中身を画面の上端から下端まで流し、操作部品はその上に浮かせる。

| 部品 | 変更前 | 変更後 |
|---|---|---|
| タブバー | 中身がその手前でまっすぐ切れ、後ろが無地の帯に見えた | 中身の上に浮く |
| 上の「記録・育成・ギャラリー」 | 中身がその下でまっすぐ切れた | **タブバーと同じガラス**で浮かせ、中身が下に潜る |
| 育成の時間幅のバー | 画面幅いっぱいの半透明の帯に乗っていた | **タブバーと同じガラス**で浮かせる |

**理由**: 日記とマイプラントで、同じタブバーの見え方が違っていた。

**帯を外すだけにせず、ガラスを付けた。**帯が無いと、下を流れるグラフや文字が透けて、切り替えの文字が読みにくくなる。タブバーと同じ素材にそろえるので、並んだときに別の作りに見えない。iOS 26 より前ではガラスが無いので、半透明の素材に落とす。

**上端は自前でぼかす。**日記では、上に潜った中身をナビゲーションバーがぼかして消している。マイプラント詳細の3画面はページ形式の `TabView` の中にあり、**このぼかしが効かない**。そのままだと、潜った中身が題名や時計の文字と重なった。iOS 26 の `safeAreaBar` を各ページに置いても効かなかったため、下に向かって透明になるぼかしを重ねている。帯に見えないよう、硬い境目は作らない。

**ページ形式の `TabView` は安全領域の内側しか描かない。**これが「帯」の正体だった。`TabView` ごと画面の端まで広げ、ナビゲーションバー・切り替え・タブバーのぶんの余白は各ページに足し直している。

**広げたページは、画面の上端から少し下にずれて置かれる**（iPhone 17 で 16.33pt）。ずれを足さないと、時間幅のバーがタブバーに重なる。上下の余白の差（116pt と 83pt）の半分とほぼ一致するので、`TabView` がページの枠を安全領域の高さで作り、広げた中身をその上下中央に置いていると見ている。**式は決め打ちせず、ページの位置を測って打ち消す。**

**ずれは3ページのどれでも測る**（2026-09-21）。記録だけで測っていたころは、育成やギャラリーから開くと記録が描かれず、ずれが 0 のまま時間幅のバーがタブバーの下に潜った。

| 試したこと | 結果 |
|---|---|
| 広げたうえで余白を足す（最初の実装） | 中身が 16pt 下にずれ、時間幅のバーがタブバーに重なった |
| `ZStack` をやめる | 変わらなかった（`ZStack` が原因ではなかった） |
| 広げずに `scrollClipDisabled` で枠の外まで描かせる | 位置は合ったが、`TabView` の切り取りは外れず帯が戻った |
| 広げたうえで、ずれを測って打ち消す | **位置が合い、中身も端まで流れる** |


### D56 — タブの一番上の画面の見出しを、細い見出しに揃える

**決定**: マイプラント・日記・ルーム・プロフィールの一番上の画面は、**どれも細い見出し**（`.navigationBarTitleDisplayMode(.inline)`）にする。大見出しは使わない。

**日記は大見出しにできなかった**: 大見出しにすると、上へ送ったときにカクつく。切り分けとして**マスを無地の色に置き換えた版**を触ってもらい、それでもカクついた。原因はマスの中身（写真・影付きの文字）ではなく、**大見出しと並べ方（`ScrollView` ＋ `LazyVGrid`）の組み合わせ**にある。ほかの3画面は `List` で、大見出しでもカクつかない。

**ほかを日記に揃えた理由**: 日記だけ細い見出しだと、タブを行き来したときに見出しの形が変わって見える。3列グリッドを `List` で組み直して日記を大見出しに戻す手もあったが、揃えるほうを選んだ（ユーザーの判断）。

**確かめられなかったこと**: シミュレータで指のドラッグを流して録画し、コマごとの動きを測ったが、**カクつきを数値では捉えられなかった。**シミュレータの録画自体がコマを落とすため、プロフィール（カクつかない）でも日記と同じくらいの抜けが出た。判定はユーザーの目視による。

### D45-a — 詳細の上端のぼかしを、日記・一覧の色に揃える

**決定**: マイプラント詳細（記録・育成・ギャラリー）の上端（`scrollEdgeFade`）を次の形にする。**値はユーザーが画面で1つずつ確かめて決めた。**

| 項目 | 値 |
|---|---|
| 白の幕 | **50%**（ダークでは黒 50%）。中身がうっすら透ける |
| ぼかし | **UIKit の `UIBlurEffect(.extraLight)`**（ダークは `.dark`）を **90%** の濃さで |
| グラデーション | 画面の上端〜切り替えの下端の 64pt 上（iPhone 17 Pro で 0〜91pt）は一定。そこから **88pt** かけて透明へ（〜179pt）。両端をゆるめる（smoothstep） |
| 中身 | **画面の上端まで描く。**ページは上端から 16pt 下に置かれるので、ずれのぶん上へ伸ばす |

**SwiftUI の Material は使わない。**ぼかしに灰色の色味が最初から入っていて、白いカードの上で灰色に濁る（白 255 のカードが 236 になった）。SwiftUI からはこの色味を外せない。UIKit の `.extraLight` は白寄りの色味で、濁らない。消え方の形は UIKit 側（`UIVisualEffectView.mask`）で切り抜く。外から SwiftUI の `.mask` を掛けると、ぼかしが効かなくなることがあるため。

`ultraThinMaterial` が一番弱い段階なので、ぼかしは**層ごと薄めて**弱めている（90%）。ぼかしの半径そのものは変えていない。

**中身を上端まで伸ばした理由**: 幕を半透明にすると、上端の 16pt だけ中身が無く、線で切れたように見えた（D45 のずれ）。ずれはページの枠で測る。伸ばした中身で測ると 0 になり、伸ばす量も 0 に戻ってしまう。

**システムのぼかしは使えない（再確認）**: 中身（`List` / `ScrollView`）に、画面の上端から切り替えの下までの高さの `safeAreaBar` を直接付け、`scrollEdgeEffectStyle(.soft, for: .top)` も明示した。どちらも出なかった。**SwiftUI の部品では**、ページ形式の `TabView` の中で効かせる方法が見つからない。UIKit の `UIScrollEdgeElementContainerInteraction` で自前の上端をバーとして登録する道は残っているが、SwiftUI が内部で作るスクロールをつかむ必要があり、OS の更新で壊れうるので見送った。

**経緯**:

| 回 | 形 | 結果 |
|---|---|---|
| D45 | Material 1枚を下に向かって透明に | 灰色がかったすりガラスの帯。潜った文字が上端まで読めた |
| 1 | 日記を画素で測って寄せた（ぼかし＋地の色の幕。ライト 85%・ダーク 60%） | 地の色が薄い灰色なので灰色に見えた |
| 2 | 白・不透明・88pt・Material なし | 「うまくできていない」。半透明の読み違いがあった |
| 3 | 1指示ずつ確かめるループ: 半透明 → 上端まで描く → ぼかし → 白 100%/0% を試す → ぼかし 50/75/90% → 白 50% → UIKit のぼかし | **確定** |

### D46 — ギャラリーの写真をタップした先に、1枚と前後を並べる

**決定**: マイプラントのギャラリー（3列グリッド）で写真をタップすると、**メインの写真と、その下に小さい写真を横一列に並べた画面**へ移る。戻るのは左上の＜。

```
3列グリッド ──写真をタップ──▶ メイン＋横一列 ──メインをタップ──▶ 全画面
            ◀──── 左上の＜ ────              ◀──── 左上の＜ ────
```

| 要素 | 内容 |
|---|---|
| 開いたとき | **タップした写真をメインにする。**小さい写真の列も、その写真が見える位置まで送っておく |
| メインの写真 | **切り抜かず、写真全体を見せる。**左右になぞると前後の写真へ送る（**→ 形は D46-b で正方形に固定した**） |
| 小さい写真の列 | **左が古く、右が新しい。**横にスクロールでき、タップした写真がメインになる。選んでいる写真に印を付け、メインが変わると列も追従する（**→ 示し方と動きは D46-a で改めた**） |
| 添える情報 | 撮った日と「出会って○日目」 |
| メインをタップ | 全画面で大きく見る（従来の拡大表示）。そこで送った写真は、戻ったときメインにも反映する |

**理由**: 3列グリッドは量と全体を見るのに向くが、**1枚ずつの変化は追いにくい。**全画面は1枚を大きく見られるが、**前後に何があるかが見えない。**その間に「1枚を見ながら前後も見える」段を置いた。

**並びの向きを、グリッドと列で変える。**グリッドは新しい順で、いまの姿から遡る一覧。列は左が古く右が新しく、**育ちを時間の流れのまま辿る**もの。ギャラリーは「この子がどう育ったか」を見る場所なので（§4.4）、1枚を追う段では時間の向きに合わせる。

**モードの切り替えにはしなかった。**最初は「3列」と「メイン＋横一列」を切り替える2つの表示として考えていた。切り替えにすると、どちらで閉じたかを覚えるかなど、決めることが増える。**入口をいつも3列にして、タップで重ねる**形にすれば迷わない。

**メインを左右に送れるようにした。**最初は、詳細のページ切り替え（記録・育成・ギャラリー）と横の操作が取り合うので、送らない案だった。別の画面に移るならこの取り合いは無くなる。残るのは画面の左端からなぞって戻る操作だが、端に限った操作なので両立する。

**メインは切り抜かない。**グリッドは縦長・横長で崩れないよう正方形に切り抜くが、1枚を見る段でも切ると、撮ったときの構図が失われる。（**→ D46-b で改めた。**写真ごとに枠の形が変わってぶれるため、メインは正方形に切り抜き、写真全体は全画面で見る）

**D42 の「撮った1枚」とは別物のまま。**あちらはカメラの上で1枚を確かめるだけで、送る操作を持たない。

**実装上の制約**:

- マイプラントのナビゲーションでは、**行き先を直接渡す `NavigationLink`（`NavigationLink { 行き先 }`）を使わない。**`navigationDestination` と同じスタックに混ぜると、詳細からこの画面へ進んだとき、詳細ごと作り直されて「記録」に戻された。一覧から詳細へは値で、グリッドからこの画面へは `navigationDestination(isPresented:)` で渡す
- `navigationDestination` は**詳細の3ページ（ページ形式の `TabView`）の中に置かない。**「lazy なコンテナの中」として無視され、リンクが効かなくなる


### D46-a — 写真の見せ方と切り替えの動きを、写真アプリに合わせる

**決定**: 1枚を追う画面と全画面の見た目と動きを、iPhone の写真アプリに合わせる。

| 要素 | 変更前（D46） | 変更後 |
|---|---|---|
| メインの写真 | 画面の幅いっぱい、角は四角 | **左右に16ptの余白、角を12pt丸める** |
| 開く・閉じる | 横から入る画面遷移 | **マスから拡大して開き、戻るときは見ている写真のマスへ縮む。**下になぞっても閉じる。全画面もメインから拡大する |
| 列をなぞる | メインは変わらない | **中央に来た写真へ、メインがその場で次々と切り替わる** |
| 列の写真をタップ | メインが横にスライドして変わる | **スライドせず、その場で切り替わる** |
| 見ている写真の示し方 | 枠を付け、ほかを薄くする | **見ている1枚だけ元の縦横比に広がる。**ほかは細く並ぶ（**→ D46-b で正方形に固定した**） |
| 全画面の点 | 何枚目かを点で出す | **出さない** |

**理由**: 写真を1枚ずつ見る動きとして、いちばん広く知られているのが写真アプリ。同じ動きにしておけば、操作を説明しなくて済む。

**余白と角丸で、メインを「1枚の写真」として見せる。**画面の幅いっぱいだと背景との境目が無い。余白があると、送るときも写真と写真の間が空いて流れ、次の1枚に替わったことが分かる。

**戻るときは、開いたときではなく「いま見ている」写真のマスへ縮む。**途中で写真を変えたなら、その写真がグリッドのどこにあるかを示すほうが自然。ただし見えていないマスには縮めないので、**戻る前にグリッドをそのマスまで送っておく。**

**なぞっている間は、全部を細くそろえる。**見ている1枚を広げたままなぞると、広がった分だけ中央の写真がずれて、選び直しが起きる。止まったら、見ている1枚を広げて中央に据え直す。

**点を消した。**写真が増えると点が並びきらず、位置を示せなくなる。

**写真アプリと同じにしていないところ**: 写真アプリでは、メインを指で送っている最中から列が指に合わせて動く。ここでは送り終えてから列が運ぶ。

**実装上の制約**:

- 拡大・縮小は iOS 18 の `navigationTransition(.zoom)` と `matchedTransitionSource` で作る。起点は詳細画面が持つ「見ている写真」で、1枚を追う画面・全画面と共有する。戻るときの行き先もこの値で決まる
- 列のなぞりは、**指で動かしている間（`onScrollPhaseChange` の interacting / decelerating）だけ**メインを追わせる。自分で列を送ったときの位置の変化まで拾うと、メインと列が互いを動かし合う
- メインをその場で切り替えるときは、アニメーションを切った更新にする。そのままだとページ形式の `TabView` がスライドする


### D47 — 仕込みの株に、仮の写真を持たせる

**決定**: 本物のひまりの成長写真（screen-design §8-b）が揃うまで、**ひまりの日記に仮の写真を持たせる。**ギャラリーは日記の写真を集めるので（§4.4）、ギャラリーにも並ぶ。

| 項目 | 内容 |
|---|---|
| 絵 | 起動時に描く鉢植え。**育ちの段階に合わせて描き分ける**（芽 → 本葉 → 水切れで葉が垂れる → つぼみ → 開花 → 結実 → 枯れ） |
| 見分け | **左上に「仮　○日目」の札を入れる。**本物と取り違えないため |
| 置く日 | 何か書いた日だけ（段階の変わり目の8日と、ふつうの日記の12日）。開花の45日目は2枚、「写真ばかり撮っている」とある50日目は3枚。お休みの日には置かない |
| 縦横比 | 縦長を基本に、正方形と横長を混ぜる。花の先と札は中央の正方形に収め、グリッドで切り抜いても切れないようにする |
| カメラの「直近の1枚」（D42） | **出さない。**来場者が撮ったものではないため |
| リセット（D33） | 仕込みと一緒に作り直す。描いた絵は使い回す |

**理由**: ギャラリーの3列・1枚を追う画面・日記のグリッドは、**写真が並んでいないと出来を確かめられない。**確かめるたびに一時的な写真を差し込むのは手間なので、アプリに持たせる。

**画像ファイルを同梱せず、描く。**仮のものをリポジトリの履歴に残さないため。本物が揃ったら、描く仕組みごと消せば跡が残らない。

**段階ごとに描き分ける。**同じ絵や色だけの板だと、列をなぞっても「育っていく」流れが見えず、ギャラリーの目的（この子がどう育ったか）を確かめられない。

**「直近の1枚」から外す。**D42 では、まだ1枚も撮っていなければ何も出さない。仮の写真を含めると、来場者が撮る前からひまりの枯れた姿が左下に出てしまう。

**状態を「暫定」にしている。**本物の写真に差し替えた時点で役目を終える。

**実装上の制約**:

- 描くのは `PlaceholderPhotos`。仕込み（`PlantStore.seed`）から呼ぶ。起動時の仕込みにかかる時間は、シミュレータで約0.3秒になった
- 仮の写真の参照名は `PlantStore` が覚えておき、「直近の1枚」の候補から外す


### D46-b — メインと列の見ている1枚の形を固定する（D46 / D46-a の改訂）

**決定**: 1枚を追う画面では、**写真の縦横比に関わらず形を固定する。**写真をそのまま見せるのは全画面に任せる。

| 要素 | 変更前 | 変更後 |
|---|---|---|
| メインの写真 | 切り抜かず、写真の縦横比のまま（D46） | **正方形に固定し、写真を中央で切り抜く。**余白と角丸は残す。画面が低い機種では、正方形のまま小さくする |
| 列の見ている1枚 | 元の縦横比に広がる（D46-a） | **56×56 の正方形に固定。**ほかは 40×56 の細いまま |
| 列の見ている1枚の位置 | 中央に寄せるが、ずれることがあった | **いつも画面のちょうど中央。**両端の写真でも中央に置き、端の側は空く |
| 全画面 | 切り抜かず、写真全体 | **変えない**（写真をそのまま見せる） |

**理由**: 縦長・横長の写真が混ざると、送るたびにメインの枠の形と位置が変わり、**画面がぶれる。**列の見ている1枚も、写真ごとに幅が変わると両隣が押し広げられて揺れる。1枚を追う画面は前後を見比べる場所なので、形がそろっているほうが違いを追いやすい。

**正方形にした。**グリッドと同じ形なので、グリッドのマスから拡大して開くときも形が変わらない。候補には縦 3:4（縦長の写真の切り抜きが少ない）もあったが、まず正方形で試す。

**写真全体は全画面で見る。**メインで切り抜かれた部分は、タップして開けば見られる。D46 で「メインは切り抜かない」とした理由（撮ったときの構図が失われる）は、全画面が引き受ける。

**実装上の制約**:

- 列の位置は、**写真の番号から計算で決める。**列の両端に「画面の半分 − 見ている1枚の枠（両隣の間を含めて 68pt）の半分」の余白を置くと、i 枚目を中央に置く送り位置は i × 42pt（細い写真の幅 40pt ＋ 間 2pt）になり、画面の幅に左右されない
  - `scrollPosition(id:anchor: .center)` で中央に寄せる形は使わない。見ている1枚が広がる前の幅で位置を決めるため、広がった分の半分（7pt）右にずれた
- **なぞっている間は、細くなった分（28pt）を列の右端の余白に足し、列の長さを変えない。**長さが変わると、止まって広げるときの送り先が短い列の端で頭打ちになり、いちばん新しい写真だけ中央から 28pt 右にずれた
- iOS 26 では、画面のどこからでも右へなぞると前の画面に戻る。**列がいちばん古い端に着いた状態から右へなぞると、グリッドに戻る。**端に着くまでのなぞりは列が受け取るので、写真を送っている途中に戻ってしまうことはない

### D48 — 触覚を2つの層に分け、鳴らさない場所も決める

**決定**: ハプティクスを入れる。**操作の触覚と植物の触覚を層として分け、混ぜない。**

| 層 | 何を伝えるか | 材料 |
|---|---|---|
| **操作の触覚** | 機械がこちらの操作を受け取ったこと | 標準（`tick` / `tap` / `snap` / `thud` / `caution`） |
| **植物の触覚** | その子が居ること、どんな状態か | Core Haptics のカスタム（`pulse` / `meet` / `thirst` / `drink` / `unease` / `farewell`） |

**理由**: 原則2で数値を出さないと決めた以上、状態を伝える経路は**視覚と言葉の2つしかなく、どちらも画面の中にある。**触覚は数を使わずに「渇いている」を伝えられ、**騒がしい展示会場でも届く。**音を足さずに手応えだけを足せる。

**層を混ぜない理由**: 操作の返事に植物のパターンを使うと、押した手応えが生き物の気配に化ける。逆に**出会いに標準の `success` を使うと「登録という作業が完了した」音になり、**D9（登録を出会いに溶かす）と噛み合わない。

**`error` も `success` も使わない。**このアプリに「ユーザーの失敗」は無い（原則3 / D24）。嬉しいことが起きるのは植物の側なので、そこで返すのは植物の触覚になる。

**「鳴らさない場所」も表に書く。**書いていないと、後から誰かが鳴らす。全画面の写真、グラフの送り、日記の保存、上限で押せなくなったボタン、タブの切り替え、植物を見失ったときは鳴らさない。

**迎え入れの合図は、名前をつけた瞬間に置く。**「話しかける」→「はじめまして」→名前の入力→確定が数秒のうちに起きるので、出会いの手応えを2回鳴らすと、どちらが成立なのか分からなくなる。「はじめまして」は `pulse`（居る）に留める。

**株の削除に成功を鳴らさない。**D18-a で植物を人と同等に扱うと決めた以上、ここは作業の完了ではなく別れになる。

**段階を分ける**: 段階1は標準の語彙だけ、段階2で Core Haptics の植物の触覚（どちらも実装済み）。**段階1は既存の操作に閉じていて外せるが、段階2は手触りそのものを作る仕事で、強さと長さは実機がないと決まらない。**

**看取りの触覚（`farewell`）は、いまは株の削除でしか鳴らない。**セッションの中で生きている株が枯れる経路が無いため（観察の記録はいまの段階をそのまま書き戻す）。枯死の瞬間に鳴らすなら、段階の進みかたを決めるところから。

詳細は [../design/haptics.md](../design/haptics.md)。


### D49 — 吹き出しは風船にし、しっぽの先端を空間に打った点そのものにする

**決定**: 吹き出しを**半透明の風船**として描き直す。しっぽは「先端＝打った点」として置き、
**本体をそこから逆算する。**震えは1€フィルタと不感帯で取り、**打った点そのものを走らせながら寄せ直す。**

**なぜ**: 手ぶれで先端の向きが定まらず、**どの株の言葉なのかが読み取れなかった。**
D2 で「実物の植物から吹き出しが出る」と決めた以上、指す先が揺れる吹き出しは中核体験そのものを損なう。

**「しっぽを無くす」は採らない。**株が2つ以上あるとき、しっぽの無い吹き出しは
**誰の言葉なのかを示せない。**D40 で2株目以降を迎えられるようにした以上、ここは残す必要がある。
向きが定まらないのは記法の問題ではなく、置きかたと計測の問題だった。

**原因は3つあり、どれも別の場所にあった。**

| # | 原因 | 直しかた |
|---|---|---|
| 1 | **本体の中心**を打った点に重ね、しっぽは常に真下に出していた | 先端を点に置き、本体を逆算する。本体の高さがいくつでも先端は点に貼り付く |
| 2 | 投影した点にバネのアニメーションを掛けていた | **外す。**毎フレーム更新される値にバネを掛けると、追いつく前に次の目標が来て泳ぐ |
| 3 | **奥行きが取れないとき、画面の中央に点を打っていた** | その点を通る視線の上に置く。さらに、相手が決まったあとも測り直して寄せる |

**3が一番大きい。**レイキャストが外れた株は、画面のどこに写っていても中央に打たれていた。
植物は平面検出が最も苦手な被写体（D3）で、外れる回は多い。**姿勢推定の震えより、
奥行きを外したときの視差のほうが大きく効いていた。**

**打った点を走らせながら直す。**相手が決まったら検出を止めていたが、止めると
最初の1回で決まった点を使い続けることになる。1.2秒ごとに測り直し、0.25ずつ寄せる。
**1回の結果に飛びつかない。**隣の鉢や通りがかりの人を拾った拍子に持って行かれる。

**画面の中へは寄せない。**株が画面の端に寄ったとき、本体を画面内へ収めることもできる。
だがそうすると**本体は残るのに先端だけが株から離れていく。**指す先が狂うくらいなら、
画面の外へ出て消えるほうがよい。**吹き出しは空間に固定されたもので、画面の持ち物ではない。**

**反射は輪郭に沿って走らせる。**ぼかした塊を中ほどに置くと、平らな板に汚れが乗ったようにしか見えない。
丸い面に映り込む光は輪郭をなぞる。**しっぽの側面は直線にし、先端だけ側面に接する円で丸める。**
曲線で先端まで描くと、向きを揃えなければ角が出て菱形に見え、揃えれば手前で細って水滴に見えた。

**素材のぼかしは使えない。**`Material` は ARKit が Metal で描く映像を取り込めない
（弧で分かっている制約）。白の重なりと艶で自前で作り、**濃さは実測した明るさから決める。**
薄いままでは、明るい背景で黒い文字が読めない。

**写実に寄せない。**映り込みを増やすほど絵としての軽さが消え、カメラ映像の一部に見えてくる。艶は2つまで。

**置き場所は D50 で改訂した。**「先端＝打った点、本体はその真上」は尻尾の正確さを最優先にした形で、
**優先順位が違っていた。**見た目（風船・反射・尻尾の形）と震えの始末は、この決定のまま残る。

詳細は [../design/speech-bubble.md](../design/speech-bubble.md)。

### D50 — 吹き出しは株の斜めに置き、悪くなったときだけ置き直す

**決定**: 吹き出しを**株の真上ではなく斜め（左上・右上・左下・右下）**に置く。
位置も象限も**空間に固定**し、**明らかに悪くなったときだけ置き直す。**
尻尾は本体と株を繋ぐ役に回り、向きは角度を制限して株の方を指す。

**理由**: D49 では「尻尾の先端＝空間に打った点」を最優先にし、本体をその真上に逆算していた。
**優先順位が違っていた。**大事なのは尻尾が正確に指すことではなく、**吹き出し自体が
常に適切な位置にあり続けること。**真上に置くと株の頭を隠し、株が画面の上寄りにいると
本体が画面の外へ出る。**尻尾は正確なのに、居場所が悪い。**

**「適切」の中身**（この優先順）:

1. 株を隠さない（**葉先に少し掛かるのは可**）
2. 画面に収まっている
3. 画面下端の操作（シャッター・弧）に被らない
4. 株に近い

**空間固定と「常に適切」は両立しない。**空間に固定したままでは、端末を振れば画面の端へ寄り、
外へも出る。かといって画面に追従させると、端末を動かすたびに吹き出しだけが遅れて付いてきて、
**板に貼った字幕に見える。**折衷として、**間は完全に空間固定、明らかに悪くなったときだけ置き直す。**

**点を2つ持つ。**

| 点 | 何を表すか | 使い道 |
|---|---|---|
| 株の点 | 葉の塊の中ほど | 尻尾が指す先 |
| 本体の点 | 株から斜めにずらした位置 | 本体の置き場所 |

どちらも空間に固定して毎フレーム投影する。**2つとも固定だから、全体が空間の中で1つの物として動く。**
本体だけ画面で決めると、結局「板に貼った字幕」に戻る。

**象限の決め方**:

- **左右** — 株が画面の右寄りなら左、左寄りなら右。中央付近は**ヒステリシス（±15%）**で前の側を保つ。
  ここで揺れると、以前より悪くなる
- **上下** — **上を優先。**漫画の記法に沿い、画面の下端は操作で埋まっている。上に余地が無いときだけ下

**置き直す条件**: ①本体が画面の外へ出そう ②株を大きく隠している
③象限の判定が反対側に変わって一定時間続いた。

**置き直しはなめらかに移動する。**消えて出ると、セリフを読んでいる途中で途切れる。

**尻尾**: 象限に応じて下辺／上辺の、株に近い側から生やす。角の丸みには掛けない。
向きは葉の塊へ向けるが、**辺の垂直から 15〜45°** に制限する。**正確さより形の安定を取る**——
これがこの決定の趣旨そのもの。先端の丸みは半径 2.5pt（4pt では丸すぎた）。

**制約**: 象限の判断材料になる株の枠は、**検出が1.2秒ごとにしか更新しない**（D49）。
切り替えが最大1.2秒遅れる。頻繁に切り替えない方針なので実害は見込んでいない。

**限界**: 本体の点は、置いた時点のカメラの右／上を基準に株からずらす。
**株の周りを大きく回り込むと、ずらした向きが意味を失う。**そのときは置き直しの条件に掛かる。

**判定の基準は「画面に見えているか」ではない。**株に向けたときに**株に対して
適切な位置にあるか**で判定する。カメラを株から外せば見えなくなってよい。

置き直すのは、**株に対する位置がずれたとき**に限る。ずれる原因は2つ。

- **株の点が直り続ける**（D49 の寄せ直し）。本体は置いたままなので、2点の関係が変わる
- **株の周りを回り込む。**ずらした向きは打った時点のカメラ基準なので、角度が変わると
  斜めに置いたはずの吹き出しが株の真上や裏に見える

**画面は、どの象限を選ぶかの参考にしか使わない。**置き場所そのものは株の枠からの
相対だけで決まる。画面に収める寄せを入れると、**株に対する位置が画面の都合で変わり、
端末を振るたびに吹き出しが画面へ戻ってくる。**

**実装して分かったこと（1）**: 象限を「株を隠す／画面からはみ出す／株から遠い」の点数だけで
選ぶと、**株のいる側が選ばれて、そのうえに乗った。**縦のずらしで株の頭は避けられてしまうため、
左右の選択が「隠す割合」にほとんど響かず、判断が「近いほう」に落ちるため。
**「株が右寄りなら左」を点数の項として明示的に足す必要がある。**

**実装して分かったこと（2）**: 置き直しの判定を画面基準（はみ出し25%超）で書いたところ、
**端末を振るたびに吹き出しが画面へ戻ってきた。**縦は範囲の端から15ptで条件に入るうえ、
打ち直した位置はそのときの画面から計算されるので、置き直し自体が「画面の良い位置へ戻す」
動きになる。**判定を株からの相対に置き換える必要がある。**

**実装して分かったこと（3）**: 画面に収める寄せを外すと、今度は株の枠の外へ出しすぎた。
食い込み（本体の12%）が唯一の調整代なので、**0.28 まで増やして釣り合いを取った。**

**限界**: 株の見かけも本体も距離に反比例して大きくなるため、「株＋吹き出し」の並びは
**距離によらず同じ形**のまま拡大する。株が画面いっぱいに写る距離まで寄れば、その並びは
画面に入らない。**画面に収める寄せをしない以上、寄りすぎたときは端から出る。**

詳細は [../design/speech-bubble.md](../design/speech-bubble.md) 3章。

### D50-a — 吹き出しの大きさは株の見かけの大きさに繋ぐ

**決定**（2026-09-21 改訂）: 倍率を**株の見かけの大きさ**から決める。

```
1行ぶんの本体の高さ ＝ 株の枠の（幅＋高さ）÷2 × 0.25
```

両端だけ止める。近いほうは**本体の幅が画面の85%**、遠いほうは 0.3 倍。

**改訂の理由**: はじめは距離に反比例させていたが、**株の大きさを一切見ていなかった。**
小さい株ほど近くに寄って見るので、**小さい株ほど倍率が上がり、株に対して吹き出しが大きくなる。**

株の見かけ自体が距離に反比例するので、**「遠ざければ小さく」は新しい式のままで成り立つ。**
むしろ上位互換で、株の大小にも合う。**等倍になる距離（0.8m）は不要になり、
L-11 の宿題がひとつ消えた。**

**基準は「1行ぶんの本体の高さ」。**本体そのものの高さに合わせると、2行のセリフだけ
文字が小さくなる。

**幅と高さの平均を使う。**高さだけだと横に広がった株で、幅だけだと背の高い一本茶で、
吹き出しが小さくなる。

**0.25 は理想の見本（添付画像）を測った値。**本体 388×96px に対し株（葉のかたまり）405×358px。
**実機で合わせ直す前提。**見本で測ったのは葉だけだが、検出が返す枠は前景マスクなので
鉢まで含む可能性が高い。診断パネルにスライダーを置いた。

**測り直しで跳ねさせない。**株の枠は1.2秒ごとにしか更新されないので、
**「1mのときの大きさ」に直して覚え、測り直すたびに少しずつ寄せる。**

**それでも入口は段になる**ので、**出口でまとめて均す。**目標の倍率を毎フレーム計算し、
時定数 0.2 秒でそこへ寄せる。距離も、配る値（0.02m 刻み）と計算に使う値（刻みなし）を分ける。
**刻みは診断表示のためのもので、大きさの計算に持ち込むと段として見える。**

**分かった限界**: 縦持ちの画面は狭い。**9文字のセリフはこの大きさで画面幅の61%**
（見本の square な画面では38%）を占めるため、株が画面の中ほどにいると、
横に並べる余地が残らない。株の枠に食い込ませる割合（見本の実測で横0.40／縦0.36）を
当てても、はみ出す場合がある。**文字の折り返し幅（いま250pt）を狭めるのが次の手。**

**理由**: いままでは `1.2 ÷ 距離` を 0.6〜1.2 で頭打ちにしていた。

| 距離 | いままでの倍率 |
|---|---|
| 1.0m 以下 | 1.2（頭打ち） |
| 1.2m | 1.0 |
| 2.0m | 0.6 |
| 2.0m 以上 | 0.6（頭打ち） |

**1〜2m の外では完全に固定**で、その中でも変化は2倍ぶんしかない。
遠ざかっても近づいても大きさが変わらず、**株との比が崩れる。**
吹き出しが空間に在るなら、株と同じように遠近が付かないとおかしい。

**斜めのずらし量もメートルで持つ**（D50）ので、これも一緒に縮む。
**株との位置関係が、距離によらず一定になる。**

**遠くで読めなくなるのは、そのままにする。**読めないこと自体が「近づいてみて」という誘いになる。
物としては正しい振る舞いで、実際そこに植物はあるので人は近づく。
**読める大きさで下限を止めると、遠くでは株より大きい吹き出しになり、空間から浮く。**
0.3 倍で止めるのは、それ以下が点にしか見えないため。

**近いほうは、倍率ではなく本体の幅で止める。**セリフの長さで本体の幅が違うので、
倍率で止めると長いセリフだけ画面から切れる。**文字を折り返し直す手は採らない。**
距離で吹き出しの形が変わり、同じ物に見えなくなる。

**基準の距離（何メートルで等倍か）は 0.8m を出発点に、実機で詰める。**
展示での立ち位置が決まっていない（L-11）。

**刻みは要らなくなる。**いまは倍率を 0.05 刻みに丸めている。大きさが変わると
しっぽの付け根が動くためだったが、D50 では**本体の中心が投影点そのもの**になり、
拡大縮小しても中心が動かない。滑らかに変える。

詳細は [../design/speech-bubble.md](../design/speech-bubble.md) 4.5。

そのため、

### D52 — 未設定のときは、映像を眠らせて撮れないことを形で示す

**決定**: 弧で「未設定」を選んでいるあいだ、**カメラ映像をぼかし、「撮る」に斜線を入れて
押せなくする。**「見当たらないなぁ」は出さない。

**理由**: D40-a により、誰も選ばれていないあいだ**植物は探してすらいない。**
それなのに「見当たらないなぁ」と出していた。**見つからないのではなく、見ていない。**
嘘になっている。

**向けても何も起きない画面が、向ければ何か起きる画面と同じ見え方をしていると、
押せないことに気づけない。**ぼかしと斜線で、状態を形にする。

**斜線はボタンの端から端まで引き、縁の輪も断ち切る。**中に収めると「記号が入っている」に見えて、押せないことが伝わらない。

**ぼかすのは映像だけ。弧とシャッターは鮮明に残す。**この状態から出る道がそこにしかない。
**「迎える」も塞がない**——未設定から出るもう一つの道（D40-a）。

**仕込みの株（ひまり）を「迎え入れた株」として数える。**ひまりは一生を終えた状態で
入っている（timeline.json の最終パネルが枯死）。その日の主役を選ぶ `plantForToday` が
「枯れた株は選ばない」ため、**すでに株がいるのに「先に迎えてね」と言われていた。**
生きている株が一つも無いときは、見送った株を返す。没後も日記のページは続くので、
見送った株のページに積むこと自体は、いまの作りと矛盾しない。

**残る宿題**: 「見当たらないなぁ」を消したぶん、**未設定のときに文言が一つも無くなった。**
ぼけた映像と斜線で「いまは撮れない」は伝わるが、**どうすれば出られるかは伝わらない。**
弧を触れば分かるが、展示で来場者が気づくかは実機で見る（L-11）。

### D51 — 検知は「株を捉えてから 0.3 秒」で成立させる

**決定**: 検出できた瞬間ではなく、**株を捉えた状態が 0.3 秒続いてから**検知を成立させる。
成立と同時に、触覚（`pulse`）と一言目を出す。

**理由**: 面積の下限が **3%** しかなく、**株が画面の端にちらっと入っただけで成立していた。**
判定は「植物らしさ 0.10 以上」と面積だけで、枠が画面の端で切れていても、
一度きりの検出でも通っていた。来場者から見ると**まだ株を見ていないのに話しかけられる。**

| 条件 | 前 | いま |
|---|---|---|
| 植物らしさ | 0.10 以上 | 変えない |
| 面積 | 画面の 3% | **画面の 4%**（雑音よけの床。ここでは測らない） |
| 位置 | なし | **枠が画面のどの辺でも切れていない＝株の全体が入っている** |
| 続けて | なし | **0.3秒**（はじめ1秒。待たされる感じが強かった） |

**面積では測らない。**一度 12%（見本の株が画面の13.8%）まで上げたが、
**株に限りなく近づかないと出なくなった。**面積は「どれだけ大きく写っているか」の話で、
「捉えたか」とは別物だった。**遠くても、全体が入っていればそれでよい。**

**枠が画面の端に貼り付いているかで「全体が入っているか」を見る。**マスクの枠は画面で
切られるので、辺に接していれば、そこから外へ続いていると分かる。

**切れてよいのは1辺まで**（既定）。鉢の足元や、葉先が1枚画面の端に届いた程度では落とさない。
厳しさは実機で切り替えられる（全体 / 1辺可 / 問わない）。

**取りこぼしを1回は許す。**これを許さないと、成立には**「間隔ぶん空けた検出を2回連続で
完璧に通す」**ことが要る。検出の間隔は処理時間の3倍（0.4〜2.0秒）なので、実機で処理が
0.5秒なら1.5秒間隔。**マスクが半分の確率でしか安定しないだけで、成立まで数秒〜十数秒**かかっていた。
2回続けて外したときだけ捨てる。

**探しているあいだは間隔を 0.6 秒までに詰める。**通常は処理時間の3倍まで空けて描画を守るが、
**探している間は吹き出しが出ていないので、守るべき追従が無い。**

**どの条件で落ちたかを診断パネルに出す。**「らしさ／面積／収まり」のどれで弾かれたかが
見えないと、推測で数値をいじることになる。

**アンカーは最初に条件を満たした時点で打つ。ただし見せない。**待っている1秒のあいだに
寄せ直し（D49）が効くので、**出た瞬間から正しい位置に居られる。**途中で条件を外したら捨てる。

**「はじめまして」（シャッターの「迎える」）は待たない。**「話しかける」を押した直後なので、
待つと押した手応えが消える。この経路は撮った1枚から相手を受け取るため、上の条件も通らない。
パネル（画像アンカー）もこれまで通り即座に出す。

### D54 — 写真の上限は「1日・1株につき3枚」

> **一部改訂（D54-a）。**上限は「日記のページは全体で10枚」「カメラでの撮影は1株3枚」の2つに分かれた。
> 「ページ全体には上限を置かない」は取り消し。写真が株を持つこと、撮った相手は弧で選んでいる株であること、
> 上限に達したら株の名前を言うことは、そのまま生きている。

**決定**: 日記の写真の上限を、ページ全体で5枚から**1日・1株につき3枚**に改める。あわせて、写真は1枚ずつ「どの株を撮ったか」を持つ（`DiaryPhoto`）。

**これまで**: 上限はページ全体で5枚だった（`DiaryEntry.maxPhotosPerDay`）。理由は記録されていない。2026-08-31 に日記を1日1ページの日誌に改めたとき、実装の規則として入ったまま据え置かれていた。

**ページ全体で数えると壊れること**: 日記は**1日1ページで、全体で一つ**（§5.0）。一方、その日に撮る相手は1株とは限らない。展示では、来場者が弧で仕込みの株を選んで観察し、そのあと自分の株を迎える道がある（screen-design §8-a）。ページ全体で数えると、**先に撮った株が枠を使い切り、もう一方の株が1枚も撮れない。**上限が「その日に何枚撮ったか」ではなく「誰を撮ったか」に依存してしまう。

**写真に株を持たせる**: 枚数を株ごとに数えるには、写真1枚ずつが相手を知っている必要がある。ページの主役（`DiaryEntry.plantId`）に預けると、同じ日に2株を撮ったとき後から撮ったほうが先の株の記録として積まれる。ギャラリー（§4.4）も同じ取り違えをしていた。**写真で絞る**ことで、上限とギャラリーの両方が同時に正しくなる。

**3枚にした理由**: 日記のページでは写真を左右スワイプで見る（§5.1-a）。1ページに何枚も積むと、その日のページが写真の束になり、日誌としての読み心地が落ちる。**1株につき3枚**なら、スワイプ2回で見終わる。展示の滞在は5〜6分なので、1株につき3枚で足りないことはまず起きない。

**上限に達したときは株の名前を言う**: 「今日はもう3枚あります」では、どの株が満ちたのか分からない。株ごとの上限にした以上、「ひまりは今日もう3枚あります」と名前を添える。

**ページ全体には上限を置かない**: 2株を撮れば6枚になる。1ページが長くなることより、**撮りたい相手を撮れないことのほうが体験として悪い。**

**撮った相手は、弧で選んでいる株**（`selectedPlantId`）: 「その日のページの主役」（`plantForToday`）とは別物である。後者は**生きている株を先に選ぶ**ため、見送ったひまりを見ながら撮っても、こすもの写真として積まれていた。枚数の数えもこすもの枠を食い、「こすもは今日もう3枚あります」と出る。**カメラが向いている先がそのまま被写体**であり、見送った株でも変わらない。今日のページの主役にも、撮った相手をそのまま渡す。


### D54-a — 写真の上限を「日記のページ」と「撮影」の2つに分ける（D54 の改訂）

**決定**: 上限を2つに分ける。

| 上限 | 数え方 | 数えるもの | 枠が戻るとき |
|---|---|---|---|
| **日記のページ** | 1日10枚。**ページ全体で数え、株では分けない** | カメラで撮った写真と、日記の「+」で足した写真 | 日記から外したとき |
| **カメラでの撮影** | 1日・1株につき**合計**3枚 | 「撮る」で撮った写真だけ（`DiaryPhoto.fromCamera`）。「+」で足した写真は撮影ではない | **直近の写真の画面（D42-a）で削除したとき。**日記や写真から外すだけでは戻らない |

**パラパラカメラの写真は、どちらにも数えない。**別に1日・1株につき1枚を持つ（パラパラカメラの決定は、あとで別に記録する）。

**経緯**: D54 で「1株3枚・ページ全体には上限を置かない」と決めたあと、2026-09-22 0:54 のコミット（dd64a3d）で、コードが「ページ全体で1日10枚・株では分けない」に変わっていた。コミットには「docs は後で書く」とだけあり、理由は残っていない。食い違いに気づいてユーザーに確かめ、次の答えを得た。

> 日記の写真の投稿数は、全体で十枚です。撮影は、１植物あたり三枚です。

2つは別の上限として両方効かせる。カメラで撮るときは、**先に撮影の3枚、次にページの10枚**を確かめる。

| 状況 | 表示 |
|---|---|
| その株の撮影が3枚に達した | 「ひまりは今日もう3枚撮りました」（どの株が満ちたのかを名前で言う・D54） |
| ページが10枚に達した | 「今日の日記はもう10枚あります」 |
| 撮れた | 「日記に追加しました（ひまり 2/3）」。分母は撮影の3枚 |

**撮影は「合計」で数える**: はじめは「日記から外した写真は撮影の枚数にも数えない（外せば撮り直せる）」とした。ページの上限と扱いを揃えるためだった。ユーザーから次の指示があり、改めた。

> 写真は合計三枚です。削除したら枠が復活するようにしてください。

日記や写真（マイプラント）から外しても、写真はもう片方に残っている。撮った1枚としては残っているので、枠は戻さない。**写真そのものを消したときにだけ戻す。**消す場所として、直近の写真の画面（D42-a）に削除を足した（screen-design §3.2-e）。

**数は決めてもらった値**: 10枚・3枚はユーザーの指定。D54 の「3枚にした理由」（スワイプ2回で見終わる、滞在5〜6分で足りる）は、撮影の3枚についてはそのまま当てはまる。

### D42-a — 左下の1枚を押したら、その日に撮った写真が並ぶ

**決定**: カメラ左下の「直近の1枚」（D42）を押した先を、1枚だけの拡大から**その日に撮った写真を並べる画面**に改める。構成はギャラリー（D46）と同じ**メイン＋下の小さい列**。

**なぜ1枚では足りないか**: 撮ったあとに確かめたいのは「いま撮れたか」だけではなく、**「今日どれを撮ったか」**である。1枚ずつしか見られないと、直前の1枚と見比べられず、撮り直すかどうかを判断できない。

**株はまたぐ**: 今日撮ったものがすべて並ぶ。誰を撮ったかで分けるのはギャラリーの役（screen-design §4.4）。**ギャラリーは「この子がどう育ったか」、ここは「今日これだけ撮った」。**日付は全部同じなので出さず、代わりに**どの子を撮ったか**をキャプションに置く（D54 により写真が株を持つので言える）。

**カメラの上に重ねる**: D42 の「画面を移らない」を引き継ぐ。別画面へ送ると、見終わったあとにカメラへ戻る手間が要る。ARのセッションも切らない。

**段は2つまで**: ギャラリーは「メイン＋列 → 全画面」の3段だが、ここは2段で止める。撮ってすぐ確かめる場なので、段を増やすほど戻る道が長くなる。

**メインは切り抜かない**: ギャラリーが正方形に固定する（D46-b）のは、育ちを並べて送る画面だからである。**ここは全画面の段が無い以上、メインで全体が見えないと確かめようがない。**

**閉じるのは×と下スワイプ**: D42 の「どこを触っても閉じる」は1枚しか無かった頃の作り。列とメインを触れるようになった以上、触った先が閉じるのは誤操作になる。

**左下のサムネも今日に限る**: 押した先が「その日の写真」である以上、昨日の1枚を出していると開いた瞬間に食い違う。今日まだ撮っていなければ空の枠のまま（撮る前と同じ）。展示は毎回リセットするため、当日の見え方は変わらない。


### D55 — 画面の中の切り替えを、下のタブバーと同じ作りにする

**決定**: マイプラント詳細の「記録・育成・ギャラリー」と、育成の時間幅（全体・1年…）を、**下のタブバーと同じ見た目・動き**の部品（`CapsuleTabBar`）に置き換える。あわせて、**アプリのアクセント色を緑にする**（アセットカタログの `AccentColor`）。

**これまで**: どちらもシステムの `Picker(.segmented)` を、タブバーと同じガラスに載せていた（D45）。材料は揃っていたが、部品そのものは別物で、灰色の溝に白い塊が乗る見た目だった。タブバーの選択中の色はシステムの青のままだった。

**全く同じにはできない**: タブバーはシステムの `TabView` が描いており、塊が伸びる動き・縁で色が変わる動き・押したときのガラスの玉は、外から使える部品になっていない。本物の `UITabBar` を単体で埋め込む手もあるが、項目はアイコンを置く前提で並ぶので、文字だけのタブにすると崩れる（試してはいない）。**見えているものを写して作る**ことにした。写すものは D41-a で録画をコマ送りして確かめた内容と同じ。

| 手本（タブバー） | `CapsuleTabBar` | 一致 |
|---|---|---|
| 全体枠は Liquid Glass のカプセル | 同じガラス（`floatingGlass`） | 同じ |
| 選択中は**無彩色の塊**。色が付くのは中身だけ | 同じ。塊と地の明るさの差を画面写真で測って合わせた（ライト −18 / ダーク +33） | 同じ |
| 塊は1つのまま**伸びて**移り、途中で2項目をまたぐ | 左右の端を別々に動かし、後ろの端を 0.07 秒遅らせる | 同じ |
| 色はフェードせず、**塊の縁を境に**切り替わる | 文字を2枚重ね、塊の形で出し分ける（弧と同じ作り・D41-a） | 同じ |
| 押すと膨らんだガラスの玉になり、なぞると指に付いてくる | 押すと塊が 3pt 膨らみ、なぞると指に付いてくる。離したところで決まる | **ガラスの玉にはならない** |

**緑にした理由**: 植物のアプリなので。**切り替えだけを緑にせず、アクセント色ごと変えた。**タブバーの選択中が青のままだと、「いま選ばれているもの」の示し方が画面の中で2色に割れる（screen-design §3.2-a の「示し方を1つに揃える」）。アクセント色ごと変えると、弧の名前（D41-a）・育成のグラフの強調・標準のボタンもまとめて緑になる。

**なぞっている途中では選択を変えない**: 変えると、指が通るたびにページがめくれ、育成ではグラフが作り直される。離したところで決める。

**部品は鳴らさない**: 詳細の3画面はスワイプでもめくれる。鳴らすのはページの変化に掛けた `tick` の1か所にし、押しても、めくっても1回だけ鳴るようにする（haptics §5.2）。

**システムの `Picker(.segmented)` には戻さない**: iOS 26 のものはつまみがガラスになる動きを持つが、灰色の溝のぶん、タブバーとは別の部品に見える。

**今回の範囲**: **実際のデータのやり取り（家族やほかの利用者との送受信）はしない。将来の実装に回す。**このため、下の「覆す決定」は今回のスコープでは起きず、D1・D10・D19 は維持される（D20 と同じ扱い）。

### D57-a — 4つ目のタブの名前を「トーク」にする（D57 の改訂）

**決定**: 4つ目のタブ（D57）の名前を**「トーク」**にする。画面の見出しも同じ。

| 「メッセージ」（5文字） | 185.5 / 390 / **595.5** / 785 / 999 | **7.5px＝2.5pt 左** |

## ガジェット（専用ハードウェア）

専用ガジェットを自作する前提。取得項目は**日照・水量・気温・湿度・栄養素**。

**大原則**: ガジェットなしでもアプリ単体で成立する。

**設計方針 — 「劣化版」ではなく「足し算」**:

なし版とあり版で同じUIを使い、あり版で数値欄が埋まる作りにすると、なし版は常に穴が空いて見え、ユーザーは欠落を数えることになる。そうではなく、なし版は「植物が言葉で伝える」体験として完結させ、数値の枠をそもそも作らない。ガジェットを挿すと、そこに新しい層が乗る。

| | ガジェットなし | ガジェットあり |
|---|---|---|
| 入力 | カメラ画像のみ | カメラ画像 ＋ 実測値 |
| 診断 | 見た目から推定 | 数値の裏付けあり。原因の特定精度が上がる |
| お世話の検知 | 画像の差分から推定 | 自動。水をやれば水量が上がる |
| 個体の同定 | 画像特徴 ＋ 手動修正 | ガジェットIDで確実 |
| セリフ | 見た目に基づく | 具体的になる（「今日は日が足りなかったよ」） |

これにより、ガジェットの価値が「欠けた穴が埋まる」ではなく「植物がもっと分かるようになる」という前向きな動機になる。
