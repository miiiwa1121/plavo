# 開発ログ 2026-09-20

ギャラリーの列（1枚を追う画面）の中央寄せがずれて見える、という指摘を画面写真のピクセルで検証した日。

## 指摘

> 写真と日記のアイコンを比較すると少しだけ中心がずれて見える。ただ写真は等間隔に並んでいるので、日記のアイコンのほうが中心ではないのでは。

## 測り方

実機の画面写真（1206×2622、iPhone 17 相当・3倍）を ffmpeg で生のRGBに変換し、Python で走査した。

- 列は、写真と写真の間に見えるページの地（グレー）の列を数えて、写真の左右の端を出す
- タブバーは、アイコンの黒い画素の塊を左右から挟んで中心を出す

## 結果

画面の中心は 603px（201pt）。

| 測ったもの | 位置 | 画面の中心との差 |
|---|---|---|
| 列の見ている1枚 | 519〜686px（168px＝56pt）、中心 603px | **0** |
| メインの枠 | 48〜1157px、左右の余白はどちらも48px（16pt） | **0** |
| タブバーのカプセル | 63〜1142px、中心 602.5px | ほぼ0 |
| **タブバー「日記」のアイコン** | 中心 **617px** | **+14px（+4.7pt）右** |

**指摘のとおりだった。**ギャラリー側は中央にあり、ずれて見えたのは日記のアイコンのほう。

アイコンの中心は左から 185.5 / 401 / 617 / 812 / 1012px で、間隔も 215.5 / 216 / 195 / 200px と揃っていない。iOS 26 のタブバーは、項目の幅が文字の長さ（カメラ・マイプラント・日記・ルーム・マイページ）で決まるためで、**5項目の真ん中が画面の中心に来るとは限らない。**

## 判断

**直さない。**タブバーは OS の部品で、こちらの基準は画面の中心。ギャラリーの中央寄せは D46-b のとおり合っている。

## 追記 — タブの名前を「プロフィール」に変えて中心をそろえた（D13-a）

「UI的に中心がずれて見えるのは避けたい」という依頼。直す先はタブバー側になる。

### タブバーの項目の幅は、名前の文字数で決まっていた

5つのタブを順に選んで項目の位置を測ると、**どのタブを選んでも位置は同じ**だった。幅は名前の文字数で決まる（pt、画面の中心は 201）。

| 項目 | 文字数 | 幅 | 中心 |
|---|---|---|---|
| カメラ | 3 | 74 | 62 |
| マイプラント | 6 | 88.3 | 133.8 |
| 日記 | 2 | 74（最小幅） | **205.7** |
| ルーム | 3 | 74 | 270.3 |
| マイページ | 5 | 79 | 337.5 |

左（74＋88.3＝162.3）が右（74＋79＝153）より 9.3 重く、その半分の 4.7 だけ「日記」が右へ寄っていた。**右側を1文字増やせば釣り合う。**

### 直したあと

「マイページ」を6文字の「プロフィール」にして測り直した。

| 測ったもの | 位置 |
|---|---|
| 「日記」の中心 | **201.0（画面の中心）**。5つのタブどれを選んでも同じ |
| ギャラリーの列の見ている1枚 | 519〜686px（中心 603px＝画面の中心） |
| 画面写真のタブのアイコン | 185.5 / 394 / **603** / 791 / 999px |

**左右を「3文字＋6文字」でそろえる**という形にしたので、文字の大きさが変わっても釣り合いは崩れない。タブ名を変えるときは反対側の文字数と合わせること（D13-a）。

名前の意味の面でも、D20 で「他人に公開する自己紹介」と定めているので「プロフィール」のほうが中身を言っている。

### 直さなかった案

- 列の中心をタブバーのアイコンに合わせる → 機種や文字の大きさで変わるうえ、メインの枠や日付の位置と食い違う
- 写真の画面でタブバーを隠す（写真アプリと同じ）→ **今回は見送り。**中心のずれが消えたため。別途相談する

### 波及

「マイページ」はタブ名なので、docs（要件・設計・セットアップ）とコードの表示名・コメントをまとめて置き換えた。devlog は当時の記録なので触っていない。

## 追記 — 触覚（ハプティクス）をどこに入れるか計画した

依頼は「どこにどんなハプティクスを入れるのか、まず計画を立てる」。実装はしていない。[../design/haptics.md](../design/haptics.md) に案としてまとめた。

### 調べたこと

既存の触覚は**1か所だけ**だった。`PlantSelectorArc.swift:662`、弧を回して名前が頂点を通るたびの `UISelectionFeedbackGenerator`。ほかの操作（シャッター・種類の切り替え・削除・リセット・セグメント・写真の列）はすべて無音。

最低ターゲットは iOS 18 / Swift 6 なので、`.sensoryFeedback` も Core Haptics も使える。

### 決めたこと

**2つの層に分ける。**

- 操作の触覚（標準の語彙）＝ 機械がこちらの操作を受け取ったこと
- 植物の触覚（Core Haptics のカスタム）＝ その子が居ること、どんな状態か

混ぜると、押した手応えが生き物の気配に化ける。逆に出会いに標準の `success` を使うと「登録という作業が完了した」音になり、D9（登録を出会いに溶かす）と噛み合わない。

**`error` と `success` は使わない。**このアプリに「ユーザーの失敗」は無い（原則3 / D24）し、嬉しいことが起きるのは植物の側なので、返すのは植物の触覚になる。

**「鳴らさない場所」も表に書いた。**書いていないと、後から誰かが鳴らす。全画面の写真、グラフの送り、日記の保存、上限で押せなくなったボタン、タブの切り替えは鳴らさない。

### 途中で判断を変えたところ

はじめは「はじめまして」の吹き出しで `meet`（迎え入れ）を鳴らすつもりだったが、**名前の確定に移した。**フローを追うと「話しかける」→「はじめまして」→名前の入力→確定が数秒のうちに起きる。ここで `meet` を2回鳴らすと、どちらが成立なのか分からなくなる。**迎え入れが成立するのは名前をつけた瞬間**なので、「はじめまして」は `pulse`（居る）に留める。

シャッターも、押した瞬間に鳴らす案から**「押した（`tap`）」と「撮れた（`snap`）」の2つに分けた。**`captureHighResolutionFrame` は間があるので、押した瞬間に撮影の音を鳴らすと嘘になる。間が短ければ段階3で片方を落とす。

モックの水分スライダーは鳴らさないことにした。動かすたびに帯域をまたぐので、`thirst` と `drink` が交互に鳴る。

### 見つけた直しどころ

`PlantSelectorArc.swift:662` は刻むたびに生成器を作り直していて、`prepare()` も呼んでいない。回し始めに1つ持ち、離したら手放す形に直す（段階1に入れた）。

### 決定として残した

D48。2つの層、`error` と `success` を使わないこと、鳴らさない場所を決めること、迎え入れの合図を名前の確定に置くこと、削除に成功を鳴らさないこと。

## 追記 — 段階1（操作の触覚）を実装した

「まずは1で」。標準の語彙だけを入れた。植物の触覚（Core Haptics）は段階2のまま。

### 入れたもの

`Sources/Support/Haptics.swift` を作り、**鳴らし方を1か所に閉じた。**呼ぶ側は `Haptics.tap()` とだけ書き、どの生成器をどう使うかは知らない。散らばると、設計の表（haptics.md §5）と実物が合っているかを確かめられなくなる。

状態の変化がそのまま契機になるところは SwiftUI 側で受けた（`SensoryFeedback` の拡張に同じ語を生やしてあるので、`.sensoryFeedback(.tick, trigger: page)` と書ける）。非同期の完了や条件付きの発火は `Haptics` から直接鳴らす。

| 画面 | 入れたところ |
|---|---|
| カメラ | パネルの検出、シャッター（押した `tap` / 撮れた `snap` / 上限・失敗 `caution`）、種類の切り替え、迎える1枚の確認、撮り直す・話しかける、説明員パネルの長押しとリセット |
| 弧 | 開いた、刻み（直し）、離して決まった、ガジェットによる自動選択 |
| マイプラント | 記録・育成・ギャラリーの切り替え、この子を観察する、削除、アイコンの切り抜きの決定、育成の時間幅 |
| 日記 | お休みの展開・畳み、写真を足した |
| ギャラリー | 見ている1枚が変わった（全画面では鳴らさない） |
| プロフィール | センサーの接続・失敗、リセット |

### 生成器の持ち方を直した

弧は刻むたびに `UISelectionFeedbackGenerator` を作り直していて、`prepare()` も呼んでいなかった。`Haptics.Ticker` を回し始めに1つ作り、離したら手放す形にした。ほかの語も生成器を持ち回し、鳴らしたあと次の `prepare()` を掛けてある。

### 計画から変えたところ

**列の写真のタップも刻むことにした。**計画では「`tick` が2回鳴るのを避けるため鳴らさない」としていたが、実装してみるとタップそのものには手応えを付けないので、2回にはならない。指の下の写真がメインになって列がそれを中央へ運ぶ——なぞったときと起きていることは同じなので、鳴らさない理由がなくなった。haptics.md §5.4 の理由を書き換えた。

**株の削除は暫定で `thud`。**段階1に植物の触覚が無いので、`farewell` の落とし先（非対応端末と同じ扱い）を先に使っている。段階2で差し替える。

育成の時間幅は、はじめ「同じ幅を選び直したら何もしない」と書いたが、**右端を最新の点に戻す既存の動きまで止めてしまう**ので、鳴らす条件だけに絞った。

### 確認したこと

`xcodegen generate` でファイルを取り込み直し、シミュレータで `clean build` が通ることを確認した。**触覚そのものはシミュレータでは鳴らないので、確かめられていない。**

## 追記 — 段階2（植物の触覚）を実装した

Core Haptics でパターンを組み、カメラに繋いだ。

### 入れたもの

`Haptics.plant(.pulse)` で鳴らす。エンジンと6つのパターンは `Haptics.swift` に足した——**帯域の定義と手触りを離さない**ため、`.ahap` のファイルにはしていない。

| 語 | 組み方 | 契機 |
|---|---|---|
| `pulse` | 弱い2連（2発目は弱く、近い） | 株を検出した瞬間。迎えている最中でも同じ |
| `meet` | 0.35秒ふくらんで、最後に締める | **名前が決まった瞬間**（D48） |
| `thirst` | 硬い（sharpness 0.9）2連。弱い | 帯域が `thirsty` / `critical` に入った |
| `drink` | 0.6秒、弱→強→ほどける | 帯域が `watered` に入った |
| `unease` | 0.5秒、強さを小刻みに揺らす | 帯域が `overwatered` に入った |
| `farewell` | 0.9秒かけて静かに落ちる | 株の削除 |

**帯域の触覚は、セリフが差し替わるところで鳴らす。**触覚はセリフの伴奏なので、`refreshLine` の中に置いた。`comfortable` と `drying` には何も返さない。

### 計画から変えたところ

**モックの「水をあげる」では、ボタンで鳴らさないことにした。**水をやると帯域が `watered` に変わり、セリフと一緒に `drink` が返る。押した瞬間にも鳴らすと二重になる。結果は同じで、鳴る場所が1つになる。

**水分スライダーは `refreshLine(force:silent:)` で抑えた。**帯域の変化を契機にしたので、放っておくとスライダーを動かすたびに渇きと水を得た手応えが交互に鳴る。

**`farewell` の繋ぎ先は、株の削除だけになった。**計画では「枯死に至った」も挙げていたが、`Metrics.currentStage` は「最後の観察が `withered` なら `withered`」と定めていて、**アプリは観察を記録するときにいまの段階をそのまま書き戻す。**セッションの中で生きている株が枯れる経路が無い。看取りの瞬間を作るなら、段階の進みかたを決めるところからになる。haptics.md にそう書いた。

### エンジンの扱い

- `playsHapticsOnly = true`。ARKit のカメラセッションと音声を取り合わせない
- `isAutoShutdownEnabled = true` で寝かせ、`stoppedHandler` で止まったことを覚えて次に起こし直す
- **カメラを開いたときだけ温める**（`Haptics.prepare()`）。植物の触覚が鳴るのはほぼこの画面で、最初の1つは「見つけた瞬間」になる。寝たまま迎えると、いちばん効かせたい1発が遅れる
- 対応していない端末・起こせなかったときは標準の語彙に落とす。**無音にはしない**

### 詰まった点

`Haptics` は `@MainActor` だが、**入れ子の型はそれを継ぐわけではない。**`Note` の拡張に書いた落とし先（`fallback()`）が非分離のままになり、`Haptics.snap()` を呼べずにビルドが落ちた。`@MainActor` を明示して解決。
