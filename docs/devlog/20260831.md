## 見つけた問題と原因

### 1. 何もないのに吹き出しが出る — 設計の穴

`VNGenerateForegroundInstanceMaskRequest` は「**主要被写体**」の位置を返すだけで、**それが植物かどうかを一切見ていない。**机でも壁の角でも人でも、前景と背景が分離できれば何かを返す。

コードのコメントには「鉢植えのように画面の主役が1つだけある場面で最も安定する」と書いていたが、**「植物である」ことを確かめる処理を入れ忘れていた。**前景マスクの役割を取り違えていた——あれは位置を求める道具であって、種類を判定する道具ではない。

**修正**: `VNClassifyImageRequest` を挟み、2段構えにした。

```
1. 分類で「植物が写っているか」を判定する
2. 前景マスクで「どこにあるか」を求める
```

植物を表すラベル（`plant` `flower` `leaf` `foliage` `sunflower` など20語）の確度を合計し、しきい値を超えたときだけアンカーを打つ。あわせて、画面に占める面積が小さすぎる被写体も弾く。

### 2. アプリを開いた瞬間に吹き出しが出る

原因が2つ重なっていた。

- `lastDetectionAt` の初期値が0のため、**最初のフレームで検出が走る**
- 上の問題により、必ず何かが見つかる

加えて、**トラッキングが初期化中でもアンカーを打っていた。**この時点の位置は信用できず、吹き出しが飛ぶ原因にもなる。

**修正**: トラッキングが正常になるまで検出しないようにした。

### 3. 吹き出しがぶれる

毎フレーム素直に投影しており、ARKit の姿勢推定の微細な揺れがそのまま出ていた。

**修正**: 画面座標を平滑化した。

## 追記 — 弧の形を参考画像の比率に合わせた

「もう少し円を出してほしい」という指摘に対し、**感覚で動かさず、参考画像から比率を測って合わせた。**

| | 出っ張り | 縦半分 | 比 |
|---|---|---|---|
| 参考画像（iPhone のズーム） | 363px | 577px | **0.63** |
| 修正前 | 68pt | 161pt | 0.42 |
| 修正後 | 96pt | 152pt | **0.63** |

**形は「出っ張り ÷ 縦半分」の比で決まる**と分かったのが収穫。半径は弧全体の大きさを、中心の位置は深さを決める。この2つを分けて考えられるようになったので、次に「もっと浅く」と言われても迷わない。

それまでは半径と中心を一緒に動かしていて、大きさと深さが混ざっていた。**比を見つけたことで、調整が推測から計算になった。**

## 追記 — 素材に opacity を掛けて追従を殺していた

「バーの色が背景で変わらない」という指摘。原因は**濃さの調整に `.opacity()` を使ったこと**だった。

素材（`ultraThinMaterial`）は背後の映像を取り込んでぼかす仕組みだが、`.opacity()` を掛けると別レイヤーとして合成され、**背後の取り込みが切れる。**濃さを整えたつもりで、素材である意味を消していた。

**「薄くしたい」を opacity で解こうとしたのが短絡だった。**

ただし opacity を外しても追従しなかった。**本当の原因は、SwiftUI の素材が ARKit の Metal 描画を取り込めないこと。**「普通にタブと同じものを使いまわせばいい」という提案どおり、タブバーの実体である `UIVisualEffectView` を直接置いて解決した。

**素材を使っていることで満足して、実際に追従しているか確かめていなかった。**シミュレータではカメラが動かないので、この種の不具合は実機からの報告でしか分からない。

指摘そのものは「選択中のタブの色を使っているのでは」という推測だったが、**観察（追従していない）が正しかった。**現象の報告は、原因の推測が違っていても価値がある。

## 追記 — 「迎える」の流れを最後まで繋いだ

前のコミット（`c1fca49`）で「シャッターを切り替えて、撮ってから植物を迎える」を実装したつもりだったが、**確認の画面が一度も出ない状態だった。**

`PlantConfirmView` は書いてあり、`pendingCapture` に撮った1枚も入っていた。**入れたあと、それを画面に出すコードだけが無かった。**部品を作り、状態も持たせ、繋ぐ最後の一行を忘れていた。

```
撮る → pendingCapture に入る → （誰も見ていない） → 何も起きない
```

シミュレータでは ARKit が動かず「実機で確認してください」の画面になるため、**ビルドが通っただけで確認を終えていた。**AR が絡む機能はビルドの成否では何も分からない、という 20260831 の他の項目と同じ落とし穴に、もう一度落ちた。

### 直した内容

| # | 直したこと |
|---|---|
| 1 | `PlantConfirmView` を `ZStack` に置いた。**弧より上に重ねる**——確認中は他に触れる先を作らない |
| 2 | 「撮り直す」を繋いだ（前は `onRetake` の受け手が無かった） |

### 3 — 確認の裏で相手が決まってしまう

止めないと、静止画を見ているあいだも映像の側の検出が回り続ける。確かめている裏で `subject` が `.plant` になり、戻った瞬間には**自分が選んだのとは別の相手**に話しかけていることになる。

**セッションごと止めるのではなく、検出だけ止めた。**`pause()` すると復帰に時間がかかり、確認から戻ったときに画面が固まって見える。

### 4 — 検出し直すと手応えが消える

はじめは「話しかける」で `redetect()` を呼び、映像から改めて見つけさせるつもりだった。だが**同じ植物でも見つかるまでに数百ミリ秒から数秒かかる。**押してから何も起きない間があると、押した手応えが消える。

そもそも**確かめたのはこの子だ、という判断はもう済んでいる。**それを捨ててやり直す理由がない。`adoptPlant(atNormalizedBox:)` を足し、確認で決まった枠の位置にその場でアンカーを打つようにした。押した瞬間に吹き出しが出る。

枠が取れていなかったときは画面の中ほどに置く。見つけられなかったことを理由に断らない（原則3）。

### 5 — 滑らせる的が 130pt しかなかった

シャッターの切り替えは、ボタンの上でしか滑らせられなかった。2つ並べて 134pt。「左右にスライドして選ぶ」と書いておきながら、**その的が画面幅の3分の1しかない。**下端のどこを滑らせても効くようにした。

### 判断

**D40 として決定に残した。**D9（検出したその場で名前をつける）を差し替えるのではなく、入口を1つ増やす拡張という位置づけ。専用の登録画面を作らない方針は変えていない。

1株目と2株目以降で入口を分けるのは、**周りに知っている子がいるかどうか**が違うため。1株目は「まだ誰もいない」ので、カメラが見つけた相手＝迎える相手で迷いがない。2株目以降は向けただけで話しかけられると、どの子を迎えたのか本人にも分からない。

### 学び

**「実装した」と「動く」の間に、繋ぐという工程がある。**部品が揃っていることと、それが呼ばれていることは別。今回は状態まで持たせていたぶん、書いた本人ほど「出来ている」と錯覚しやすかった。

## 追記 — 確認の操作がタブバーに乗っていた／＋の作り直し

実機からの指摘2件。

### 1. 「話しかける」がタブバーに重なる

`PlantConfirmView` を呼ぶ側で `.ignoresSafeArea()` を掛けていた。**写真を全面に出すつもりで、操作まで一緒に安全領域の外へ出していた。**下端に置いた「撮り直す」「話しかける」が、そのままタブバーの上に乗った。

**写真だけを外へ出すように分けた。**`photo` を切り出してそこにだけ `.ignoresSafeArea()` を掛け、キャプションとボタンは安全領域の内側に残す。

```
（前）PlantConfirmView 全体 → 安全領域の外  → ボタンがタブに乗る
（後）写真だけ            → 安全領域の外  → 全面のまま
     キャプションとボタン  → 安全領域の内側 → タブの上に出ない
```

**`.ignoresSafeArea()` は「この画面は全面だ」の意味で掛けがちだが、実際は「触る場所も外に出す」と言っている。**背景と操作は分けて考える。

### 2. ＋が揺れる／黒く乗って見える

**揺れの原因は、記号の大きさをボタンの大きさに比例させていたこと。**

```swift
.font(.system(size: size * 0.34, weight: .bold))   // 42→72pt で 14.3→24.5pt
```

大きさが変わるたびに**字が組み直される。**位置や大きさの変化（`offset` `frame`）は連続した値として滑らかに動くが、フォントの指定は各フレームで別の字として描き直されるため、切り替えのあいだガタつく。

**記号は選択によらず 18pt に固定した。**大きさが変わるのは円だけになり、＋はその中で静止している。

大きさは実際に描いて決めた。ImageRenderer で 15/17/19/21pt を並べて見比べ、**小さいほうの白丸（直径32pt）を潰さず、大きいほうで埋もれない**ところを取った。19pt は小さいときに窮屈で、15pt は大きいときに見失う。

| | 15pt | 18pt | 21pt |
|---|---|---|---|
| 小（白丸32pt） | 余裕あり | 収まる | 窮屈 |
| 大（白丸58pt） | 埋もれる | 読める | 良い |

**塗るのをやめて、くり抜いた。**黒で描くと白丸の上に点が乗っているように見える。`blendMode(.destinationOut)` と `compositingGroup()` で＋の形に穴を開け、向けている先がそこに透けるようにした。

`compositingGroup()` が要る。付けないと、重なりの外まで抜けてしまう。

### 検証の仕方

**ARKit はシミュレータで動かず、シャッターは AR が使える分岐の中にある。**つまりシミュレータでは一度も描かれない。実機に入れるまで見られないかというとそうではなく、`ShutterBar` は SwiftUI だけで出来ているので、**macOS 上で `ImageRenderer` に描かせて PNG で確認できた。**

くり抜きが効いているか（背景が透けるか）は、模様のある背景の上に置けば一目で分かる。**AR が絡む機能でも、AR に依存しない部分は切り離して見られる。**

## 追記 — 頂点にアイコンを固定した

指摘は2段階で入った。

1. 「選択中の植物のアイコンを、円のトップに来ているときだけ出す」
2. **訂正:「トップに来ている植物のアイコンを出す。位置は円の外側に固定」**

### 何を示す印なのかが変わった

最初の理解では、**アイコンは「いま効いているもの」の印**だった。回している最中に元の位置へ戻るための目印という位置づけ。

訂正後は、**アイコンは「頂点そのもの」の印**になる。頂点に何が来ているかを、名前とは別に見せる。

```
（前）開いている ∧ 頂点にある ∧ それがいま効いている株
（後）開いている ∧ 頂点にある
```

**条件が1つ減って、印の意味が反転した。**前者は「戻る場所」、後者は「いま見ている場所」。同じ見た目でも役割が違う。

### 位置固定が要点だった

はじめ名前に `.overlay` で付けていたので、**名前の長さでアイコンの位置が動いていた。**「そら」なら手前、「こもれび」なら奥。

`.position(x: apexX + 32, y: centerY)` で弧の縁から一定の距離に固定した。**場所が動かないからこそ、名前のほうが回っていることが分かる。**動く印は印にならない。

なお `HStack` で横に並べた最初の形は、**アイコンが出入りするたびに名前が左右に飛んだ。**`.position()` は中身の中心を置くので、幅が変われば中身がずれる。位置固定にしたことで、この問題も一緒に消えた。

### 出入りにだけアニメーションを掛けた

回転そのものは指に付けたいので、`wheelAngle` は一切アニメーションさせない。だがそのままだと頂点の印が点滅して見えるので、**`highlightIndex` の値にだけ** `.animation(_:value:)` を掛けた。同じビューの中で、追従させたいものと馴染ませたいものを分けている。

## 追記 — 選択の印をタブバーの動きに揃えた（D41-a）

「サイドバーのUIを下のタブと同じにしたい」という依頼を、**最初は見た目（形・素材）の話だと読み違えた。**シャボン玉のような浮かぶ玉を試作までしたが、指していたのは**タブバーが選択を切り替えるときの動き**だった。

### まず、その動きを実際に捉えた

シミュレータはタップできない（`osascript` に補助アクセスが無かった）ので、**同じタブ構成の確認用アプリを scratchpad に作り、時間で選択を動かして録画した。**製品コードは触っていない。

`ffmpeg` でタブバーの帯だけを切り出し、コマ送りにして分かったこと。

| # | 起きること |
|---|---|
| 1 | 印は分裂せず、**1つの塊のまま伸びて移る** |
| 2 | 伸びている間は**両端を包む長円**になる |
| 3 | **色はフェードではない。**塊の縁を境に切り替わる |
| 4 | およそ 0.4秒 |

**3 が正体だった。**「日記」の本のアイコンが**左半分だけ青く、右半分は黒**のコマがある。膜が通り過ぎた場所だけ色が変わる。言葉で「シャボン玉のような」と言われたものの中身が、これで確定した。

**推測で作らず、録って見た**のがよかった。浮かぶ玉の試作は完全な空振りで、あのまま実装していたら方向ごと外していた。

### 動くものが逆だった

| | タブバー | 弧 |
|---|---|---|
| 動くもの | **印** | **名前** |
| 止まっているもの | 項目 | 印（頂点） |

**そのままは写せない。**「A から B へ印が旅する」を、「頂点の印が伸び縮みする」に置き換えた。頂点にある名前が頂点から離れているぶんだけ伸びるので、半分まで来たところで最も長くなり、出ていく名前と入ってくる名前の両方をまたぐ。

対称に伸ばす形と、「頂点の名前から隣へ向かって伸ばす」形の2通りを計算してみたが、**数値がほぼ一致した**（高さ 44.6 と 44.5）。角度が小さいうちは sin がほぼ線形なので、どちらでも同じものになる。単純なほうを取った。

### 色を切り替える仕掛け

名前を**2枚重ねる。**下地（白）を塊の形で抜き、アクセント色を塊の形だけ出す。

```
下地（白）      … 塊の形を punch out
アクセント色    … 塊の形で mask
```

**抜くのが要点。**下地を残したまま上に色を重ねると、アクセント色の不透明度ぶん白が透けて濁る。`blendMode(.destinationOut)` ＋ `compositingGroup()` で抜いた。

塊の幅は名前の実寸に合わせる必要があるので、`onGeometryChange` で各名前の大きさを測って覚えている。短い名前に長い塊が付くと、何を指しているのか分からなくなる。

### 確かめ方

止まっている状態と、回転の途中（4分の1・半分）と、**塊の縁がちょうど名前を横切る角度**を描き分けた。半分のところで「そら」と「こもれび」の両方が青くなり、縁が横切る角度では「こもれび」が**途中まで青く、残りが白い。**狙った動きになっている。

## 追記 — 手描きをやめ、タブバーと同じ材料を使った

「シャボン玉みたいになってませんね」「サイドバーはタブと同じCSSを再利用できないのですか」

**もっともな指摘だった。**私が書いていたのは `Capsule().fill(.white.opacity(0.22))` ——ただの半透明の白。屈折も、縁の光沢も、融合も無い。**タブバーの見た目を目で見て手で真似ようとしていた。**

### 答え

**タブバーそのものは再利用できない。**CSS のようなスタイルシートは無く、あの見た目は `UITabBar` の非公開実装。iPhone に縦置きのタブバーAPIも無い。

**だが、材料は公開されている。**

| API | 何をするか |
|---|---|
| `glassEffect(_:in:)` | ガラスの材質。屈折・縁の光沢を含む |
| `GlassEffectContainer` | 近づいたガラス同士が融合して伸びる |
| `glassEffectID(_:in:)` | 位置が変わると塊が伸びて移る |

SDK にあることを型チェックで確かめてから差し替えた。**「無いから真似る」と「あるのに知らずに真似る」は別物で、後者だった。**

### 器に入れたら名前が消えた

`GlassEffectContainer` に入れたところ、**塊の中の名前が白く飛んだ。**

原因は Z 順。器はガラスを**別の層に持ち上げる**ので、同じ `ZStack` で「ガラスより後（＝上）」に置いたはずの名前が、ガラスの**下**になる。名前がガラス越しになって滲んでいた。

器が要るのは**複数のガラスを融合させるとき**だけ。印はひとつしかないので外した。外した瞬間、名前がくっきり出た。

**「関連する API だから一緒に使う」で入れたのが間違い。**それぞれが何をするものかを見ていなかった。

### 着色も間違いだった

塊に `.tint(accentColor.opacity(0.18))` を入れていたが、**中身の名前も同じアクセント色**なので、青の上に青で読めなかった。

タブバーを見返すと、**選択中の塊は無彩色**で、色が付いているのは中身のアイコンとラベルだけ。**色の役割が塊と中身で分かれている。**録画を見ていたのに、この分担を見落としていた。

### 確かめ方

シミュレータでは弧が AR の分岐の外にあるので描かれるが、**閉じているうえに座標が取れずタップできない。**そこで、**本物の `PlantSelectorArc.swift` を機械的に3箇所だけ変えて（import 削除・開いた状態・回転量）iOS の確認用アプリに載せ**、シミュレータで撮った。ガラスは実機の描画系が要るので、macOS の `ImageRenderer` では出ない。**iOS の実機描画に載せる必要がある**と分かったのが今回の収穫。

### 残っている確認

**ガラスが AR の映像を取り込むかは、まだ実機でしか分からない。**`c85d9a7`〜`7cbf8dd` で潰れたのは `UIVisualEffectView` と SwiftUI の Material で、Liquid Glass は別実装なので、同じとは限らない。

## 追記 — 名前を弧に収め、アイコンの出入りの向きを直した

### 1. 名前がはみ出していた

**名前は半径に沿って寝ているので、はみ出すかどうかは半径で決まる。**名前の中心を半径 147 に置き、弧の縁が 169 だったので、**幅 44 を超える名前はすべて外へ出ていた。**ほぼ全部の名前が該当する。

使える範囲を角度から出すようにした。

```
外側 … 弧の縁（169）から 6 内側
内側 … 画面の左端。円の中心が画面の外（x = −73）にあるので、
        角度が開くほど遠のく：73 / cos(角度)
```

| 角度 | 使える幅 |
|---|---|
| 0° | 84 |
| 16° | 81 |
| 32° | 71 |
| 48° | 60 |

**端の名前ほど短くなるのは、弧の形からの帰結**であって、恣意的な値ではない。名前の中心もこの範囲の真ん中に置くようにしたので、147 固定をやめた。

### 測る対象を間違えると振動する

「収まらなければ切る」を素直に書くと**壊れる。**

```
切っていない幅を測る → 収まらない → 切る → 幅が縮む
→ 収まる → 切るのをやめる → 幅が戻る → 収まらない → …
```

見えているほうを測ると、この輪をぐるぐる回って毎フレーム点滅する。**切っていない控えを隠して置き、そちらを測る**ようにした。控えは常に `fixedSize` なので値が動かない。

**測った値がレイアウトに戻る仕組みでは、「測る対象」と「変わる対象」を分けないと閉じない。**

### 2. アイコンが画面の中央から出入りしていた

原因は**修飾子の順序**だった。

```swift
.position(x: ..., y: ...)
.transition(.scale(scale: 0.5))   // ← position より外側
```

`.position` は**画面いっぱいに広がる器**を作って、その中に中身を置く。`.transition` をその外側に付けると、**変形するのは器のほう。**器の中心＝画面の中央を起点に拡大縮小するので、アイコンが画面中央から飛んでくるように見えていた。

`.transition` を `.position` より内側に移し、向きも円の中心の側（左）へのずれに変えた。

**「どのビューに掛かっているか」を、位置を決める器と中身とで取り違えていた。**同じ現象は `.animation` でも起きるので、位置決めの器の外側に見た目の修飾子を置かない、という形で覚えておく。
