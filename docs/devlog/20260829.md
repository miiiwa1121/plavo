### 1. 要件の矛盾を発見（D4-a）

「requirementsは詰め切ったのか」という問いを受けて見直したところ、**D4 と D25 が衝突していた。**

> **D4**: 植物を検出したら自動で1回。**以降はキャッシュ**。シャッターは持たない

### 3. アーキテクチャで決めたこと

**4層に分けた。**

| 層 | 責務 |
|---|---|
| UI Layer | SwiftUI、5タブ |
| Perception Layer | Vision（検出）/ ARKit（6DoF追従）/ RealityKit（描画） |
| Domain Layer | **UIにもARにも永続化にも依存しない純粋なロジック。このプロダクトの本体** |
| Persistence Layer | SwiftData + CloudKit + ファイルストア |

**データフローで最も重要なのは、事前定義の一言（「はにゃ？」）を診断より先に出すこと。**診断は5〜15秒かかるが、その間ユーザーは無反応の画面を見ない（D27）。順序が体験を決めている。

**保存先の使い分け**: 構造化データは SwiftData（CloudKit同期）、撮影画像はファイルシステム。数ヶ月分の画像をレコードに埋めると肥大するため。

### 4. ドメインモデルで決めたこと

#### 生育ステージの後戻りを許さない

**AIが返す `stage` はブレる。**同じ株を撮っても、光の当たり方や角度で「本葉」と「つぼみ」を行き来しうる。そのまま記録すると成長の履歴がのこぎり状になり、追悼ムービーの構成が破綻する。

したがって**個体の生育ステージ = 観察履歴における最大到達ステージ**とした。例外は `withered`（枯死）のみ。

これは要件になかった論点で、設計時に洗い出した。

#### currentStage も親密度も死因も保存しない

D23の原則を徹底した結果、Plant エンティティは驚くほど痩せた。`currentStage` すら持たない——Observation の履歴から導出する。

保存するのは以下だけ。

| 分類 | 内容 |
|---|---|
| 一次データ | 撮影画像、センサーの生値 |
| 観測 | AIが画像から読み取ったこと |
| 生成物 | セリフ、ユーザーが書いた日記 |

#### 導出指標を11個の純粋関数として定義

DLI / GDD / VPD / 開花予測 / 水やり予測 / 前回水やりからの経過 / 成長速度 / 元気さ / 画像と数値の食い違い / 親密度 / 死因。

すべて一次データから計算し、セリフ生成時にClaudeへ渡す文脈になるが**画面には出さない**（原則2）。

## 気づいたこと

**原則2（情報を情報として出さない）が、そのままデータモデルの設計指針になっている。**

当初これはUIの方針だと思っていた。「開花予測日を表示しない」という表示上の話だと。しかしD23で「再計算できるものは保存しない」と決めたことで、**表示しないものは保存もしない**という一貫した構造になった。

結果として、データモデルが非常に小さくなった。エンティティは5つ（Plant / Observation / SensorReading / DiaryEntry / Memorial）だけで、そのうち Plant はほとんど属性を持たない。**このプロダクトの複雑さは、データではなく関数の側にある。**

## 詰まった点

**Plant に `currentStage` を持たせるかで迷った。**

持たせたほうがクエリは速いし、実装も素直になる。しかしAIのブレで値が行き来する問題があり、「最大到達ステージ」という規則を入れるなら、それは導出であって保存すべきではないと判断した。パフォーマンスが問題になったら、キャッシュとして持つことは後から検討できる。

### 1. D4-a の補正

ユーザーから頻度についての補足があり、D4-a を修正した。

#### 新しい決定 — 一人称代名詞を使わない（D31）

書きながら導出された判断。**D5で声を当てないと決めたのは、声が人格を固定するからだった。一人称代名詞もまったく同じ働きをする。**「ぼく」と言った瞬間、その植物は少年になる。ユーザーが自分の植物に抱いていたイメージが、アプリの選んだ代名詞に上書きされてしまう。

日本語は主語を省略できるので制約にならず、**むしろ省略したほうが自然で余韻が出る**。

```
ぼく、のどが渇いたよ  →  のどが渇いたよ
わたしは日なたが好き  →  日なたが恋しいなあ
おれ、もうだめかも    →  もう、だめかもしれない
```

D31 として decisions.md に記録した。決定は40件になった。

#### システムプロンプトに栽培知識を厚く置く

ミニひまわりの生育段階・適正環境値・よくある症状をシステムプロンプトに詳しく書いた。狙いは2つ。

1. 診断精度が上がる
2. **プロンプトキャッシュの最小長（約1024トークン）を超える**

キャッシュが効けば、システムプロンプト分の入力コストが約1/10になる。精度とコストの両方に効く一石二鳥の構成になった。

#### コスト試算

| 条件 | 1回あたり |
|---|---|
| キャッシュなし | 約4.9円 |
| キャッシュ利用 | 約4.2円 |

D4-aのスロットルにより1日20回程度が上限なので、**1日あたり約100円**。ポートフォリオ用途では許容範囲だが無視できる額でもなく、配布する場合はレート制限が必須（N-4）。
