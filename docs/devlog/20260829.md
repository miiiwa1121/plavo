### 4. ドメインモデルで決めたこと

#### 生育ステージの後戻りを許さない

**AIが返す `stage` はブレる。**同じ株を撮っても、光の当たり方や角度で「本葉」と「つぼみ」を行き来しうる。そのまま記録すると成長の履歴がのこぎり状になり、追悼ムービーの構成が破綻する。

したがって**個体の生育ステージ = 観察履歴における最大到達ステージ**とした。例外は `withered`（枯死）のみ。

これは要件になかった論点で、設計時に洗い出した。

#### currentStage も親密度も死因も保存しない

D23の原則を徹底した結果、Plant エンティティは驚くほど痩せた。`currentStage` すら持たない——Observation の履歴から導出する。

保存するのは以下だけ。

| 分類 | 内容 |

| 一次データ | 撮影画像、センサーの生値 |
| 観測 | AIが画像から読み取ったこと |
| 生成物 | セリフ、ユーザーが書いた日記 |

### 5. バグを2つ見つけて直した

**バグ1: 日付生成で分が60になる。**10分刻みを `hour += 10/60` で累積すると浮動小数の誤差で `0.99999...` になり、`Math.round(0.99999 * 60) = 60` から `T00:60:00` という不正な時刻を生んでいた。全時刻が Invalid Date になり、DLI が NaN になっていた。総分数で計算して正規化する形に直した。

**バグ2: 水やりの跳ね上がりが緩やかすぎた。**`recovered` シナリオで水やり後の上昇を10分かけて分散させていたため、急上昇の閾値（12ポイント）を超えず検出されなかった。実際の水やりは数分で土に染みるので、1ステップの跳ね上がりとして表現し直した。

**どちらもサンプルデータを実際に流して初めて分かった。**データを作るだけでなく、指標を計算して値を目で見る工程がなければ気づけなかった。

### 1. 「展示会中は植物の時系列を表現できない」

ユーザーからの指摘。植物は数分・数時間で変化しないので、**展示物が1つでは3つの価値（AR / 時系列 / AI）を同時に見せられない。**

そこで展示物とセクションを価値ごとに分ける構成になった（D33）。

| 価値 | 展示物 |
|---|---|
| ARで吹き出しが出る | 本物の植物 |
| 時系列で変わる | 時系列パネル数枚 |
| センサー値を翻訳する | 造花＋スポンジ＋水分センサー |

私が見落としていた制約だった。L-12で「記録を事前に仕込む」とは書いたが、**植物そのものが変化しない**という当たり前の事実まで詰めていなかった。

### 2. パネルとAI診断の相性が悪いことに気づいた

パネル構想に対して問題を洗い出したところ、3つ見つかった。

| 問題 | 内容 |
|---|---|
| AIが「これは写真だ」と言う | Claude vision は印刷物を高確率で見抜く。システムプロンプトが「見えたことを具体的に書け」と指示しているので、`appearances` に「印刷物のように見える」と書かれる恐れがある |
| 記録の汚染 | パネルを見るたび観察が積まれ、同日に発芽と開花が並ぶ |
| 生育段階の後戻り防止と衝突 | 開花パネル→発芽パネルの順に見ると、発芽の前で「開花」のままになる |

**パネルではAI診断を走らせず、その日の記録を再生する**ことで全部解決した。

### 3. 造花＋スポンジという発想

「土だと水やりが頻繁にできないので、造花をスポンジに刺す」というユーザーの提案。本質は**何度でもリセットできる**こと。土だと1日の展示で水浸しになる。

ここでも**画像を外せば問題が消える**ことに気づいた。セクション4の主題は「AIが数値を気持ちに翻訳する」ことなので、画像診断は不要。造花であることがむしろ「見た目に依存せず数値だけで反応している」証明として働く。

### 4. 完全オフライン化（D34）— この日いちばん大きな判断

ユーザーからの問い。

> AIは今回の状況においては、必要ないと考えています。
> 理由は、長く触っても数分だからです。
> 実際にアプリを使うユーザーは数ヶ月から数年を共にすることを前提にしていますが、今回は状況が違います。

**同意した。**AI生成の最大の利点は多様性——同じ状態で何度観察しても違う言い回しが出ること。これは数ヶ月使うユーザーには決定的だが、**数分しか触らない来場者には一切効かない。**利点が発揮されないまま、通信断・レイテンシ・失敗という代償だけを満額で払うことになる。

ただし言い方を1つ変えることを提案した。**「AIを使わない」ではなく「AIを実行時ではなく制作時に使う」。**

セリフを人が手で全部書くと量も質もばらつく。AIに大量生成させ、人が厳選して埋め込む。これなら当日は絶対に失敗せず、質は人が管理でき、**「AIが生成したセリフです」と正直に言える。**技術者に聞かれても「製品版ではリアルタイム生成、今日は会場の回線を考えて事前生成に切り替えました」と説明できる。

**構成が劇的に単純になった。**Claude API 不要、当日のプロキシ不要、APIキー管理不要、通信断リスクゼロ。

### 5. 作った資産の位置づけが変わった

`server/` は**当日の実行環境ではなく、セリフ制作の道具**になった。

| 資産 | 新しい役割 |
|---|---|
| 診断クライアント | セリフを大量生成するために使う |
| `rules.ts` | 生成したセリフを人が選ぶとき、規則違反を機械的に弾く |
| センサーのサンプルデータ | 生成の入力条件。展示の再生データとしても使う |
| 導出指標の計算 | そのまま必要 |

**無駄になったものはない。**`rules.ts` はむしろ価値が上がった。人が数十のセリフを目視でチェックするより、一人称代名詞や字数超過を機械が弾くほうが確実。

今日は「検証の目的は何か」と問われて目的を置き直し、さらに「AIは要らないのでは」と問われて実行環境から外した。**2回とも、作ったものの意味が変わっただけで、作ったもの自体は生き残っている。**抽象化とインターフェースの分離を先にやっておいたことが効いた。

### 6. ガジェットの担当が分かれた（D35）

ハードに詳しいメンバーが水分検知ガジェットを担当することになった。**役割分担が生まれた瞬間、インターフェースの定義が最重要になる。**作り始める前に契約を確定させないと、6週間後に噛み合わないものが2つ出来上がる。

`docs/design/gadget-interface.md`（151行）として切り出し、ハード担当にそのまま渡せる形にした。

**経路の設計で1つ判断があった。**「有線は可能？Wi-Fiは準備できない」という問いに対し、**ハード→PCは有線で可能だが、PC→スマホは有線にできない**（iOSアプリのUSB通信にはMFi認証などが必要）と回答した。

代わりに**スマホのテザリングでローカルネットワークを作る**構成を提案した。会場のWi-Fiは不要、追加機材はUSBケーブル1本のみ。

仕様で最も気を使ったのは**キャリブレーションの責任分界**。静電容量式センサーの生値は環境依存で、スポンジと土では特性がまったく違う。どちらが正規化するかを決めないと「相手がやると思っていた」になる。`raw` と `percent` の両方を送る形にし、正規化はハード側、生値はアプリ側の逃げ道として残した。

## 追記 — セリフのプールを作成（L-14）

APIキーは使わない方針が決まったため、**私が直接セリフを書いた。**展示で必要な量は数十本程度で、この規模ならスクリプト経由でAPIを叩くより直接書いたほうが早く、書きながら質を判断できる。

### 作ったもの

`content/` を新設し、セリフを3ファイルに分けた。

| ファイル | 本数 | 用途 |
|---|---|---|
| `greeting.json` | 10 | 検出直後の一言（セクション2・4） |
| `moisture.json` | 33 | 土壌水分の5帯域（セクション4） |
| `timeline.json` | 16 | 時系列パネル8枚分（セクション3） |
| **合計** | **59** | |

`server/` に配置しなかったのは、これがコードではなくコンテンツであり、最終的にiOSアプリが読むものだから。

### 検証結果

```
セリフ 59 本を検証します
規則違反: 0 件 / 重複: 0 件
平均 8.2字 / 最長 16字（上限40字）
```

**規則違反ゼロ。**一人称代名詞・計測値の露出・絵文字・責める表現・指示的表現、すべて検出されなかった。

### 検証器の見落としを1つ直した

初回の実行で重複が1件出た。`「……」` が水分の `critical` と時系列の `withered` の両方にあった。

**これはセリフの重複ではなく沈黙である。**むしろ「消耗すると言葉が減る」（D30 第1層）という設計が両方の状態で一貫して現れているということで、重複していて正しい。記号だけの行を重複判定から除外する例外を入れた。

**機械的な検査は、こういう「意味のある同一」を区別できない。**弾いた結果を人が見て、規則側を直すという往復が要る。

### 文字数について

平均8.2字、最長16字。上限の40字に対してかなり短い。

意図的にそうした。**AR吹き出しは視界の中の小さな面積で、しかも来場者は歩きながら読む。**長い文は読まれない。`「のどが渇いたよ」`のような短い一文のほうが、瞬間的に伝わる。

### 帯域ごとの調子を設計に紐づけた

各帯域に `intent` を書き、どの決定に基づくかを明示した。

| 帯域 | 調子 | 根拠 |
|---|---|---|
| 水やり直後 | 喜びと回復。責めない | D30 |
| 適正 | 落ち着いて機嫌がよい。要求しない | — |
| やや乾いた | 控えめ。確信がない調子で揺らがせる | D7 |
| 水不足 | はっきりした要求。苦しさが出る | — |
| 危険 | 切迫。言葉が短く、本数も減る | D30 第1層 |

**危険帯だけセリフの本数を減らした**（5本。他は6〜8本）。消耗して言葉数が減るという設計を、プールの規模そのものに反映させている。

### 植物種への依存を切り分けた

| ファイル | 種依存 |
|---|---|
| `greeting.json` | しない |
| `moisture.json` | **しない。**水分だけで決まるため |
| `timeline.json` | **する。**現在はミニひまわり前提 |

D17-a で植物の種類が未確定だが、**影響を受けるのは `timeline.json` だけ**と分かった。種が決まっても、59本のうち16本を書き直すだけで済む。
