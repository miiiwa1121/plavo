## 追記 — 何もしていなくても CPU を1コア使い切っていた（パラパラ導入から）

### 依頼

> パラパラの実装後辺りから画面が非常に重くなってしまいました。原因を探し出してください。

### 測ったこと

シミュレータ（iPhone 17）で各タブを開き、起動から8秒待ってから何も触らずに10秒間、アプリの CPU 使用率を取った。

| ビルド | 何もしていないときの CPU | 10秒余りで作られた `AppModel` |
|---|---|---|
| dd64a3d（パラパラ導入前） | 0.2〜0.9% | 2回 |
| a7adf06（パラパラ導入） | **約100%（どのタブでも）** | **103回** |
| 修正後 | 0.1〜0.7% | 1回 |

トーク（何も動かない画面）でも100%だったので、画面ではなくアプリ全体の問題と分かった。`sample` で取った呼び出し履歴では、メインスレッドの約85%が `PlavoApp.body` → `RootView.init()` → `AppModel.init()`（育成の記録の JSON 0.8MB の読み込みと、仕込みの株2つの組み立て）に使われていた。

### 原因

1. `RootView` が `@State private var model = AppModel()` で持っていた。**`@State` の初期値は、ビューが作り直されるたびに評価される。**SwiftUI が残すのは最初の1つだけで、2つ目からは作っては捨てていた（パラパラ導入前から2回作られていたのはこれ）
2. `RootView()` は `PlavoApp.body` の中で作られる。捨てられる `AppModel` の初期化で観察対象（`images` など）に触れるので、**`PlavoApp.body` が捨てた側の `PlantStore` を見張る**ことになる
3. パラパラ導入で、仕込みの株のパラパラの仮写真を**起動後に裏で1枚ずつ描いて `images` に入れる**ようにした（`seedFlipbook`）。捨てた側でもこの処理は走り、`images` を書き換える → `PlavoApp.body` が作り直される → `RootView()` → 新しい `AppModel` → またパラパラを裏で描く……の輪になった

実機ではカメラ（AR・検出・吹き出しの追従）がこの輪とメインスレッドを取り合うので、特に重く感じたはず。

### 確かめ方

パラパラ導入版を2通り直して、輪が止まるかを見た。

- 仮写真を裏で描かず、その場で描く → 止まる（2回）。**引き金はこれ**
- 裏で描くのはそのまま、`AppModel` を作る場所を `PlavoApp` に移す → 止まる（1回）。**根本はこれ**

### 直したこと

`AppModel` を `PlavoApp` の `@State` で1回だけ作り、`RootView` には渡すだけにした（`let model: AppModel`）。App の構造体は起動時に1回しか作られない。パラパラの仮写真を裏で描く作りはそのまま（起動を待たせないため）。

修正後、全タブで CPU が 1% 未満に戻り、パラパラのページも仮写真が描き上がることをシミュレータで確かめた。**実機のカメラでの体感はまだ確かめていない。**

### 次にやること

- 実機でカメラを開き、吹き出しの追従と撮影の重さが戻ったかを見る
- `CameraTab` の `@State private var scene = SceneController()` も同じ形（作り直しのたびに作って捨てる）。いまは作るのが軽いので輪にはならないが、重い処理を足すと同じことが起きる

## 追記 — 写真の1枚を追う画面で、下の列をなぞると固まっていた

### 依頼

> マイプラントの写真・パラパラの詳細画面、プロフィールの写真の詳細画面の下の列写真をスクロールするときの挙動が非常に重いです。原因を探し出してください。

### 測り方

シミュレータで、列を指でなぞるのと同じ経路（列の送り位置を動かし、中央に来た写真へメインを切り替える）を 800pt/秒で動かし、1秒あたりのフレーム数と、33ms を超えたフレームの数を取った。計測用のフックは複製にだけ入れ、作業ツリーには入れていない。

| | 写真（49枚） | パラパラ（26枚） | プロフィール（101枚） |
|---|---|---|---|
| a7adf06（今日のリファクタリング前） | 31.7 fps | 51.4 fps | 13.5 fps（33ms超 66回） |
| リファクタリング後 | **1.1 fps** | **2.8 fps** | **0.5 fps**（1コマに最長 3.0秒） |
| 修正後 | 59.0 fps（0回） | 57.9 fps（0回） | 58.3 fps（4回） |

写真が多い画面ほど遅いので、「1枚切り替えるたびに全写真ぶんの仕事をしている」形と見た。

### 原因

**メインの大きい写真を並べたページ形式の `TabView` が、1枚切り替わるたびに全ページの中身を作り直していた。**見ている1枚（`current`）が変わると列の画面全体が描き直され、`ForEach` の中身の書き方（その場のクロージャ）では、SwiftUI は全ページを作り直すしかない。ページごとに写真を開いていたので、1枚送るたびに全写真を開き直していた。

- リファクタリング前は、ページごとに `UIImage(data:)` を作っていた（JPEG の頭を読むだけでも、101枚ぶんで毎回数十ミリ秒）
- **リファクタリングで悪化させた。**元の写真を開き直さないよう、長辺 1600px に縮めて覚える `displayImage` に替えたが、覚える枚数を12枚にしていたため、全ページぶんを開くと毎回ほぼ全部が追い出され、**1枚送るたびに全写真を 1600px で開き直す**ことになった

要因を1つずつ外して測った（プロフィール・リファクタリング後）。

| 外したもの | 平均 fps |
|---|---|
| なし | 0.5 |
| メインの写真を出さない | 49.2 |
| メインの1ページを「写真が変わらない限り作り直さない」ビューにする | 31.9 |
| 親の画面が見ている写真を読まない | 0.5 |

メインの写真を外した状態を基準にすると、残りの3つはどれも33ms超のフレームが 8 → 1〜2回になる程度だった。

### 直したこと

- **`DisplayPhoto`**（新規）: 画面いっぱいに出す1枚。`.equatable()` を付けて使い、写真が変わらない限り作り直さない。ギャラリーのメイン・全画面（`PhotoViewer`）・直近の写真（`TodayPhotosView`）の3か所。全画面と直近の写真も同じ作りで、同じ問題を抱えていた
- **前後の写真を裏で開いておく**（`prefetchingNeighbors`）。送った先でその場で開くと、1枚ごとに引っかかる
- **列の小さい絵（200px）を、画面を開いたときに裏で開いておく。**プロフィールのグリッドは 400px で開いてあるが、列は 200px なので使えず、見えたときにその場で開いていた

見た目は変えていない（リファクタリング前の版と同じ場面の画面写真を並べて確かめた）。

### 判断を変えた点

リファクタリングでは「描き直しのたびに元の写真を開き直さない」ために縮めた絵を覚える形にしたが、**覚える枚数の上限と、ページ形式の `TabView` が全ページを作り直すことの組み合わせを見ていなかった。**画像の開き方だけでなく、何回開かれるかを測ってから入れるべきだった。
