# 開発ログ 2026-09-13

マイプラントの詳細を**記録・育成・ギャラリー**の3つに分けた日。育成では**原則2を初めて解禁した**（D43）。

## 何をしたか

| | 変更前 | 変更後 |
|---|---|---|
| 詳細の画面 | 情報／ギャラリー | **記録／育成／ギャラリー** |
| 「情報」の中の節「記録」 | 記録 | **観察の履歴**（画面名と重なるため） |
| 土壌水分 | いまの1点だけ持つ | **株ごとに推移を積む**（セッション内・500点まで） |

育成には、土壌水分の**いまの値・適正範囲との比較・推移の折れ線**を置いた。グラフは Swift Charts。

## 原則2と衝突した

依頼は「水分量グラフなどリアルタイムの育成サポート」。そのまま作ると、**3原則のひとつ「情報を情報として出さない」に真正面から反する。**マイプラントの冒頭にも「数値のダッシュボードにしない」と書いてある。

黙って作るのも、黙って翻訳した表現に置き換えるのも違うので、実装の前に確認した。答えは「**カメラ画面は言葉による育成のまま。このセクションでは情報を解禁する**」。

整理するとこうなる。原則2が守っていたのは**植物が話しかけてくる場面**で、育成は**人が自分から確かめに来る場所**。場面が違うので、境界を画面の入口で引けば原則は崩れない。これを D43 に書き、原則2を述べている3箇所（decisions / functional-requirements / screen-design §2.1）に例外として足した。

## 実装で決めたこと

### 推移は選択中の株に積む

センサーの値はどの株のものかを持っていない。**値がどの株のものかは選択中の株で決まる**（D39）ので、`updateMoisture` の中で選択中の株に積むようにした。

そのため**実センサーの受信で、株の解決と水分の更新の順番を入れ替えた。**元は「水分を更新 → ガジェットから株を決める」の順で、最初の1点が株の決まる前に来ると、誰の記録にもならない。

### `SensorReading` を使わなかった

PlavoCore には `SensorReading` があるが、光・気温・湿度・養分も必須で持つ。**実測されているのは土壌水分だけ。**残りを0で埋めて詰めると、`Metrics.dli` や `vpd` に渡したときに**もっともらしい誤った値**が出る。アプリ側に `MoistureSample`（時刻と値だけ）を置いた。

同じ理由で「次の水やりまで」の予測も今回は出していない。`Metrics.daysToNextWatering` 自体は水分しか見ないが、入力の型が `SensorReading` なので、使うには0埋めが要る。

### 見送った株の空状態

ひまり（見送った株）の育成を開くと、「**この子を観察すると**、土の湿りがここに届きます」と出ていた。観察できない株に先の話をしている。**枯れた株に現在進行形を使わない**という既存の決まり（§8-a）に合わせ、「土の記録は残っていません」だけにした。

## 追記 — 育成のグラフを増やす前の調査

育成に土壌水分以外（CO2・気温・湿度・光量・葉の数・草丈・EC・日長・土の温度・pH）も出すことになった。対象はひまり、刻みは10分。**仕様の確認が済むまで実装はしない。**

### 葉の数は画像で数えられるか

**数えられるが、±1〜2枚の推定になる。ひまわりは難しい部類。**

| 観点 | 分かったこと |
|---|---|
| 研究の到達点 | 真上から撮ったロゼット状の植物（シロイヌナズナ等）を照明を固定して撮ると、平均誤差0.72枚、ぴったり一致44%、±1枚以内83%（人同士の一致は約90%） |
| 限界 | 葉が1〜2ダースを超えると重なりが支配的になる。視点・照明・葉の形が変われば学習し直しが要る |
| 汎用のAI（視覚つき言語モデル） | 10個未満ならほぼ正確だが、個数が増えると誤差が伸び、30を超えると急に崩れる |
| Apple Vision | 葉を数える機能は無い。Core ML のモデルを自前で学習させる必要がある。ひまわりの葉の公開データセットは見つからなかった |
| ひまわりの数え方 | 公式の定義がある（Schneiter & Miller 1981）。**4cm以上の本葉を数え、子葉は数えない。下葉が落ちたら葉の跡を数える**。葉の跡は画像ではまず見えない |

茎に葉が互い違いに付くため、横からは重なり、上からは上の葉が下を隠す。**発芽〜本葉10枚ほどまでは現実的で、つぼみ以降は怪しい。**

### 確認待ちの論点

1. 葉の数の定義（いま付いている葉か、出た葉の累計か）
2. 登録したての株のグラフも10分刻みにそろえるか（展示の数分では点がほぼ増えない）
3. 毎日の計測を観察として持つと、記録の「観察の履歴」に78件並ぶ
4. 78日×10分（11,232点）の見せ方
5. ミニひまわりの葉の最大枚数は根拠が見つからなかった

## 追記 — 育成のグラフの仕様を確定した（D44）

上の論点に答えが出た。**実装はまだしていない。**決定は D44、画面は screen-design §4.5 に書いた。

| 論点 | 決まったこと |
|---|---|
| 葉の数 | **入れない。**ただし項目をあとから足せる構造にする |
| 登録したての株の刻み | 10分にそろえる。細かい変化はカメラ画面の会話が担う |
| 草丈の置き場所 | **観察ではなく、グラフ用の値の列に入れる**（観察の履歴に日付だけの行が並ぶのを避ける） |
| 見せ方 | 下端に「全体・1年・1ヶ月・1週間・1日・1時間」のバー。全グラフを一斉に切り替え、左右に送れる |
| データより長い幅 | 全体と同じ表示 |

### 項目を足しやすくするために

項目を**定義**（ID・単位・刻み・まとめ方・適正範囲）と**値の列**に分けた。画面は定義を読んで並べるので、項目を足すときは定義に1行・データに1列で済む。測れなかった点は `null`、定義に無い列は読み飛ばす。

### 自分で決めて、確認を取っていないこと

仕様を詰める途中で、こちらの判断で埋めたところがある。実装の前に見てもらう。

| 項目 | 決めたこと |
|---|---|
| まとめ方 | ボタン名ではなく**実際に表示する長さ**で決める。データより長い幅を全体と同じにするには、こうしないと短いデータが1点に潰れる |
| 日長の閾値 | 1,000 lux 以上の時間（室内照明を日中に数えないため） |
| 既定の幅 | 全体 |
| 値の無い項目 | 枠を出さない |
| 適正範囲を持つ項目 | 土壌水分・気温・湿度・EC・pH（6.0〜7.5 を足す） |

### 自分の説明が矛盾していた

「データより長い幅をどうするか」を聞いたとき、**冒頭で「1年と全体はほぼ同じ見え方になる」と書き、選択肢では「そのまま出すと右に寄った短い線になる」と書いていた。**この2つは両立しない。答えは「同じものが表示される状態でよい（そのまま出す）」だったので、言葉どおり**全体と同じ表示**として仕様にした。

## 追記 — 育成の10項目を実装した（D44）

仕様の確認が取れたので実装した。

| 場所 | 作ったもの |
|---|---|
| `server/src/fixtures/growth.ts` | ひまりの一生分の仮データの生成（`npm run gen:growth`）。10分刻み×79日、398KB |
| PlavoCore `MetricCatalog.swift` | 項目の定義。**項目を足すときはここに1行** |
| PlavoCore `MetricSeries.swift` | 値の列・まとめ方・日長・10分ごとの平均・ファイルの読み込み |
| PlavoApp `GrowthSection.swift` | 育成の画面。項目ごとの枠と、下端の幅のバー |

前回の `MoistureSample`（水分だけの型）と1株500点の上限は消した。

### 仮データを筋書きに合わせる

一番手間がかかったのは土壌水分。**時期によって乾き方がばらついた。**最初の式では、中盤は3日で42%までしか下がらず、60日目前後は毎回17%まで下がっていた。水の吸い上げを草丈に比例させていたので、小さいうちは乾かず、大きくなると乾きすぎる。

吸い上げの大きさへの依存を弱め（最小でも0.55倍）、水やり直前の値を全日並べて見ながら合わせた。

| | 水やり直前の土壌水分 |
|---|---|
| ふだん（3日に1回） | 26〜30%。適正範囲の下限（25%）の少し上 |
| 水切れのパネルの日 | 14%。前の水やりを5日前にし、暑い日を重ねた |
| 70日目以降 | 40%台。吸い上げが落ちて乾かない |

ECも最初は肥料が積み上がって2.3まで上がり、適正範囲を外れ続けた。肥料で上がる量を抑えて1.0〜1.8に収めた。

**気温は、開花のパネルの日に積算温度が958に届くよう、全体を同じ量だけずらした。**ずらす量は全日で同じなので、1日の上下の形は変わらない。

### テストが見つけたこと

水やりを2刻み（20分）かけて染みさせていたら、**既存の水やり検出が1回の水やりを2回と数えた。**検出は TypeScript 版と共通なので触らず、データを1刻みで染みる形にした。

筋書きとの一致（水切れの日の値、開花の日の積算温度、芽が出る前は草丈が無い）を `MetricSeriesTests` に入れた。PlavoCore のテストは19件から33件になった。

### 1時間の幅が開かなかった

最初は Swift Charts のスクロールに全期間の点を渡していた。1日と1時間の幅で**画面が真っ白のまま**になった。落ちてはおらず、描き終わるまでに時間がかかっていた。

| 幅 | 渡していた点 | 横幅（画面何枚ぶん） | 開くまで |
|---|---|---|---|
| 1ヶ月 | 79 | 2.6 | 約2秒 |
| 1週間 | 1,896 | 11 | 約3秒 |
| 1日 | 11,376 | 79 | 約6秒 |
| 1時間 | 11,376 | 1,896 | **20秒以上** |

点の数と横幅の両方で遅くなる。自動の目盛りも全期間ぶん作られていた。**見えている幅の前後1つ分の点と目盛りだけを渡し、送るたびに作り直す**ようにして、どの幅も約1.5秒になった。

送る操作そのものは Swift Charts のスクロールのまま使っている。自前のドラッグにすると、ページ送り（記録・ギャラリー）や縦スクロールと取り合いになるため。

縦軸は、見えている点だけで決めると送るたびに伸び縮みするので、全期間の値から決めて固定した。

## 追記 — マイプラント詳細の帯を外した（D45）

「タブバーとセグメンテッドコントロールの後ろにある枠を外し、日記と同じにしたい」という依頼。**まず枠の正体を画面で確かめてから**、実装に入った。

### 枠は2種類あった

| 枠 | 正体 |
|---|---|
| 時間幅のバーの後ろ | 自分で敷いた `.background(.bar)`。画面幅いっぱいの半透明の帯 |
| タブバーの後ろ | **ページ形式の `TabView` が安全領域の内側しか描かない**ため、中身がタブバーの手前でまっすぐ切れ、下が無地に見えていた |

後者は誰も敷いていない帯で、コードを読むだけでは見つからなかった。日記と撮り比べて分かった。

### 直し方

- `TabView` ごと画面の端まで広げ、上下の余白（ナビゲーションバー＋切り替え、タブバー）は各ページに足し直した
- 上の切り替えと時間幅のバーは、帯の代わりにタブバーと同じガラスで浮かせた（`floatingGlass()`）

### 上端で中身が時計と重なった

広げたら、**上にスクロールした中身がナビゲーションバーの題名や時計の文字とそのまま重なった。**日記ではナビゲーションバーが潜った中身をぼかしているが、ページ形式の `TabView` の中のスクロールには効かない。

iOS 26 の `safeAreaBar` を各ページに透明なバーとして置けばぼかしが効くかと試したが、**変わらなかった。**効くか確かめられない仕組みは残さず戻し、下に向かって透明になるぼかしを上端に自前で重ねた（`scrollEdgeFade`）。

### 確かめ方

一時的な UI テストで、一覧から「ひまり」をタップして詳細を開き、記録と育成をそれぞれ上へスクロールしたところ、ギャラリー、横に送って育成へ戻したところを撮った。

| 見たこと | 結果 |
|---|---|
| 下端 | 中身がタブバー・時間幅のバーの後ろまで流れる |
| 上端 | 潜った中身がぼけて消え、題名と時計が読める |
| 横に送る | 切り替えは上に固定され、選択だけが追従する |

UI テストとその設定は消した。

## 追記 — 時間幅のバーがタブバーに重なった

指摘を受けて測ると、時間幅のバーの下端が 795pt、タブバーの上端が 791pt で、**4pt 重なっていた。**本来は 779pt に来るはず。自分で撮ったスクリーンショットにも写っていたのに、中身が流れているかばかりを見ていて気づかなかった。

### 数値で測った

画面が見えずクリックできないので、UI テストから `XCUIElement.frame` を読み、アプリ側でも位置をファイルに書き出した。

| 測ったもの | 値 |
|---|---|
| ナビゲーションバーまでの余白（上） | 116pt |
| タブバーの余白（下） | 83pt |
| ページの中身の置かれ方 | **上下とも 16.33pt 下にずれていた** |

16.33pt は上下の余白の差の半分（16.5pt）とほぼ一致する。`TabView` がページの枠を安全領域の高さで作り、画面いっぱいに広げた中身をその上下中央に置いていると見ている。

### 回り道

| 試したこと | 結果 |
|---|---|
| `ZStack` が上下中央に寄せていると考え、外した | 変わらなかった |
| 広げるのをやめ、`scrollClipDisabled` で中身を枠の外まで描かせる | 位置は合ったが、`TabView` の切り取りは外れず帯が戻った |
| 広げたうえで、**ページの位置を測ってずれを余白で打ち消す** | 位置が合い、中身も端まで流れた |

式（差の半分）を決め打ちせず測ることにしたのは、仕組みを推測でしか説明できていないため。端末や OS が変わっても、測っていれば合う。

### ついでに見つかった不具合

横に送れるかを前後の画像の差で確かめたところ、**「全体」から「1時間」に切り替えた直後、グラフが空だった。**なぞるとデータの先頭（6/26 0:00）が出た。

スクロールできない「全体」から切り替えるとき、幅を変えたあとで位置を送っていたので、グラフは位置を受け取らずに先頭に居座っていた。**D44 の実装からあった不具合**で、あのときは「1日→1時間」しか試していなかった。

幅と位置を同じ更新で変え、幅が変わったらグラフを作り直すようにした。切り替えた直後に最新の1時間が出ることを確かめた。
