## 追記 — 発熱のレビューと、見た目を変えない範囲の手当て

### 依頼

> スマートフォンの発熱がすごいのですが、適切な処理ができているかレビューしてほしいです。

### 調べ方

シミュレータでは ARKit も Vision も動かないので、**カメラ周りはコードと API の性質からの指摘、それ以外は実測**で分けた。実測できたのは次の4点。

| 測ったこと | 結果 |
|---|---|
| 何もしていないときの CPU（全タブ） | 0.1〜1.0%。9/22 に直した「作り直しの輪」は再発していない |
| ムービーのページが解放されるか | **全画面に覆われても、別タブへ移っても解放されない**（`onDisappear` は届く） |
| 小さい絵の置き場 | 仕込みの101枚だけで 47.9MB。上限は 48MB で、来場者が数枚撮ると溢れる |
| 吹き出しの文字の実寸計測 | 1回 63〜215µs（シミュレータ。実機はこれより遅い）。毎フレーム走っていた |

### 見つかったこと（発熱への効きの大きい順）

1. **映像が高解像度・60fps・HDR で回り続ける**（`SceneController.attach`）。既定は「撮影優先」の形式で、`.max` だと同じ解像度なら fps の高いほうを選ぶ。取り込み・追跡・描画のすべてがこれに比例する
2. **3D を何も描いていないのに、RealityKit の描画機能がほぼ全部有効**だった（切っていたのは10種類中3つ）
3. **Vision の前景マスク＋分類が止まらない。**株が決まった後も 1.2秒ごとに走り続ける（D49 の寄せ直し）
4. **「未設定」の間、カメラ映像に毎フレーム全画面ぼかし**（`.blur(radius: 16)`）。来場者が株を迎えるまでずっとこの状態
5. 毎フレームの無駄: 診断用の特徴点を常に数えていた／吹き出しの位置をカメラ画面の body で読んでいたため、**吹き出しが動くたびに画面全体を作り直していた**（その中で文字の実寸計測も走る）
6. ムービーが、見えていないところ（覆われた裏・別タブ）でも流れ続ける。全画面では2本同時
7. センサーのポーリングが1秒固定で、繋がらない場所でも1秒ごとに通信を試み続ける
8. 画像の置き場が上限すれすれ（上記の実測）。溢れると一覧やスクロールのたびに開き直しになる
9. `ProcessInfo.thermalState` をどこでも見ていない。熱くなっても何も落とさない
10. 画面が消えない設定（`isIdleTimerDisabled`）が全タブ・全時間

### 直したこと（ユーザーの選択: 見た目が変わらない分だけ）

- **描画の機能を全部切った**（2）。3D のものは1つも置いていないので、影も環境光もカメラの粒子も要らない
- **診断用の特徴点は、診断パネルを開いている間だけ数える**（5）
- **吹き出しを別のビュー（`BubbleLayer`）に切り出した**（5）。位置を読む場所をそこに閉じ込めたので、吹き出しが動いてもカメラ画面の残り（弧・シャッター・直近の1枚）は作り直されない
- **文字の実寸は一度測ったら覚える**（5）。セリフは決まったプールから出るので数は知れている
- **ムービーは見えている間だけ流す**（6）。`onAppear` / `onDisappear` と、背面に回ったときで止める
- **センサーは失敗が続いたら間隔を伸ばす**（7）。1秒 → 2 → 4 → 8 → 15秒で頭打ち、繋がったら1秒に戻す
- **画像の置き場を配り直した**（8）。小さい絵 48MB → 96MB、画面いっぱいの1枚 12枚/96MB → 8枚/64MB。一覧の先読みは `.utility`（効率コア寄り）にし、列の先読みは開いた直後に要るので急ぎのまま

### 手を付けていないもの（見た目・体験が変わるため）

1（映像の質）・3（検出の間隔）・4（ぼかし）・9（サーマル対応）・10（画面常時点灯）。**発熱の主因は 1 と 3 なので、ここに手を入れない限り体感は大きく変わらない見込み。**

### 確かめたこと

- クリーンビルドが通る（既存の警告1件: `PhotoLibraryGrid.swift:332` の main actor 越境は今回の変更とは別）
- PlavoCore 65件のテストが通る
- 列のスクロールの滑らかさは、対策の前後で差が出ない（プロフィールで 45〜52 fps。**9/22 の 58 fps と比べているのではなく、今日のコードで対策を外した版と比べた。**その間にプロフィールの作りが変わっているため）
- プロフィールと詳細の画面写真で、見た目が変わっていないことを確認

### 次にやること

- **実機で診断パネルの「映像」の行を見る**（例: `3840x2880 @60fps`）。1 の効きの大きさがそこで分かる
- 熱の主因（1・3）に手を入れるかを決める。展示で数時間回すなら、サーマル対応（9）はいずれ要る

決定として D59-d に記録した。**おうちのアイコンがどれも同じで、アイコン表示では見分けがつかない**点はユーザーに確認中。

### おうちを開くと落ちた

> グループを開こうとすると予期しないエラーでアプリが落ちました。

**原因**: 落ちたときの記録（2件）はどちらも、右上の切り替えの塊の色 `UIColor { ... }` の中で止まっていた。ビュー（MainActor）の中で作った関数は MainActor のものになり、**SwiftUI が画面の切り替えの途中でこの色を MainActor の外で読んだ**ため、Swift 6 の確かめ（`swift_task_isCurrentExecutor`）に掛かった。

**直し方**: 色を `Color.selectionBlob`（MainActor ではない `extension Color` の static）に移し、中の関数を `@Sendable` にした。**`CapsuleTabBar` の塊も同じ作りで、同じ落ち方をしうる**ので、同じ色を使うようにした。

**確かめ方の限界**: シミュレータを指で操作する道具（idb など）が無く、押して開く操作は再現できなかった。「起動の1.5秒後にアニメーション付きで開く」一時的なコードで試したが、**直す前の色でも落ちなかった**。押したときと同じ状況になっていないので、この方法では直ったかを確かめられない（一時的なコードは消した）。**ユーザーの手で押して確かめてもらう。**

**覚えておくこと**: ビューの中で `UIColor { traits in ... }` のような、あとで UIKit から呼ばれる関数を作らない。作るなら MainActor の外（`extension Color` の static など）で作る。

| メンバー・植物は横スライドではなく折り返しで | 折り返して並べる `WrapLayout` を作った（わが家は1段に収まるので、折り返すところはまだ見ていない） |
| リストモードの一番下にもグループ追加ボタン（灰色四角） → 横長にして | 灰色の横長の角丸に＋ |
| 窓モードは、デフォルトで先頭のグループが開かれている状態に | アイコン表示にしたとき・アイコン表示で始めたとき、先頭のおうちの枠を開く |

**詰まった点**: 列表示の一番下にボタンを足すため `List(households)` を `List { ForEach ... }` に組み替えたら、消したはずの線と詰めた余白が戻った。`listRowSeparator` / `listRowInsets` を List 全体に付けても行には効かない。行ごとに付けるようにした（`talkListRow()`）。

### 日記のクローズドSNS化（D60）

> 日記のクローズドSNS化。自分の日記とみんなの日記で分けます。画面上の「日記」を「自分の日記」と「みんなの日記」に分け、切り替えられるようにしてください。画面スライドで切り替えます。みんなの日記画面は、縦型タイムライン型です。３列グリッドはないです。

- 日記タブを、上の切り替え＋横スライドの2ページにした。作りはマイプラント詳細と同じ（ページ形式の TabView を画面の端まで広げ、切り替えは浮かせ、ページのずれを測って打ち消す）
- 見出しの帯を出さず、「日記」のあった場所に切り替えを置いた
- 縦フィードへの行き先（`navigationDestination`）をグリッドの中から日記タブへ移した。ページ形式の TabView の中では効かないため
- みんなの日記は架空の書き手の8ページ（`CommunityStore` / `CommunitySeed`）。写真は起動後に1枚ずつ描く。白いコスモスとマリーゴールドの見た目を足した
- **自分の日記はみんなの日記に出していない。**公開の線引き（L-9）が未決のため

**確かめたこと**: 両方のページを起動引数で開き、画面写真で確かめた。1回目の画面写真で自分の日記が下のほうまで送られていたが、続けて3回起動するといずれも先頭（今日）から出た。4回目はマイプラントのタブが出ており、撮っている間にシミュレータが手で操作されていたとみている。

**直し**: 「日記はあってください。その下に『みんなの日記』と『自分の日記』のタブがある形に」。見出しの帯を隠すのをやめ、細い見出し「日記」の下に切り替えを置いた（マイプラント詳細と同じ並び）。

**直し**: 「他のページでは、上の薄背景のようなUIが画面下にも入っているのに、ここだけ入っていない」。タブバーの裏のぼかしはシステムが付けるが、ページ形式の TabView の中のスクロールには効かない（上端と同じ理由）。上端の自前のぼかし（`scrollEdgeFade`）を上下に返した `bottomScrollEdgeFade` を作って敷いた。
- 1回目は安全領域の高さ＋24pt で約180pt になり、プロフィール（システムのもの）と並べると高すぎて濃かった → 画面の下端から 96pt に
- 2回目は、ぼかしが安全領域（タブバーの上）で止まり、タブバーの上端で線のように切れた。高さだけ決めて下に置くと、安全領域の内側に置かれる → 画面の高さいっぱいを取ってから下に寄せ、安全領域を無視させた
- プロフィールの下端と画面写真で並べて、同じ見え方になったことを確かめた
