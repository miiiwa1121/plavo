## 認識のすり合わせ

### 答えで形が変わった

切り替えの答えは「**3列で写真をタップすると切り替わり、左上の＜で戻る**」。モードではなく**画面を重ねる形**だった。

そのほかは最初の案のまま決まった。

- 小さい写真の列は**左が古く、右が新しい**

## グリッドのタップが、もともと効いていなかった

確認用の UI テストで、グリッドの写真をタップしても**画面が移らなかった。**シミュレータのログにこう出ていた。

> Do not put a navigation destination modifier inside a "lazy” container ... It will be ignored.

`navigationDestination` をギャラリーのページの中に置いていたが、**ページ形式の `TabView` は lazy なコンテナ扱いで、宣言ごと無視されていた。**今回の変更より前からの不具合で、全画面の表示にも行けなかったことになる。いつから壊れていたかは追っていない（詳細をページ形式にした時点からの可能性が高い）。

追加の依頼は2つ。「メインの写真に左右の余白と角丸を付ける」「写真の切り替えアニメーションを iPhone の UI/UX にする」。

### 「iPhone の UI/UX」の範囲を先に確かめた

写真アプリには、切り替えに関わる動きがいくつかある。どれを指しているかで作る量が大きく変わるので、実装の前に3つに分けて確認した。答えは「全てです」。

| # | 動き |
|---|---|
| A | マスから拡大して開き、戻るとそのマスへ縮む。下になぞっても閉じる |
| B | 列をなぞると、中央に来た写真へメインが次々と切り替わる。タップもその場で切り替わる |
| C | 見ている小さい写真だけ、元の縦横比に広がる |

メインを送るときに写真の間が空いて流れる動きは、余白を付ければ自然にそうなるので、確認には含めなかった。

### 作り方

- **A**: iOS 18 の `navigationTransition(.zoom)`。下になぞって閉じる操作も一緒に付いてくる。**戻るときの行き先を「いま見ている写真」にする**ため、見ている写真を詳細画面に持たせ、1枚を追う画面と全画面にはそれを共有させた。前回はそれぞれが自分で持っていた
  - グリッドのタップは `NavigationLink(value:)` をやめ、ボタンで「見ている写真を決める → 開く」の順にした。`NavigationLink(value:)` には、遷移の前に見ている写真を書き換える入り口が無い
  - 見ている写真が変わったら、グリッドをそのマスまで送っておく。見えていないマスには縮めない
- **B**: 列に `scrollPosition(id:)` を付け、中央の写真を読む。`onScrollPhaseChange` で**指で動かしている間だけ**メインを追わせる。列を自分で送ったときの変化まで拾うと、メインと列が互いを動かし合うため
  - メインをその場で切り替えるときは、アニメーションを切った `Transaction` で更新する。そのままだとページ形式の `TabView` がスライドする
- **C**: 見ていない写真は幅40pt、見ている1枚は高さ56ptに対する元の縦横比（高さの2倍で止める）。**なぞっている間は全部を細くそろえる。**広げたままなぞると、広がった分だけ中央の写真がずれて選び直しが起きるため。写真アプリも同じようにしている
- 見ている写真の枠と、ほかを薄くする表現は外した。形で示すので要らない

## 追記 — メインと列の形を固定し、見ている1枚をちょうど中央に置いた（D46-b）

依頼は2つ。

- 全画面は写真をそのまま見せ、メイン＋横一列のメインは形を固定してぶれないようにする
- 列の見ている1枚は画面の中央に来るようにし、写真によって大きさが変わらないよう固定する

### 認識のすり合わせ

| # | 確認したこと | 答え |
|---|---|---|
| 1 | 全画面はいまも切り抜きなしで写真全体を出している。変えるところはあるか | OK（変えない） |
| 2 | メインの枠の形。案は縦 3:4 | **正方形にしてみる** |
| 3 | 両端の写真も中央に置き、端の側は空く | そうです |
| 4 | 見ている1枚だけ 56×56 に広げる（a）か、全部同じ大きさで枠を付ける（b）か | **a** |

メインを切り抜くのは、D46 の「メインは切り抜かない」を覆す。写真全体は全画面で見る、という分担に変わるので D46-b として残した。

### 中央に来ていなかった原因

前回の画面写真で、見ている1枚が中央から約 7pt 右にずれていた。`scrollPosition(id:anchor: .center)` で寄せていたが、**見ている1枚が広がる前の幅で送り先を決めていた。**広がった分（14pt）の半分がずれになる。

**位置を写真の番号から計算で決める形に変えた。**列の両端に「画面の半分 − 見ている1枚の枠（68pt）の半分」の余白を置くと、i 枚目を中央に置く送り位置は i × 42pt になる。画面の幅も広がる前後も関係しない。なぞっている間に中央にある写真も、送り位置から逆算する。

### 数値で測った

見た目で「ちょうど中央か」は判断しにくいので、一時的に見ている1枚とメインに目印（アクセシビリティの識別子）を付け、UI テストで位置を読んで書き出した。

1回目の結果。

| 手順 | 見ている1枚の中心（画面の中心は 201pt） | メインの枠 |
|---|---|---|
| 開く（74日目） | 201 | 370×370 |
| 列の左隣をタップ | 201 | 370×370 |
| メインを送る | 201 | 370×370 |
| いちばん古い端までなぞる | 201 | 370×370 |
| **いちばん新しい端までなぞる** | **229** | 370×370 |
| 途中までなぞる | 201 | 370×370 |
| **勢いよくはじいて新しい端へ** | **229** | 370×370 |

**新しい端だけ 28pt ずれた。**なぞっている間は全部が細くなるので、列が 28pt 短くなる。止まって広げるのと同時に送ると、送り先が短いほうの列の端で頭打ちになる。**なぞっている間は、細くなった分を右端の余白に足して列の長さを変えない**ようにしたところ、全手順で 201 になった。

メインの枠は、縦長・横長・正方形のどの写真でも 370×370、位置も同じだった。

### 途中で戻ってしまった件

最初の UI テストでは、古い端へ向かって4回なぞったところで**グリッドに戻っていた。**3回で端に着き、4回目は端に着いた状態から右へなぞり始めていた。iOS 26 では画面のどこからでも右へなぞると戻るので、横に送れる列でも、端に着いていると「戻る」として扱われる。

アプリの不具合ではないのでテストを3回に直した。端に着くまでのなぞりは列が受け取るので、送っている途中に戻ることはない。D46-b に書いておいた。

目印・UI テスト・その設定は、確認後に消した。
