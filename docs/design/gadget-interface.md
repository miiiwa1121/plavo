# ガジェット連携インターフェース仕様

センサーガジェットとアプリの間の契約。**ハードウェア担当に渡すための仕様書。**

最終更新: 2026-08-29

## 1. 前提

| 項目 | 内容 |
|---|---|
| 用途 | 2026年10月中旬の技術イベント展示（D32） |
| 担当 | ガジェット本体・ファームウェアはハード担当。データの受け取り以降はアプリ側 |
| 最小要件 | **土壌水分だけ取れれば展示は成立する。**他の項目は任意 |
| 目的 | 来場者が水をやると、植物がその場で反応する |

**この仕様を満たしていれば、モックのスライダーと実センサーを差し替えられる。**どちらが間に合っても展示は動く。

## 2. 経路

```
ガジェット ──USB(シリアル)──▶ 担当PC ──ローカルHTTP──▶ スマホ
                                  │
                                  └─ server/ を動かす

  ネットワークは「スマホのインターネット共有」で作る
  （会場のWi-Fiは使わない。必要なのはUSBケーブル1本のみ）
```

会場のWi-Fiは信用できないため使わない。スマホのテザリングでローカルネットワークを作り、PCをそこに繋ぐ。

**BLEで直接スマホに送れる場合は、PCが不要になる。**ハード担当が対応可能なら、そちらのほうが展示物が減って有利。その場合もペイロードの形式は同じにする。

## 3. ペイロード

```json
{
  "gadgetId": "gadget-001",
  "measuredAt": "2026-08-29T18:20:00+09:00",
  "soilMoisture": { "raw": 512, "percent": 38.2 },
  "lightLux": 12400,
  "temperature": 24.6,
  "humidity": 52.1,
  "nutrientEc": 1.4,
  "battery": 87
}
```

| フィールド | 型 | 必須 | 内容 |
|---|---|---|---|
| `gadgetId` | string | **必須** | 個体の識別子。複数台を並べる場合に区別する |
| `measuredAt` | string | **必須** | ISO 8601。タイムゾーン付き |
| `soilMoisture.raw` | number | **必須** | センサーの生値（ADC値など） |
| `soilMoisture.percent` | number | **必須** | 0〜100 に正規化した値 |
| `lightLux` | number \| null | 任意 | 照度 |
| `temperature` | number \| null | 任意 | ℃ |
| `humidity` | number \| null | 任意 | % |
| `nutrientEc` | number \| null | 任意 | mS/cm |
| `battery` | number \| null | 任意 | 0〜100 |

**未対応の項目は `null` を送る。**フィールド自体を省略してもよい。

### なぜ raw と percent の両方を送るのか

静電容量式センサーの生値は環境依存で、**スポンジと土ではまったく特性が違う**。キャリブレーションをどちらが持つかを決めないと、双方が「相手がやると思っていた」ことになる。

| 値 | 責任 | 理由 |
|---|---|---|
| `percent` | **ハード側が正規化する** | センサーの特性を一番よく知っているのはハード側 |
| `raw` | 併せて送る | 展示会場でスポンジの状態が変わったとき、アプリ側で再調整できる逃げ道を残す |

キャリブレーションの基準は以下で合わせる。

- **0%** = 乾いたスポンジ（水を絞りきった状態）
- **100%** = 十分に水を含んだスポンジ（それ以上吸わない状態）

## 4. 送信頻度

| 場面 | 頻度 |
|---|---|
| 展示 | **1秒に1回**。水やりの反応を即座に見せるため |
| 製品版（将来） | 省電力のため間引く。10分に1回程度 |

展示では電池寿命より応答速度を優先する。USB給電なら電池を気にしなくてよい。

## 5. 受信側のエンドポイント（PC経由の場合）

`server/` が以下を提供する。

```
POST /sensor
  Content-Type: application/json
  Body: 上記のペイロード
  Response: 204 No Content
```

```
GET /sensor/latest?gadgetId=gadget-001
  Response: 最新の1点
```

```
GET /sensor/recent?gadgetId=gadget-001&seconds=300
  Response: 直近N秒分の配列
```

アプリは `GET` でポーリングする。

## 6. 展示で必要な最小構成

**水やりの実演だけなら、以下で足りる。**

- `gadgetId`
- `measuredAt`
- `soilMoisture.raw` と `soilMoisture.percent`
- 1秒に1回の送信

他の項目は、間に合えば追加する。

## 7. 動作確認の観点

ハード担当に確認をお願いしたい項目。

| 観点 | 確認したいこと |
|---|---|
| 応答速度 | 水をやってから値が上がるまで何秒か。**5秒以内が望ましい** |
| 分解能 | 乾いた状態と湿った状態で、値が十分に離れているか |
| 安定性 | 静置したとき値が暴れないか。暴れるなら移動平均を入れる |
| 復帰 | スポンジを絞ったあと、乾いた状態の値まで戻るか |
| 連続動作 | 展示時間（数時間）を通して動き続けるか |

**スポンジは土と保水特性が違う。**一気に吸って一気に落ちるため、土向けのキャリブレーションをそのまま使うと値が振り切れる可能性がある。

## 8. 想定される運用上の問題

| 問題 | 対策 |
|---|---|
| 何十回も水をやるとスポンジが飽和し、受け皿から溢れる | トレイとバケツを用意。合間にスポンジを絞る |
| 見た目が実験装置になる | 鉢カバーをかける |
| USBケーブルが来場者の動線を横切る | 配線経路を事前に決め、養生する |

## 9. モックとの互換

アプリ側は、実センサーと画面上のスライダーを**同じインターフェースで扱う**。

```
SensorSource
  ├─ GadgetSensorSource   実センサー（このドキュメントの仕様）
  └─ MockSensorSource     スライダーと再生データ
```

**実センサーが間に合わなくても展示は成立する。**逆に間に合えば、切り替えるだけで実演が可能になる。
