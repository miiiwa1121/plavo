# ドメインモデル

plavo が扱う概念と、その関係を定義する。**何を持ち、何を持たないか**が本ドキュメントの主題。

最終更新: 2026-08-29

## 1. 設計の根幹 — 保存するものと計算するもの

D23で決めた原則が、このモデル全体を規定する。

> **再計算できるものは保存しない。**

| 分類 | 内容 | 保存 |
|---|---|---|
| 一次データ | 撮影画像、センサーの生値 | **する** |
| 観測 | AIが画像から読み取ったこと（見た目・ステージ・草丈・確信度） | **する** |
| 生成物 | セリフ、ユーザーが書いた日記 | **する** |
| 導出指標 | DLI・GDD・VPD・開花予測・水やり予測・元気さ・親密度・死因 | **しない** |

**観測を保存する理由**: センサー値や計算値は何度計算しても同じ答えになるが、AIが見たことはその瞬間にしか存在せず再現できない。保存しないと、3ヶ月後の再診断で当時のセリフと食い違い、**その日の記憶が書き換わる**（D23-a）。

**導出指標を保存しない理由**: 保存すると、後で計算式を直したときに過去データと矛盾する。元データだけ持てば、式を変えても全期間が即座に新しい値になる。

## 2. エンティティ

### Plant（個体）

育てている植物1株。

| 属性 | 型 | 備考 |
|---|---|---|
| id | UUID | |
| name | String | ユーザーがつけた名前（D9） |
| species | String | AIが推定し、後から修正可（D9） |
| plantedAt | Date | 育成開始日 |
| gadgetId | String? | ガジェットがあれば個体IDになる（D8） |
| imageFeature | Data? | 画像特徴。ガジェットなしの自動同定に使う（D8） |
| archivedAt | Date? | 枯死してアーカイブされた日時 |

**保持数**: 少数精鋭。候補が少ないほど自動同定の精度が上がる（L-5）。

**削除**: 可能。ただし強い確認を挟む（D29）。

**currentStage を持たない**: 生育ステージは Observation の履歴から導出する（後述）。

## 3. 生育ステージ

```
seed(種) → sprout(発芽) → trueLeaf(本葉) → bud(つぼみ) → bloom(開花) → seedSet(結実) → withered(枯死)
```

### 遷移規則 — 後戻りを許さない

**AIが返す `stage` はブレる。**同じ株を撮っても、光の当たり方や角度で「本葉」と「つぼみ」を行き来しうる。これをそのまま記録すると、成長の履歴がのこぎり状になり、追悼ムービーの構成が破綻する。

したがって**個体の生育ステージは、観察履歴における最大到達ステージとする**。

```
currentStage(plant) = max(observation.stage for observation in observations(plant))
```

例外は `withered`（枯死）で、これだけは他のどのステージからも遷移しうる。

**これも導出値であり保存しない。**Observation の履歴から都度計算する。

### ステージが持つ意味

| ステージ | セリフの文脈 | 天寿判定（D30） |
|---|---|---|
| seed / sprout / trueLeaf | 育っている最中 | 到達していない |
| bud | もうすぐ咲く。開花予測が効く | 到達していない |
| **bloom** | 咲いた | **天寿の境界。ここに届けば「役目を果たした」** |
| seedSet | 種を残した | 完全な天寿 |
| withered | 終わり | — |

## 3.5 植物プロファイル（D17-a）

植物種に依存する知識は `PlantProfile` に切り出し、差し替え式にしている。展示に使う植物が未定のため、種が決まったらプロファイルを1つ書くだけで済む構造にした。

| 項目 | 内容 |
|---|---|
| `isAnnual` | 一年草か。false なら枯死をライフサイクルの正常な完結として扱えない |
| `baseTempC` / `gddToBloom` | GDDの基準温度と開花までの積算温度。null なら開花予測をしない |
| 適正環境 | 光・土の湿り・気温・湿度・養分の範囲 |
| `stages` | この植物が取りうる生育段階と説明 |
| `symptoms` | よくある症状と原因。診断精度に直結する |
| `character` | 性格の記述。セリフの個性のもとになる |
| `naturalCompletionStage` | 天寿の判定段階（D30）。null なら到達段階で判定できない |

実装は `server/src/domain/profile.ts`。現時点でミニひまわりとポトスの2種を定義している。

**未解決（L-10）**: 多年草は室内でまず開花しないため `naturalCompletionStage` が null になる。この場合、D30の「天寿のときだけ明示し、不在で察させる」仕組みが機能しない。多年草を選ぶ場合は天寿の判定基準を別に定める必要がある。

## 4. 導出指標（保存しない純粋関数）

すべて一次データから計算する。セリフ生成時に計算してClaudeへ渡す文脈になるが、**画面には出さない**（原則2）。

| 関数 | 入力 | 出力 | 用途 |
|---|---|---|---|
| `dli(readings, date)` | 照度の時系列 | mol/m²/day | 1日に浴びた光の総量 |
| `gdd(readings, from, to)` | 気温の時系列 | ℃·day | 生育の進行度。基準温度 6.7℃ |
| `vpd(temp, humidity)` | 気温・湿度 | kPa | 蒸散の効率。適正 0.8〜1.2 |
| `predictedFloweringDate(plant)` | GDDの推移 | Date | GDD 958 到達予測 |
| `nextWateringDate(readings)` | 土壌水分の減衰 | Date | 次の水やりタイミング |
| `daysSinceLastWatering(readings)` | 土壌水分の急上昇履歴 | Int | 前回の水やりからの経過 |
| `growthRate(observations)` | 草丈の推移 | cm/day | 徒長の検知 |
| `vitality(observation, readings)` | 観測＋センサー | 0〜100 | 総合の元気さ |
| `discrepancies(observation, readings)` | 観測＋センサー | [String] | 画像と数値の食い違い |
| `intimacy(plant, observations)` | 観察履歴 | 0〜100 | 親密度（D12） |
| `deathCause(plant, observations, readings)` | 全履歴 | DeathCause | 死因判定（D30） |

### GDD基準値（ミニひまわりの場合）

| 到達点 | 積算温度 |
|---|---|
| 発芽 | 約206 GDD |
| **開花** | **約958 GDD** |
| 成熟 | 約1725 GDD |

基準温度は 6.7℃。`GDD = Σ max(0, 日平均気温 − 6.7)`。

### 画像と数値の食い違い

**最も情報量が多いのは両者が矛盾したとき。**

> 土壌水分は十分なのに、葉がしおれている → **根腐れの疑い**

これは画像だけでも数値だけでも出せない診断であり、ガジェットの価値の証明になる。`discrepancies()` がこれを検出し、セリフ生成の文脈に渡す。

## 5. 親密度

**指標は一本だけ**（D12）。複数のゲージを持つと植物が管理対象に見え、育成シミュレーションのステータス画面になる。

```
intimacy = f(観察の回数, 継続日数, 健康を保った期間)
```

駆動する対象は2つ。

| 駆動先 | 内容 | 今回 |
|---|---|---|
| セリフの層の深さ | 状態を伝えるだけ → 挨拶 → 名前を呼ぶ → 思い出を語る | 実装しない（G-06） |
| 夢の出現率 | 高いほど夢を見やすい | 実装しない（G-01） |

**ゲージは画面に出さない。**ユーザーは「最近よく喋るようになった」と体感するだけ。

今回は駆動先の両方が実装外のため、G-06として設計のみ残す。ただし導出関数として定義しておけば、セリフの層だけなら後から安価に接続できる。

## 6. 死因判定（D30）

```
enum DeathCause {
  naturalCompletion   // 天寿。bloom 以降に到達している
  waterShortage       // 枯死前2週間の土壌水分が低位
  overWatering        // 土壌水分が高いまま、かつ葉のしおれを観測
  lightShortage       // 同期間のDLIが低位
  heatStress          // 気温が上限を逸脱
  coldStress          // 気温が下限を逸脱
  unknown             // 特定できない
}
```

**主軸は到達ステージ**。`bloom` に届いていれば `naturalCompletion`。ひまわりは咲けば役目を果たしている。

補助的に、枯死前2週間の土壌水分・DLI・気温の逸脱から原因を推定する。

### 使い方の制約

| 用途 | 死因の扱い |
|---|---|
| 追悼ムービーのトーン（第2層） | 判定に応じてトーンを変えるが、**明示しない**。天寿のときだけ「役目を果たした」と言い、そうでないときはその言葉が出ない |
| 振り返り画面（第3層・F-14） | 事実として記述する。ただし**断定を避ける** |
| セリフ | 死因を植物に語らせない |

**観察頻度は判定材料に使うが、ユーザーに見せる文言には絶対に出さない。**「あなたは20日間会いに来ませんでした」は、このプロダクトが最も言ってはいけない言葉である。

## 7. 再診断の判定（D4-a）

```
needsRediagnosis(plant, lastObservation, readings) -> Bool
```

| 条件 | 判定 |
|---|---|
| 土壌水分が前回診断時から急上昇 | 再診断（水やりが行われた） |
| 照度が大きく変化し継続している | 再診断（置き場所が変わった） |
| 前回診断から一定時間が経過 | 再診断 |
| いずれも該当しない | キャッシュを使う |

**ユーザーは何も操作しない。**D7の「申告制を採らず、機械が検知したものだけ信じる」原則がそのまま適用される。

## 8. 関係図

```
Plant 1 ──── * Observation ──── 1 (image file)
  │                  │
  │                  └─ dialogue（そのとき言ったこと）
  │
  ├──── * SensorReading（時系列）
  │
  ├──── * DiaryEntry ──── * (photo files)
  │
  └──── 0..1 Memorial ──── 1 (video file)

導出（保存しない）:
  currentStage    ← Observation の最大到達ステージ
  intimacy        ← Observation の履歴
  deathCause      ← Observation + SensorReading
  DLI/GDD/VPD/予測 ← SensorReading
  vitality        ← Observation + SensorReading
```
