## 2. レイヤの責務

### Perception Layer（知覚層）

カメラ映像から植物を見つけ、吹き出しを空間に固定する。

| 要素 | 責務 |
|---|---|
| Vision framework | 毎フレームの植物検出。バウンディングボックスを返す |
| ARKit | ワールドトラッキング（6DoF）。特徴点ベース。**平面検出は使わない**（D3） |
| RealityKit | 吹き出しエンティティの描画と、ルーム画面の3D描画（D16-a） |

**奥行きの決定**（D3-a）: 検出したバウンディングボックスの中心方向へレイキャストし、特徴点または平面に当たればその距離を採用。外れたら固定距離（1.2m）にフォールバックする。

**検出頻度**: 描画のフレームレート（30fps）を守ることを優先し、検出は数フレームおきで構わない。吹き出しの追従が落ちると体験が一気に安っぽくなるため、描画を阻害しない範囲に抑える。

### Domain Layer（ドメイン層）

**UIにもARにも永続化にも依存しない純粋なロジック。**このプロダクトの本体はここにある。

- 個体の同定と登録
- 観察の記録
- **導出指標の計算**（保存しない純粋関数）
- 親密度の算出
- 生育ステージの遷移判定
- 死因の判定
- 再診断が必要かの判定（D4-a）

詳細は [domain-model.md](./domain-model.md)。

### Persistence Layer（永続化層）

| 対象 | 保存先 | 理由 |
|---|---|---|
| 個体・観察・日記のメタデータ | SwiftData（CloudKit同期） | 構造化データ。iCloudで自動保全（D19） |
| 撮影画像 | ファイルシステム（CloudKit同期） | バイナリをレコードに埋めない。数ヶ月分で肥大するため |
| センサーの時系列 | SwiftData | 時系列だが件数が限られる（1日数百点） |
| 外部制作の追悼ムービー | ファイルシステム | 再生するだけ（D22） |

**保存しないもの**: 導出指標すべて（D23）。DLI・GDD・VPD・開花予測日・次の水やり予測日・総合の元気さ・緊急度・推定原因・親密度・死因。これらは元データから計算する。

### Diagnosis Client / Proxy

**プロキシを置く唯一の理由は、APIキーをアプリバイナリから隠すこと。**データは持たない（D10）。

| 項目 | 内容 |
|---|---|
| リクエスト | 画像（base64）＋ センサー時系列 ＋ 前回の観察 ＋ 個体情報 |
| レスポンス | 構造化された観測 ＋ セリフ |
| モデル | `claude-opus-5` |
| 方式 | vision + structured outputs（構造化出力） |
| タイムアウト | 20秒。超えたらフォールバックへ |
| リトライ | 1回まで。それ以上待たせない |

**プロキシの実装言語は未定。**薄い中継なので何でも構わない。要件は「APIキーを保持し、リクエストを転送し、レスポンスをそのまま返す」だけ。

## 3. データフロー

### 3.1 通常の観察

```
① カメラ起動
       ↓
② Vision が植物を検出
       ↓
③ 個体を同定（ガジェットID or 画像特徴 → Domain）
       ↓
④ ARKit でアンカーを打ち、吹き出しを配置
       ↓
⑤ 事前定義の一言を即座に表示（「はにゃ？」/ 0秒 / 通信不要）
       ↓
⑥ 再診断が必要か判定（D4-a）
       │
       ├─ 不要 → キャッシュ済みのセリフを表示 → 終了
       │
       └─ 必要
              ↓
       ⑦ Domain が導出指標を計算（DLI / GDD / VPD / 予測）
              ↓
       ⑧ Diagnosis Client が Proxy 経由で Claude を呼ぶ
              ↓
       ⑨ 観測とセリフを受け取る
              ↓
       ⑩ Persistence に保存（画像・観測・センサー・セリフ）
              ↓
       ⑪ 吹き出しにセリフを表示
```

**⑤ が ⑥〜⑪ より先に来るのが重要。**診断は5〜15秒かかるが、その間ユーザーは無反応の画面を見ない（D27）。

### 3.2 再診断の判定（D4-a）

**画像診断とセンサー読み取りは頻度が違う。**

| 対象 | 頻度 | 理由 |
|---|---|---|
| 画像診断 | 数分に1回のスロットル ＋ 急変で即時 | 植物の姿は数分から数日変わらない |
| センサー読み取り | リアルタイム | 値は刻々と変わる。水やりの検知もここで起きる |

```
検出した
   ├─ 土壌水分が急上昇した        → 再診断（水やりが行われた）
   ├─ 照度が大きく変化し継続       → 再診断（置き場所が変わった）
   ├─ スロットル時間が経過した      → 再診断
   └─ いずれも該当しない
          → キャッシュを使う
          → ただし本編のセリフは繰り返さない。
            短い一言だけ出すか、黙る（D27）
```

コアループ（観察 → 世話 → 再観察 → 差分に気づいて喜ぶ）が閉じる。**ユーザーは何も操作しない。**

### 3.3 異常系

原則3（失敗をユーザーのせいにしない）に従い、**すべての異常系を植物の様子として表現する**。

| 状況 | 挙動 |
|---|---|
| 植物が見つからない | 「見当たらないなぁ」程度の軽い表示（D24）。診断は走らせない |
| 通信できない | 事前定義セリフ ＋ 前回の観察で振る舞う。植物が眠そうにしている（D28） |
| 診断がタイムアウト | 同上 |
| 診断が失敗した | 同上 |
| ARトラッキングを失った | 吹き出しを消さず、その場に留める。復帰したら追従を再開 |
| カメラ権限が拒否された | 他タブへの導線を残し、理由と再許可の導線を出す |

**「エラー」「失敗」「できません」という語を、ユーザーに見せる文言に一切使わない。**

## 4. 外部依存

| 依存先 | 用途 | 障害時の挙動 |
|---|---|---|
| Claude API | 診断とセリフ生成 | 事前定義セリフにフォールバック（D28） |
| CloudKit | 記録の同期 | ローカルで動作を継続。復帰時に同期 |
| ガジェット（将来） | センサー値 | 今回はモックデータソースで代替（F-10） |

**動画生成API は今回使わない**（G-01）。追悼ムービーも外部制作の動画を再生するだけ（D22）。

## 5. 差し替え可能にする箇所

保守性のため、以下はインターフェースで抽象化する。

| 箇所 | 理由 |
|---|---|
| センサー入力 | 今回はモックデータセット、将来はBLE（F-10） |
| 診断エンジン | プロンプトとスキーマをコードから分離し、ビルドなしで調整を試せるようにする |
| 対象植物のプロファイル | ミニひまわり特化から段階的に解放する（D17） |
| 導出指標の計算 | 純粋関数として実装。保存しないため、式の変更が過去データに波及しない（D23） |
