# 技術選定

採用する技術と、その根拠。**実装しながら埋めていく生きたドキュメント**であり、確定したものと未決のものを区別して書く。

最終更新: 2026-08-29

## 0. 状態の凡例

| 記号 | 意味 |
|---|---|
| **確定** | 根拠とともに決定済み。覆すなら理由が要る |
| **暫定** | 現時点の選択。実装しながら検証し、問題があれば変える |
| **未決** | まだ選んでいない。判断が必要 |

## 2. アプリの構成

| 項目 | 選定 | 状態 | 根拠 |
|---|---|---|---|
| プロジェクト生成 | **xcodegen** | **暫定** | `project.yml` で構成を宣言でき、gitで差分が読める。`.xcodeproj` は生成物として扱う。既に環境に導入済み |
| モジュール分割 | ドメイン層を Swift Package（`PlavoCore`）に分離 | **確定** | **実機もカメラもAPI認証もなしに `swift test` で検証できる。**Xcodeプロジェクトを組む前にロジックの正しさを固められた |
| 状態管理 | SwiftUI の `@Observable`（iOS 17+） | **暫定** | 外部ライブラリを入れない。展示までの期間が短く、依存はビルド問題のリスクになる |
| 依存ライブラリ | **なし**（標準フレームワークのみ） | **暫定** | 同上。必要になった時点で個別に判断する |
| テスト | XCTest | **暫定** | Swift Testing も使えるが、`swift test` での実績を優先した |
| 最低iOSバージョン | iOS 18.0 | **未決** | N-1。展示は自分の端末で行うため新しめでよい。`PlavoCore` は iOS 17 / macOS 14 を下限にしてある（macOSでテストを走らせるため） |

## 3. 永続化 — 展示と製品で分ける

**D19（CloudKit で自動保全）と D33（毎回データをリセット）は衝突する。**用途を分けて解く。

| 用途 | 展示での実装 | 製品版の設計 | 状態 |
|---|---|---|---|
| 時系列パネルの記録 | **アプリバンドル同梱の JSON**（読み取り専用） | 端末内 + CloudKit | **暫定** |
| セリフのプール | アプリバンドル同梱の JSON | 同上 | **暫定** |
| セッション中の状態 | **メモリのみ**（来場者ごとにリセット） | SwiftData + CloudKit | **暫定** |
| 撮影画像 | 保存しない | ファイル + CloudKit | **暫定** |

**展示に CloudKit は要らない。**むしろ有害で、Apple ID が必要になり、リセットが同期先まで波及し、端末を変えたときに挙動が変わる。

D19 は製品版の決定として維持し、**今回の実装からは外す**。

## 4. コンテンツの配布

| 項目 | 選定 | 状態 |
|---|---|---|
| セリフ（`content/dialogues/*.json`） | アプリバンドルに同梱 | **暫定** |
| センサーの再生データ（`server/fixtures/sensors/*.json`） | アプリバンドルに同梱 | **暫定** |
| 時系列パネルの記録 | 未作成 | **未決** |

**リポジトリのルートにある JSON を、ビルド時にアプリへコピーする。**`PlavoCore` のテストは同じファイルをリポジトリ相対で直接読んでいるため、二重管理にならない。

## 5. センサーの受け取り

| 項目 | 選定 | 状態 | 根拠 |
|---|---|---|---|
| 経路 | ガジェット → USB → PC → ローカルHTTP → スマホ | **確定** | D35 |
| ネットワーク | スマホのテザリングでローカルLANを作る | **確定** | 会場のWi-Fiを使わない。追加機材はUSBケーブル1本 |
| 取得方式 | **HTTP ポーリング**（URLSession） | **暫定** | WebSocket も可能だが、1秒に1回のポーリングで足りる。実装が単純なほうを選ぶ |
| 実センサーとモックの切替 | 同一のインターフェースで差し替え | **確定** | F-10。どちらが間に合っても展示は成立する |

## 6. 今回使わないもの

**展示スコープ（D21・D34）では実装しない。**製品版の設計としては維持する。

| 技術 | 本来の用途 | 使わない理由 |
|---|---|---|
| Claude API | 診断とセリフ生成 | D34。当日は完全オフライン。セリフは事前生成 |
| CloudKit / SwiftData | 記録の保全 | 展示では毎回リセットするため（本ドキュメント §3） |
| Core Bluetooth | ガジェット連携 | D35。USB→PC 経由にしたため不要 |
| 動画生成API | 夢の映像 | G-01。実装対象外 |
| AVFoundation の動画合成 | 追悼ムービー生成 | D22。外部制作の動画を再生するだけ |
| Sign in with Apple | アカウント | G-03。SNS層は実装対象外 |

## 7. 意図的に採らなかった選択肢

| 検討したもの | 採らなかった理由 |
|---|---|
| Unity + AR Foundation | ARは強いがUIが極端に弱い。D13のタブUIを自作することになり、**未定のルーム1画面のために確定した4画面の質を犠牲にする**構図になる（D15） |
| Unity as a Library | ビルド構成と状態受け渡しの複雑さを常時背負う。個人開発では統合の手間が重くのしかかる |
| React Native / Expo | メンテされた6DoF ARモジュールが存在しない（D15） |
| SceneKit | 非ARの3Dでは扱いやすいが、ARKit側とアセットパイプラインが分かれる。Appleの投資も RealityKit に移っている（D16-a） |
| ARKit の平面検出 | 植物は平面検出が最も苦手な被写体。特徴点ベースのワールドトラッキングのみを使う（D3） |
| BLE 直結 | 製品版の設計（D11）とは一致するが、iOS側のBLE実装が6週間に乗り、ペアリング失敗が展示中のリスクになる（D35） |

## 9. 検証できていないこと

**ARKit はシミュレータで動かない。**以下は実機がないと確認できない。

- ワールドトラッキングの安定性
- 奥行き推定（レイキャスト＋固定距離フォールバック、D3-a）
- Vision による植物検出の精度と速度
- 吹き出しの追従とフレームレート
- 会場の照明下での挙動

**ドメイン層を先に Swift Package として切り出したのは、この制約があるため。**実機なしで固められる部分を先に固めた。
