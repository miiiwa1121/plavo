# 展示設計

2026年10月中旬の技術イベントでの展示の設計。**目的は「将来こんなサービスを作りたい」と知ってもらうこと**であり、買ってもらうことではない（D32）。

最終更新: 2026-08-29

## 1. 伝えたい3つの価値

展示物とセクションを、価値ごとに分ける。混ぜない。

| # | 価値 | 展示物 |
|---|---|---|
| 1 | **ARで植物から吹き出しが出る** | 本物の植物 |
| 2 | **時系列でコミュニケーションが変わる** | 時系列の植物パネル数枚 |
| 3 | **センサー値を気持ちに翻訳する** | 造花＋スポンジ＋水分センサー |

**この分離が展示設計の要。**1つの展示物で全部を見せようとすると、来場者はどれを見ているのか分からなくなる。

## 2. 来場者の体験フロー

```
① サービスの説明
     ↓
② 本物の植物にカメラを向ける        → ARで吹き出しが出る
     ↓
③ 時系列のパネルに順に向ける        → 成長をショートカットで体験
     ↓
④ 造花に水をやる                   → センサー値が変わり、植物が反応する
     ↓
   データをリセットして次の来場者へ
```

想定所要時間は1人あたり5〜6分。1時間で10人前後。

**「浅く多く」より「深く少なく」を選ぶ。**知ってもらうことが目的なので、通り過ぎる人数より理解した人数が重要。ただし列ができたときのために、**セクション単位で切り上げられる**設計にしておく。

## 3. 各セクションの設計

### ① サービスの説明

**このセクションが「積み重ね」の価値を担う。**

展示では毎回データをリセットするため、数ヶ月の積み重ね（日記・追悼ムービー）は体験として成立しない。②③④はいずれも数分で完結する断片であり、**「植物と過ごした時間が積み上がっていく」という本質は、ここで説明するしかない。**

### ② 本物の植物 — ARの証明

本物の植物にカメラを向けると、その周りに吹き出しが浮かぶ。

- 出るのは**事前定義の短い一言**（「はにゃ？」など）に留める
- ここでの主題は「吹き出しが出ること」であって「中身」ではない
- 中身は④で見せる。役割を分けることで、②と④の違いが体験として伝わる

### ③ 時系列パネル — 記録の再生

生育段階の異なるパネルを数枚並べ、順にカメラを向ける。

**パネルではAI診断を走らせない。その日に植物が言ったことを再生する。**

理由は3つ。

| 理由 | 内容 |
|---|---|
| AIが「これは写真だ」と言う | Claude vision は印刷物を高い確率で見抜く。「印刷された写真のように見える」と観察に書かれたら展示が壊れる |
| 記録が汚染される | パネルを見るたび観察が積まれ、同日に発芽と開花が並ぶ |
| 生育段階の後戻り防止と衝突する | 開花パネル→発芽パネルの順に見ると、発芽の前で「開花」のままになる |

再生であれば、これらがすべて起きない。

**パネルの制作上の注意**

- **マット紙・非光沢ラミネート必須。**光沢があると照明を反射して検出精度が落ちる
- 吹き出しは**パネル面より手前にオフセット**する。レイキャストは平面によく当たるため、そのままだと吹き出しが紙に貼り付いて見える

### ④ 造花＋スポンジ — センサーの証明

造花をスポンジに刺し、水分センサーを差す。来場者が水をやると値が跳ね上がり、植物の言うことが変わる。

**スポンジを使う理由は「何度でもリセットできる」こと。**土だと1日の展示で水浸しになるが、スポンジなら絞れば元に戻せる。

**このセクションでは画像を一切使わない。**入力はセンサー値だけ。これにより以下が消える。

| 問題 | 画像を使わないと |
|---|---|
| AIが「これは造花です」と言う | 消える |
| 会場の照明・グレア | 無関係になる |
| 記録の汚染 | 消える |

**造花であることは、むしろ証明として働く。**見た目に依存せず数値だけで反応するので、「本当にセンサーを読んでいる」ことが伝わる。

実センサーが間に合わない場合は、画面上のスライダーで代替する（[gadget-interface.md](./gadget-interface.md) §9）。

## 4. 完全オフラインで動かす（D34）

**当日は Claude API を一切呼ばない。**セリフはすべて事前に生成し、アプリに埋め込む。

### なぜAI生成が不要か

AI生成の最大の利点は**多様性**——同じ状態で何度観察しても違う言い回しが出ること。これは数ヶ月使うユーザーには決定的だが、**数分しか触らない来場者には一切効かない。**利点が発揮されない一方で、通信断・レイテンシ・失敗という代償だけは満額で払うことになる。

技術イベントの会場はモバイル回線が混雑し、API呼び出しが通らない可能性が現実的にある。

### AIは「実行時」ではなく「制作時」に使う

セリフを人が全部手で書くと、量も質もばらつく。**AIに大量に生成させ、人が厳選して埋め込む。**

- 当日は絶対に失敗しない（通信不要・待ち時間ゼロ）
- セリフの質を人が完全に管理できる
- 「AIが生成したセリフです」と**正直に言える**

技術者に聞かれたら「製品版ではリアルタイム生成、今日は会場の回線を考えて事前生成に切り替えました」と説明する。**この判断自体が展示の設計として評価される。**

### 構成が単純になる

| | オンライン前提 | 完全オフライン |
|---|---|---|
| Claude API | 必要 | **不要** |
| プロキシ（`server/`） | 当日も稼働 | **当日は不要**（セリフ制作の道具になる） |
| PC | プロキシ＋センサー中継 | **センサー中継のみ** |
| APIキーの管理 | 必要 | 不要 |
| 通信断のリスク | 残る | **ゼロ** |

ハード担当がBLEで直接スマホに送れる場合、**PCすら不要**になる。

## 5. データのリセット

**毎回リセットする。**前の人の記録が残っていると、次の人の体験が変わってしまう。展示は再現性がすべて。

**ただしリセットの操作を設計する必要がある。**

| 課題 | 検討事項 |
|---|---|
| 誰が押すか | 説明員が手動で押すなら、忙しいときに必ず忘れる |
| 途中離脱 | 最後まで到達しなかった人の直後にどうするか |
| 誤操作 | 体験中に押されないようにする |

案としては、①説明員用の隠し操作（画面の隅を長押しなど）、②一定時間の無操作で自動リセット、③セクション①に戻ったら自動リセット、などがある。**当日の運用に直結するため、実装項目として立てる**（L-13）。

## 6. 会場環境のリスク

| リスク | 対策 |
|---|---|
| 照明が強い・特殊 | パネルはマット紙。現地で検出精度を確認する時間を取る |
| モバイル回線が混雑 | **完全オフライン化により影響しない**（D34） |
| 騒がしい | 音に依存しない設計。D5（テキストのみ）が有利に働く |
| 来場者が順番を守らない | 動線と掲示で誘導する。アプリ側で強制するかは要検討 |
| 配線が動線を横切る | 事前に経路を決めて養生する |
| スポンジの水が溢れる | トレイとバケツ。合間に絞る運用 |
