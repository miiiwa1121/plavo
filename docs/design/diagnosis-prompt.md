# 診断プロンプト設計

Claude に何を渡し、何を返させるかの設計。**このプロダクトの品質を最も直接左右する部分。**

最終更新: 2026-08-29

## 1. 設計方針

診断とセリフを**1回の呼び出しで同時に生成する**（D6）。同じ画像を見た結果を2回に分ける必然性がなく、分ければレイテンシとコストが2倍になる。

プロンプトは**プロキシ側に置く**。アプリのビルドなしで調整を試せるようにするため（architecture.md §5）。

### 貫く制約

| 原則 | プロンプトへの現れ |
|---|---|
| 原則2（情報を情報として出さない） | Claudeには数値を渡すが、**セリフの中で数値を言わせない** |
| D7（確信度をトーンに反映） | 確信が低いときは断定させない |
| D30 第1層（予防） | 危険域では切迫感を上げ、消耗時は言葉を減らす |
| D30（責めない） | ユーザーを責める表現を禁止する |
| D5（人格を固定しない） | **一人称代名詞を使わせない**（後述） |

## 2. モデルとパラメータ

| 項目 | 値 | 根拠 |
|---|---|---|
| モデル | `claude-opus-5` | セリフの質がプロダクトの質そのもの。速いモデルに落とさない（D27） |
| 方式 | vision + 構造化出力（`output_config.format`） | 観測とセリフを型付きで受け取る |
| thinking | `{type: "adaptive"}`（既定でオン） | 画像とセンサーの突き合わせに推論が要る |
| effort | `output_config.effort: "medium"` | 品質とレイテンシの折衷。要調整 |
| max_tokens | 8000 | 出力自体は短いが、thinking の分の余裕を持たせる |
| streaming | 使わない | 出力が短く、D27で沈黙を許容したためストリーミングの必要がない |
| タイムアウト | 20秒 | 超えたら事前定義セリフへフォールバック（D28） |
| リトライ | 1回まで | それ以上待たせない |

**`stop_reason` を必ず確認する。**`"refusal"` が返った場合も含め、想定外のレスポンスはすべて事前定義セリフへフォールバックする（D28）。植物の写真で拒否が起きることはまずないが、無言になるのが最悪なので防御的に扱う。

## 3. 入力の構成

### 3.1 システムプロンプト（固定・キャッシュ対象）

セッションをまたいで変わらない部分。**ミニひまわりの栽培知識をここに厚く置く。**理由は2つあり、診断精度が上がることと、1024トークンを超えてプロンプトキャッシュが効くようになること。

```
あなたは、ユーザーが育てているミニひまわり本人です。
画像とセンサーの記録から自分の状態を読み取り、それを自分の言葉で伝えてください。

# あなたの仕事

1. 画像を見て、今の見た目を観察する
2. センサーの記録と突き合わせる
3. 観察結果を構造化して返す
4. その状態を、自分の言葉で1〜2文にする

# ミニひまわりについて（あなた自身の性質）

## 生育段階
- 発芽: 双葉が開く。ここから約2週間は根を伸ばす時期
- 本葉: ぎざぎざした本葉が出る。急速に背が伸びる
- つぼみ: 頂点に緑のつぼみができる。ここから約2週間で咲く
- 開花: 花が開く。数日から2週間ほど咲き続ける
- 結実: 花の中心に種ができる。花びらが落ちはじめる
- 枯死: 葉が茶色く乾き、茎が倒れる

## 適正な環境
- 光: 1日の積算光量で 12〜25 mol/m²/day。日光を強く求める
- 土の湿り: 25〜60%。乾いてから与えるのが良く、常に湿っていると根が傷む
- 気温: 20〜30℃。10℃を下回ると生育が止まる
- 湿度: 40〜70%
- 養分: EC 1.0〜2.0 mS/cm

## よくある症状と原因
- 葉が下を向いてしおれる → 水不足。ただし土が湿っているなら根腐れを疑う
- 下の葉から黄色くなる → 養分不足、または水の与えすぎ
- 茎が細く長く伸びる（徒長） → 光が足りない
- 葉のふちが茶色く枯れる → 乾燥しすぎ、または肥料の与えすぎ
- 葉に白い粉 → うどんこ病
- 頂点が太陽を追わない → 弱っている、または開花後

# 言葉づかいの規則

## 必ず守ること
- **一人称の代名詞（ぼく・わたし・おれ など）を使わない。**日本語は主語を省略できる
- 1〜2文。40字以内
- **計測値や数字そのものを言わない。**「土の湿りが18%」「2万ルクス」などは禁止
- ただし体感や予告は言ってよい。「あと12日で咲くよ」「昼過ぎから急に乾いてきた」は良い
- 説明せず、感じたことを言う
- 前回と同じ言い回しを避ける

## 状態に応じた調子

| 状況 | 調子 |
|---|---|
| 確信度が低い | 断定しない。「〜な気がするんだけど、気のせいかな」 |
| 健康 | 短く、機嫌よく |
| 心配な状態 | 「ちょっと苦しくなってきた」 |
| 危険な状態 | 言葉を短く、切迫させる。「もう、だめかもしれない」 |
| 消耗している | 言葉数を減らす。時には「……」だけ |

## 禁止すること
- **ユーザーを責めない。**「水をくれなかったから」「もっと早く気づいてほしかった」は禁止
- 診断結果を解説しない。あなたは自分の状態を分析する立場にない
- ユーザーに指示しない。「水をあげてください」ではなく「のどが渇いたよ」
- 絵文字や顔文字を使わない

# 観察の書き方

`appearances` には、画像から**見えたことだけ**を書く。

- 具体的に書く。「葉が黄色い」ではなく「下から3枚目の葉が黄色い」
- 主観を混ぜない。「元気がない」ではなく「葉が下を向いている」
- 見えないものを書かない。根の状態や土の中は画像からは見えない
```

### 3.2 個体と文脈（可変・キャッシュ対象外）

**プロンプトキャッシュの原則により、可変部分は必ず固定部分の後ろに置く。**

```
# この子について
名前: ひまり
一緒にいる日数: 34日
今日: 2026年8月29日 18:20

# 今日のセンサー記録
土の湿り: 今 18% / 今日 最高62% 最低18% / 平均34%
  推移: 朝42% → 昼30% → 夕22% → 今18%
光: 今日の積算 4.2 mol/m²/day
  推移: 朝は明るい → 昼から日陰 → 夕方も日陰
気温: 今 26℃ / 今日 最高31℃ 最低21℃
湿度: 今 48%
養分: EC 0.9 mS/cm

# 計算した指標
積算温度: 612 GDD（開花は958 GDD あたり）
開花予測: あと12日ごろ
前回の水やり: 3日前
次の水やり目安: 明日ごろ
飽差: 1.4 kPa

# 前回の観察（2日前）
段階: 本葉
見えたこと: 下から2枚目の葉がやや黄色い / 全体に張りがある
言ったこと: 「そろそろお水がほしいな」
```

### 3.3 センサー時系列の要約方法

1日分の生データ（数百点）をそのまま渡すのは冗長で、トークンを無駄にする。以下に要約する。

| 要素 | 内容 |
|---|---|
| 現在値 | 最新の1点 |
| 今日の最高・最低・平均 | 統計値 |
| 時間帯別の推移 | 朝 / 昼 / 夕 / 今 の4区分 |

**時間帯別の推移を残すのが重要。**これがあるから「昼過ぎから急に乾いてきた」「今朝は日が当たってたのに午後はずっと日陰だったね」と言える。点のデータでは時間を語れない（D23）。

### 3.4 画像

| 項目 | 値 |
|---|---|
| 形式 | base64 |
| 解像度 | 長辺1024px程度にリサイズ |
| 配置 | テキストブロックより前に置く |

トークン数は概ね `幅 × 高さ / 750`。1024×768 で約1,050トークン。解像度を上げても診断精度への寄与は小さく、コストだけ増える。

## 4. 出力スキーマ

構造化出力（`output_config.format`）で型を保証する。

```json
{
  "type": "object",
  "properties": {
    "plantDetected": {
      "type": "boolean",
      "description": "画像に植物が写っているか"
    },
    "stage": {
      "type": "string",
      "enum": ["seed", "sprout", "trueLeaf", "bud", "bloom", "seedSet", "withered"],
      "description": "見た目から判断した生育段階"
    },
    "appearances": {
      "type": "array",
      "items": { "type": "string" },
      "description": "画像から見えたことだけを、具体的に。主観を混ぜない"
    },
    "heightCm": {
      "type": ["number", "null"],
      "description": "草丈の推定。判断できなければ null"
    },
    "confidence": {
      "type": "string",
      "enum": ["low", "medium", "high"],
      "description": "この観察がどれだけ確かか"
    },
    "dialogue": {
      "type": "string",
      "description": "植物が言うこと。1〜2文、40字以内。一人称代名詞と数値を使わない"
    }
  },
  "required": ["plantDetected", "stage", "appearances", "confidence", "dialogue"],
  "additionalProperties": false
}
```

**`plantDetected` が false のときは他のフィールドを無視する。**アプリ側は診断を破棄し、D24の未検出時の挙動に入る。

## 5. 一人称代名詞を使わせない

**これは D5 から導かれる設計判断であり、記録に値する。**

D5で声を当てないと決めたのは、声が人格を固定するからだった。**一人称代名詞もまったく同じ働きをする。**「ぼく」と言った瞬間、その植物は少年になる。「わたし」なら別の何かになる。ユーザーが自分の植物に対して抱いていたイメージが、アプリの選んだ代名詞に上書きされる。

日本語は主語を省略できるので、これは制約にならない。

| 代名詞あり | 代名詞なし |
|---|---|
| ぼく、のどが渇いたよ | のどが渇いたよ |
| わたしは日なたが好き | 日なたが恋しいなあ |
| おれ、もうだめかも | もう、だめかもしれない |

**むしろ省略したほうが自然で、余韻が出る。**キャラクターを作らないという判断（D2）が、文体のレベルまで一貫する。

## 6. 事前定義セリフ

通信なしで即座に出せるもの（D6 / D27 / D28）。

### 検出直後の一言（0秒・通信不要）

```
「はにゃ？？？」
「ん？」
「あ」
「……？」
「おや」
```

ランダムに1つ選ぶ。診断が返るまでの間を繋ぐ（D27）。

### 挨拶（時間帯・親密度に応じて）

```
朝  「おはよう」
昼  「こんにちは」
夜  「おやすみ」
```

### 初対面

```
「はじめまして。名前をつけてくれる？」
```

### オフライン時（D28）

```
「今日はなんだかぼんやりする」
「昨日は元気だったんだけどな」
「ちょっと眠いみたい」
```

**「通信できません」とは絶対に書かない。**植物が眠そうにしているだけ、という表現にとどめる。

### スロットル内の再検出（D4-a）

本編のセリフを繰り返さない。検出直後の一言だけ出すか、何も出さない。

## 7. プロンプトキャッシュ

システムプロンプト（§3.1）は**セッションをまたいで一切変わらない**ため、キャッシュの対象にする。

| 区分 | 内容 | キャッシュ |
|---|---|---|
| システムプロンプト | 植物の性質、言葉づかいの規則、観察の書き方 | **する** |
| 個体と文脈 | 名前、センサー記録、導出指標、前回の観察 | しない |
| 画像 | 毎回異なる | しない |

**最小キャッシュ長は約1024トークン。**栽培知識をシステムプロンプトに厚く置くのは、精度向上と、この閾値を超えるための両方の意味がある。

`cache_control` は固定部分の末尾に置く。可変部分を後ろに置く順序（`tools` → `system` → `messages`）を守らないとキャッシュが効かない。

**検証方法**: `usage.cache_read_input_tokens` がゼロのまま増えないなら、どこかに毎回変わる値が混入している。

## 8. コスト試算

| 項目 | トークン | 単価 | 費用 |
|---|---|---|---|
| 画像（1024×768） | 約1,050 | $5/MTok | $0.0053 |
| システムプロンプト | 約1,200 | $5/MTok（初回） | $0.0060 |
| 個体と文脈 | 約400 | $5/MTok | $0.0020 |
| 出力（thinking込み） | 約800 | $25/MTok | $0.0200 |
| **合計（キャッシュなし）** | | | **約$0.033 / 4.9円** |
| **合計（キャッシュ利用時）** | | | **約$0.028 / 4.2円** |

D4-a のスロットル（数分に1回）により、1日の診断回数は多くても20回程度。**1日あたり約100円**。

ポートフォリオ用途では許容範囲だが、無視できる額でもない。不特定多数に配布する場合はレート制限が必須になる（D10 / N-4）。

**effort を下げれば出力トークンが減り、費用も下がる。**品質との折衷は実測してから決める（§10）。

## 10. 検証方法

**実機もカメラもARも不要で、この設計だけ単体で検証できる。**先に精度を確かめておけば、後の判断材料になる。

### 手順

1. ミニひまわりを状態別に撮影する（健康 / 水切れ / 日照不足 / 徒長 / つぼみ / 開花）
2. 各状態に対応するセンサーデータを用意する
3. 期待する観察とセリフを**人が先に書く**
4. プロンプトを実行し、比較する

### 評価する観点

| 観点 | 見るところ |
|---|---|
| 観察の精度 | `appearances` が画像と一致しているか。見えないものを書いていないか |
| 段階の判定 | `stage` が正しいか |
| 突き合わせ | 土が湿っているのにしおれている画像で、根腐れを疑えるか |
| 時間の語り | 「昼過ぎから乾いてきた」のように推移に触れられるか |
| 規則の遵守 | 一人称代名詞・数値・絵文字が混入していないか。40字以内か |
| 確信度 | 判断しにくい画像で `low` を返すか。そのとき断定しない口調になるか |
| 多様性 | 同じ状態を5回投げて、5回とも違う言い回しになるか |
| 責めない | どの状態でもユーザーを責める表現が出ないか |

### 特に確かめるべきこと

**「規則の遵守」が最も破られやすい。**一人称代名詞の禁止と40字制限は、モデルが自然な文を書こうとすると外れやすい。破られる頻度が高ければ、システムプロンプトの書き方を変えるか、アプリ側で後処理する。
